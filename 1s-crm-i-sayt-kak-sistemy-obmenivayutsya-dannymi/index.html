АРХИТЕКТУРА // SYSTEM_INTEGRATION_OVERVIEW

На схеме интеграция 1С, CRM и сайта часто выглядит элементарно:

На практике такая схема почти ничего не говорит о том, что именно происходит с данными.

Где хранится актуальная цена?
Какая система знает настоящий остаток товара?
Кто создаёт заказ?
Где меняется его статус?
Что происходит, если менеджер изменил данные в CRM, а через минуту в 1С пришла другая информация?
А если сайт был недоступен два часа?

Именно на таких вопросах заканчиваются простые интеграции и начинается нормальная архитектура обмена данными.

Потому что задача заключается не в том, чтобы «соединить 1С с сайтом».

Задача — построить систему, в которой несколько независимых приложений согласованно работают с одними и теми же бизнес-данными.

коммуникации;
задачи;
история работы с клиентом.

ПРАВИЛА ДАННЫХ // DATA_SOURCE_OF_TRUTH

Главное правило: у каждого типа данных должен быть источник истины

Одна из самых частых ошибок — хранить одни и те же данные как независимые значения сразу в нескольких системах.

Например:

// CONFLICT_DUPLICATION_RISK //
Цена
 ├── 1С: 5 490 ₽
 ├── CRM: 5 490 ₽
 └── Сайт: 5 490 ₽

Пока значения одинаковые, кажется, что всё работает.

Но затем кто-то изменил цену в 1С.

Через час сайт всё ещё показывает старую.

CRM содержит третье значение.

И уже непонятно, какая цифра правильная.

Поэтому ещё до разработки интеграции нужно определить:

Какая система является владельцем конкретного типа данных?

Например:

Данные: Товар
Источник истины: 1С
Данные: Цена
Источник истины: 1С
Данные: Остаток
Источник истины: 1С
Данные: Клиент
Источник истины: CRM
Данные: Задачи менеджеров
Источник истины: CRM
Данные: Контент страницы
Источник истины: Сайт
Данные: Корзина
Источник истины: Сайт
Данные: Заказ
зависит от архитектуры

Последняя строка особенно важна.

Заказ может появиться на сайте, но после оформления стать объектом CRM и затем документом в 1С.

Чтобы избежать циклического обмена, необходимо различать исходные изменения и обновления, полученные от другой системы. Для этого используют идентификаторы событий, сведения об источнике изменения, версии объектов или другие механизмы контроля. Простое сравнение значений не всегда достаточно: одинаковое значение может быть повторно отправлено, а два разных изменения могут прийти почти одновременно. Для каждого поля необходимо заранее определить правила разрешения конфликтов.

Системы могут хранить связанные представления одного бизнес-объекта, используя общие внешние идентификаторы. При этом необходимо определить, какая система отвечает за создание заказа, его коммерческие условия, исполнение и итоговый статус. В CRM заказ может быть представлен сделкой или заявкой, а в 1С — документом; эти объекты не следует считать полностью взаимозаменяемыми.

 

ТОПОЛОГИЯ // INTEGRATION_LAYER_ISOLATION

Не нужно синхронизировать всё со всем

На первый взгляд хочется построить такую архитектуру:

Каждая система напрямую общается с каждой.

Сначала это кажется удобным.

Потом появляется новая система.

Например, интернет-магазин, мобильное приложение, сервис доставки и аналитическая платформа.

Связей становится всё больше:

// DEPENDENCY_OVERLOAD_LOG //
10:37:05 1С ↔ CRM
10:37:06 1С ↔ Сайт
10:37:06 CRM ↔ Сайт
10:37:07 1С ↔ Мобильное приложение
10:37:07 CRM ↔ Мобильное приложение
10:37:08 Сайт ↔ Аналитика
...

Каждая новая интеграция добавляет новые зависимости.

Поэтому в крупных проектах часто появляется отдельный интеграционный слой:

Он может отвечать за преобразование данных, очереди, маршрутизацию, журналирование и повторную обработку.

 

ИДЕНТИФИКАЦИЯ // DATA_MAPPING_STRATEGY

Один товар в разных системах — это не три разных товара

Предположим, в 1С товар имеет идентификатор:

SKU = 10482

На сайте он может иметь:

product_id = 7815

В CRM:

product_id = 322

Если интеграция каждый раз пытается сопоставлять товары по названию, неизбежно появятся проблемы.

Название может измениться.
Может отличаться написание.
Могут появиться одинаковые названия у разных товаров.

Поэтому нужен устойчивый идентификатор товара и таблица соответствий между его идентификаторами в разных системах. Артикул или SKU можно использовать для сопоставления, если обеспечены его уникальность и стабильность; надёжнее хранить отдельный внутренний идентификатор интеграции и явные связи с идентификаторами 1С, сайта и CRM.

Например:

Система должна понимать:

10482, 7815 и 322 — это разные технические идентификаторы одного товара.

Такое сопоставление называют mapping (сопоставлением идентификаторов).

И чем больше интеграций, тем важнее держать его под контролем.

СЕМАНТИКА // PRICE_SEMANTICS_CONTEXT

Цена — не просто число

В реальном бизнесе цена редко является одним простым полем.

Могут существовать:

розничная цена;
оптовая цена;
цена для конкретного клиента;
акция;
минимальная цена;
цена с НДС или без НДС;
разные цены для разных каналов.

Например:

// EXTENDED_PRICE_SCHEMA //
Базовая цена:6 000 ₽
Цена сайта:5 490 ₽
Оптовая цена:5 100 ₽
Цена по акции:4 990 ₽

Если передавать в CRM только поле price, без указания типа цены и условий её применения, получатель не сможет однозначно определить её смысл. Вместе со значением необходимо передавать или однозначно определять тип цены, валюту, условия применения и, если применимо, период действия.

Поэтому ещё на этапе проектирования нужно определить семантику каждого поля.

Интеграция должна передавать не просто значения.

Она должна передавать значения в понятном контексте.

 

ЛОГИСТИКА // STOCK_SEMANTICS_CALCULATION

Остатки — ещё сложнее

С остатками ситуация похожая.

В 1С может быть:

// 1C_WAREHOUSE_STOCKS //
Склад Москва:35 шт.
Склад Санкт-Петербург:12 шт.
Резерв:8 шт.
В пути:20 шт.

А сайту нужно показать:

Доступно: 39 шт.

Прогнозируемая доступность с учётом разрешённых поступлений: 59 шт.

При этом поступления в пути не следует включать в доступное количество автоматически: это зависит от бизнес-правил, подтверждения поставки и требований к резервированию.

Для него может рассчитываться отдельный показатель:

Доступно =
остатки
− резерв
+ разрешённые поступления

Правила зависят от бизнеса.

И это хороший пример того, почему интеграция — не механическая пересылка полей.

Между системами существует бизнес-логика.

С товарами поток часто идёт из 1С на сайт.

С заказом всё наоборот.

Покупатель оформляет его на сайте:

После этого информация должна попасть дальше.

Например:

Но в каждой системе заказ может получить собственный идентификатор:

// LOCAL_ORDER_IDENTIFIERS //
Сайт: 100582
CRM:  45821
1С:   0000-123456

И снова нужен mapping.

В системе важно хранить связь:

Тогда любой участник цепочки может однозначно понять, о каком заказе идёт речь.

 

ФИНАНСОВАЯ НАДЕЖНОСТЬ // TRANSACTION_IDEMPOTENCY

Почему нельзя просто отправить заказ два раза

Представим:

// DUPLICATE_ORDER_RISK //
• сайт отправил заказ в 1С;
• 1С его успешно создала;
• ответ потерялся;
• сайт решил, что произошла ошибка;
• отправил заказ повторно.

Если принимающая система не проверяет повторную обработку, один и тот же заказ может быть создан в 1С дважды. Поэтому перед повторной отправкой необходимо проверять результат предыдущей попытки и использовать устойчивый идентификатор операции или ключ идемпотентности. Если первая операция завершилась успешно, повторный запрос должен возвращать её результат, а не создавать новый документ.

Поэтому интеграции должны учитывать идемпотентность.

Перед созданием документа можно проверить:

Внешний ID = 100582

Если такой заказ уже существует:

не создавать новый

а вернуть существующий объект.

Это особенно важно для заказов, платежей и других операций, где повторная обработка может иметь реальные финансовые последствия.

 

СИНХРОНИЗАЦИЯ // ORDER_STATUS_MAPPING

Статус заказа тоже является данными

Заказ может пройти длинную цепочку:

Но разные системы могут использовать разные статусы.

Например:

// SYSTEM_STATUS_MISMATCH_LOG //
1С:
Отгружен

Сайт:
Передан в доставку

CRM:
Заказ выполнен

Поэтому между системами нужен словарь соответствий:

Одного словаря соответствий недостаточно, если статусы отражают разные этапы процесса. Необходимо определить допустимые переходы и правила обработки запоздавших событий. Например, поздно пришедшее уведомление «Заказ принят» не должно возвращать уже отгруженный заказ в начальное состояние. Если системы используют разные модели жизненного цикла, соответствие статусов должно учитывать бизнес-смысл, а не только названия.

 

КОНФЛИКТЫ // BIDIRECTIONAL_CONFLICT_RESOLUTION

Двусторонний обмен требует особенно аккуратной логики

Представим:

Цена изменилась в 1С, и сайт получил новую цену.

Всё просто.

Но если сайт тоже может изменять цену:

возникает вопрос:

кто теперь главный?

Если оба источника могут менять одно поле, появляется конфликт.

Например:

// INFINITE_LOOP_RACE_CONDITION //
10:00 — 1С: 5 490 ₽
10:01 — Сайт: 5 290 ₽
10:02 — 1С: 5 490 ₽
10:03 — Сайт: 5 290 ₽

Можно получить бесконечную борьбу изменений.

Поэтому для каждого поля необходимо определить:

кто может его менять;
кто является владельцем;
куда изменение передаётся;
что происходит при конфликте.

Чем больше двусторонних связей, тем важнее эти правила.

 

РЕЖИМЫ ОБМЕНА // SYNCHRONIZATION_STRATEGIES

Синхронизация бывает разной

Не все данные нужно передавать одинаково.

Периодический обмен

Например, сайт проверяет остатки каждые пять минут.

Это простой и надёжный вариант, если задержка в несколько минут допустима.

Событийный обмен

Если данные должны передаваться практически сразу:

Например, изменение остатка может практически сразу отразиться на сайте.

Комбинированный вариант

На практике часто используются оба подхода.

События обеспечивают оперативность, а периодическая сверка обнаруживает то, что по какой-либо причине не дошло.

Это гораздо надёжнее, чем рассчитывать только на один механизм.

 

ОТКАЗОУСТОЙЧИВОСТЬ // FAILOVER_RETRY_POLICY

А что если данные не дошли?

Ошибки обмена — нормальная часть любой интеграции.

Проблема не в том, что ошибка произошла.

Проблема — если система не умеет её обнаружить и обработать.

Например:

Сайт вернул:

500 Internal Server Error

Интеграция должна понимать:

можно ли повторить запрос;
сколько раз;
через какой интервал;
нужно ли уведомить администратора;
надо ли поместить операцию в очередь;
нужно ли отменить дальнейшую цепочку.

 

КЛАССИФИКАЦИЯ // ERROR_CLASSIFICATION_RETRY

Повторять нужно не все ошибки

Например:

500
503
timeout

могут быть временными ошибками.

Повторная попытка имеет смысл.

Но:

400
invalid field
missing required value

обычно требуют исправления данных.

Если автоматически повторять такой запрос сто раз, ничего не изменится.

Поэтому ошибки стоит классифицировать.

Отдельно нужно обрабатывать HTTP 429 (превышение допустимой частоты запросов), ошибки авторизации 401 и 403, а также конфликты данных, например HTTP 409. Для ошибки 429 следует учитывать указанный сервером интервал ожидания, ошибки авторизации требуют проверки учётных данных и прав, а конфликты обычно требуют сверки состояния объектов. Повторная отправка без устранения причины не гарантирует успешного результата.

Это снижает нагрузку на систему, которая и так может находиться под нагрузкой.

 

БУФЕРИЗАЦИЯ // TRANSACTIONAL_QUEUES

Как обеспечить сохранность изменений при сбоях

Для важных операций полезно использовать очередь сообщений или заданий.

Например:

Если сайт недоступен:

При этом основной процесс в 1С не обязательно должен ждать ответа сайта. Очередь защищает от потери изменений только при правильной реализации. Сообщение должно надёжно сохраняться до подтверждения обработки, а фиксация исходной бизнес-операции и постановка события в очередь не должны приводить к ситуации, когда одно выполнено, а другое потеряно. Для этого применяют устойчивое хранение и, при необходимости, паттерн Transactional Outbox. Получатель также должен уметь безопасно обрабатывать повторно доставленные сообщения.

Это особенно важно для больших объёмов данных.

 

ДИФФЕРЕНЦИАЦИЯ // DATA_DIFF_SYNCHRONIZATION

Полная синхронизация и обмен изменениями

Есть два принципиально разных подхода.

Первый:

Передать все 100 000 товаров

Второй:

Для больших каталогов второй вариант значительно эффективнее.

Но тогда системе необходимо отслеживать изменения:

время изменения;
версию;
статус синхронизации;
внешний ID;
результат последней передачи.

Например:

// OBJECT_SYNC_SUCCESS //
SKU 10482
Изменён: 10:42
Передан: 10:42
Результат: OK

А если возникла ошибка:

// OBJECT_SYNC_FAILURE //
SKU 10482
Изменён: 10:42
Передан: 10:43
Результат: ERROR
Следующая попытка: 10:48

Такой журнал позволяет контролировать не просто факт запуска обмена, а результат обработки каждого объекта.

 

РЕЖИМЫ ИНТЕГРАЦИИ // ARCHITECTURAL_SYNC_MODES

Начальная загрузка и последующая синхронизация — разные задачи

Это часто упускают из виду.

Когда интеграцию запускают впервые, нужно передать большой объём данных:

// INITIAL_BULK_LOAD //
50 000 товаров
20 000 клиентов
10 000 заказов

Это начальная загрузка.

Во время начальной загрузки данные в источнике могут продолжать изменяться. Поэтому необходимо определить контрольную точку, с которой фиксируются новые изменения, и обеспечить их последующую передачу после завершения загрузки. Иначе часть обновлений может потеряться между выгрузкой старых данных и запуском регулярной синхронизации. Перед переключением в рабочий режим полезно выполнить контрольную сверку количества объектов и ключевых полей.

После запуска ежедневный процесс выглядит совершенно иначе:

// REGULAR_INCREMENTAL_SYNC //

42 новых заказа
17 новых клиентов

Нельзя проектировать ежедневную синхронизацию так, будто каждый раз нужно переносить всю базу.

ИЗОЛЯЦИЯ // SYSTEM_CHANGE_ADAPTABILITY

Интеграция должна переживать изменения систем

1С, CRM и сайт не стоят на месте.

Меняются:

версии;
API;
структуры данных;
обязательные поля;
бизнес-правила;
каталоги;
статусы;
форматы документов.

Поэтому интеграция должна быть построена так, чтобы изменение одной системы не приводило к каскадному переписыванию всего решения.

Именно здесь особенно полезен отдельный слой преобразования.

Если API CRM изменился, корректируется её адаптер.

Внутренняя модель и логика остальных систем при этом могут остаться прежними.

Поэтому полезно хранить состояние обмена:

08:15

После восстановления:

Само хранение времени последней успешной синхронизации не гарантирует восстановление всех изменений после простоя. Необходимо сохранять возможность определить пропущенные изменения, повторно передать их после восстановления связи и сверить итоговое состояние систем. Если источник не хранит историю изменений, может потребоваться полная или частичная повторная синхронизация.

ИТОГ // ECOSYSTEM_DECOUPLING_SUMMARY

Главное — не сделать три системы одним большим справочником

Хорошая интеграция не означает, что во всех системах должны находиться абсолютно одинаковые данные.

Наоборот.

Каждая система должна хранить то, за что она отвечает, а обмен должен передавать ровно те данные, которые нужны другой стороне для работы.

// 1C REGION //
1С не обязана знать всё, что происходит в интерфейсе сайта.
// WEB REGION //
Сайт не должен хранить всю внутреннюю бухгалтерскую информацию.
// CRM REGION //
CRM не должна превращаться в копию ERP.

Задача интеграции — обеспечить согласованность необходимых данных, а не создать три одинаковые базы.

Итог

Связать 1С, CRM и сайт технически можно довольно быстро.

Нужно заранее определить:

кто является источником истины;
какие данные передаются;
какие системы могут их изменять;
как идентифицируются объекты;

как передаются цены и остатки;
как проходит заказ;
как сопоставляются статусы;
что происходит при повторной отправке;
как обрабатываются ошибки;
где хранится очередь;
как выполняется повторная обработка;
как обнаруживаются расхождения;
как контролируется результат обмена.
