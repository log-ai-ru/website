Api, webhook или очередь сообщений?

 

 

 

 

LOG-AI / SYSTEM INTEGRATION TECHNICAL ANALYSIS

Как выбрать способ обмена данными между системами

 

Покупатель оплатил заказ на 12 490 рублей один раз, а на складе распечатали два листа сборки. В выписке банка один платёж, в учётной системе один заказ, отгрузок две. Дефекта в коде отгрузки не нашлось: обе команды были сформированы правильно. Разбор журналов выглядел так:

EVENT TRACE / ORDER #A-482913 INCIDENT LOG
14:02:10 / EVENT SENT

Платёжный сервис отправляет магазину уведомление «заказ оплачен». Это HTTP-запрос на адрес, который магазин заранее указал в настройках; такой механизм называют webhook (вебхук, обратный вызов по HTTP).

14:02:11 / PROCESSING

Магазин принимает уведомление и передаёт команду на отгрузку в складскую систему, которая в этот момент пересчитывает остатки.

14:02:20 / TIMEOUT

Платёжный сервис не получил ответ за 10 секунд и считает попытку неудачной.

14:02:25 / CONNECTION CLOSED

Склад принимает команду. Магазин пытается ответить «принято», но соединение уже закрыто.

14:02:50 / RETRY

Платёжный сервис повторяет уведомление. Магазин не знает, что оно уже обрабатывалось, и формирует вторую команду.

Каждый участник вёл себя штатно. Провайдер повторяет доставку, если не получил подтверждения в установленный срок. Магазин отвечает после того, как закончил работу. Склад тратит на команду столько времени, сколько нужно. Ошибочным было представление о том, что обещает такой способ передачи: webhook сам по себе не гарантирует доставку. Если отправитель реализует повторные попытки, событие может прийти несколько раз. Получатель обязан учитывать это, а конкретные гарантии доставки определяются контрактом отправителя.

ROOT CAUSE / ARCHITECTURAL ERROR

Подобные инциденты возникают потому, что API, webhook и очередь сообщений воспринимают как варианты одного действия: «передать данные из системы А в систему Б». Различаются они не форматом, а тем, кто инициирует передачу, где хранится недоставленное сообщение, как подтверждается приём и что происходит при сбое. Ниже эти различия разобраны по механике, затем даны условия выбора, расчёты и испытания, которые стоит провести до запуска.

01 / TRANSPORT MODELS

Три способа, которые различаются ответственностью, а не форматом

API в том узком смысле, который здесь нужен, означает синхронный вызов: клиент отправляет запрос, сервер отвечает, и пока ответ не получен, результат клиенту неизвестен. Само слово шире: API (application programming interface, программный интерфейс) называют любой описанный набор операций, через который одна программа обращается к другой. Чаще всего это HTTP-запросы с телом в JSON, текстовом формате для структурированных данных. Если сервер недоступен, клиент получает ошибку или таймаут и сам решает, что делать дальше. Таймаут не означает, что сервер не выполнил операцию: он мог завершить её, но ответ не дошёл до клиента.

Webhook устроен наоборот: источник сам отправляет HTTP-запрос на адрес получателя в момент события. Технически это тот же вызов API, только инициатором выступает источник события, поэтому получатель должен иметь адрес, доступный отправителю. Недоставленное уведомление может хранить и повторять отправитель по собственным правилам: сколько попыток, с какими паузами и в течение какого времени. Это необходимо уточнять в документации конкретного провайдера.

Очередь сообщений (message queue) вводит посредника — брокера (broker). Он принимает сообщение, сохраняет его в соответствии с настройками надёжности и отдаёт получателю, когда тот готов. Отправитель и получатель не обязаны работать одновременно и не знают адресов друг друга. Недоставленное сообщение хранится в брокере, то есть в инфраструктуре, которую компания эксплуатирует сама либо использует как управляемый сервис.

Чтение истории

Соединения

OPERATIONAL RESPONSIBILITY

У каждой модели есть собственная зона ответственности получателя:

  • API — обработка результата, ошибок и безопасных повторов.
  • Webhook — проверка подлинности, быстрая фиксация, дедупликация, обработка повторов.
  • Очередь — подтверждения, дедупликация, обработка повторов, контроль накопления.

Зависимость от доступности также различается. Для API она важна в момент вызова. Для webhook она важна для приёма, но отправитель может повторить доставку позже. Для очереди одновременная доступность отправителя и получателя не требуется, если сообщение надёжно сохранено брокером.

Три способа не исключают друг друга. Обычная связка для внешнего источника выглядит так: тонкий приёмник принимает webhook, проверяет подпись, сохраняет событие в собственной базе или надёжно передаёт его брокеру и быстро отвечает. Отдельный обработчик выполняет бизнес-операцию, а при необходимости дочитывает актуальное состояние через API. Поэтому вопрос «что выбрать» чаще означает «что поставить на какой границе».

02 / MESSAGE STORAGE

Очередь и журнал: два устройства под одним названием

Слово «очередь» скрывает разные модели хранения и чтения. В классическом брокере (например, RabbitMQ) сообщение маршрутизируется в очередь, доставляется одному из потребителей и после подтверждения может быть удалено. Правила маршрутизации определяют, в какую очередь оно попадёт. Такая схема подходит для задач: «отправить письмо», «пересчитать счёт», «сформировать документ».

Журнал (класс решений вроде Apache Kafka) устроен иначе. Это последовательность записей, в которую сообщения дописываются. Журнал разбит на партиции (partition) — независимые последовательности, внутри каждой из которых сохраняется порядок записей. Чтение сообщения не удаляет его: данные хранятся заданное время или до достижения настроенного объёма. Каждая группа потребителей запоминает собственную позицию (offset, смещение), поэтому новый потребитель может прочитать доступную историю, а существующий — повторно обработать данные, переместив позицию назад.

STORAGE MODEL / COMPARISON QUEUE ≠ LOG

Классическая очередь

TASK DISTRIBUTION

Сообщение предназначено для обработки. После подтверждения оно обычно исчезает из очереди. Потребители распределяют работу между собой.

 

Журнал событий

EVENT STREAM

Запись остаётся в журнале после чтения. Разные группы потребителей могут независимо читать одни и те же события и возвращаться к доступной истории.

СХЕМЫ КОНЦЕПТУАЛЬНЫЕ. Фактическое распределение сообщений зависит от конфигурации брокера и модели потребления.

Различие не абсолютно: отдельные брокеры поддерживают хранение, повторное чтение или дополнительные режимы доставки, а журналы могут использоваться и для распределения задач. Но классическая очередь обычно ориентирована на передачу работы, а журнал — на сохранение последовательности событий и независимое чтение разными потребителями.

Как правило, команды и задачи ложатся на очередь, а факты о случившемся, которые нужны нескольким потребителям и могут потребовать перечитывания, — на журнал. Журнал даёт повтор истории ценой дискового пространства, политики хранения и понимания партиций. Классический брокер даёт гибкую маршрутизацию и распределение задач, но после подтверждения сообщения его история обычно недоступна.

ARCHITECTURAL RULE

Очередь отвечает на вопрос: «Кто должен выполнить эту работу?». Журнал отвечает на вопрос: «Какие события произошли и кто хочет их прочитать?». Это разные задачи, даже если технически обе модели используют брокер сообщений.

03 / SYNCHRONOUS COMMUNICATION

Синхронный API: простота, за которую платят связностью

Синхронный вызов уместен, когда результат нужен в том же действии: рассчитать стоимость доставки до подтверждения заказа, проверить остаток, получить справочные данные. Доступность вызываемого сервиса здесь является частью процесса. Если справочник недоступен, оформить заказ всё равно нельзя, и очередь добавила бы только иллюзию надёжности.

Ломается вызов чаще не на ошибке, а на медлительности. Недоступный сервис возвращает отказ за миллисекунды. Медленный удерживает соединения и потоки вызывающих, пул заканчивается, и вызывающий сервис сам перестаёт отвечать, передавая проблему своим клиентам. Отсюда обязательные таймауты на каждом вызове (у ряда библиотек значение по умолчанию означает «ждать очень долго») и ограничение числа параллельных обращений к одному сервису.

DEPENDENCY CHAIN FAILURE PROPAGATION
Медленный ответ распространяет задержку вверх по цепочке. Если соединения и потоки ограничены, зависание одного сервиса может привести к отказу нескольких соседних систем.

Повторы усиливают сбой. Допустим, цепочка из четырёх сервисов: A вызывает B, B вызывает C, C вызывает D, и на каждом из трёх звеньев заложено до трёх попыток. При неработающем D один исходный запрос может превратиться в 3 × 3 × 3 = 27 обращений к D. Сервис, который пытается подняться, получает вал нагрузки вместо тишины.

Защита состоит из нескольких мер:

01 / RETRY CONTROL

Один уровень повторов

Повторы делаются на одном уровне цепочки, а не на всех.

02 / BACKOFF + JITTER

Растущие интервалы

Паузы между попытками растут по экспоненте со случайным разбросом (exponential backoff with jitter).

03 / CIRCUIT BREAKER

Автоматический выключатель

После серии ошибок клиент на время прекращает обращения и сразу возвращает отказ либо переключается на предусмотренный резервный сценарий.

04 / CONCURRENCY LIMIT

Ограничение параллелизма

Ограничивается число одновременно выполняемых запросов, чтобы отказ одного сервиса не исчерпал ресурсы остальных.

Повтор запроса, который меняет данные (создать платёж, выставить счёт), безопасен только при корректной реализации идемпотентности. Идемпотентность означает, что повторное выполнение операции с теми же параметрами не приводит к повторному бизнес-эффекту.

Клиент генерирует уникальный ключ идемпотентности (idempotency key) и отправляет его вместе с запросом. Сервер сохраняет ключ, параметры операции и результат в надёжном хранилище. При повторе с тем же ключом возвращает сохранённый результат, не выполняя операцию заново. Повтор с тем же ключом, но другими параметрами должен отклоняться.

Тот же механизм потребуется приёмнику webhook и потребителю очереди, различается лишь место хранения ключа и граница защищаемой операции.

04 / PERIODIC DATA RETRIEVAL

Опрос по таймеру: четвёртый способ, о котором забывают

Опрос (polling) — это API, вызываемый по таймеру: получатель каждые N секунд спрашивает источник, не изменилось ли что-нибудь. К нему относятся свысока, хотя в ряде условий он остаётся единственным подходящим способом:

01 / SOURCE LIMITATION

У источника нет webhook.

02 / NETWORK POLICY

Получатель находится во внутренней сети, куда извне ничего не пропускают.

03 / LATENCY TOLERANCE

Задержка в минуты процессу безразлична.

04 / RECONCILIATION

Требуется периодически сверять состояние, даже если уведомления об изменениях могут теряться.

Расчёт на салфетке. Допустим, источник меняет статусы примерно 120 заказов в сутки. Опрос раз в 10 секунд даёт 86 400 / 10 = 8 640 запросов в сутки, из которых полезны 120, то есть около 1,4 %. При равномерном распределении изменений относительно интервала опроса средняя задержка составляет половину интервала — 5 секунд, максимальная при штатной работе — около 10 секунд.

Опрос раз в 5 минут даёт 86 400 / 300 = 288 запросов, среднюю задержку 2,5 минуты и максимальную около 5 минут. Частота опроса остаётся основной ручкой между нагрузкой на источник и задержкой. Многие процессы, например выгрузка статусов в личный кабинет, пять минут переносят без последствий. Если у источника есть лимит запросов (rate limit), он сам задаёт нижнюю границу интервала.

POLLING INTERVAL / LATENCY CONCEPTUAL TIMELINE

Чем чаще опрос, тем быстрее обнаруживается изменение, но тем больше запросов приходится на источник. В реальной системе дополнительно учитываются неравномерность событий, задержки сети и лимиты API.

Главная ошибка инкрементального опроса — запомнить время последнего запроса и в следующий раз просить «всё, что изменено позже». Метка времени может проставляться в начале транзакции, а запись становится видимой другим только после её фиксации.

12:00:00
Транзакция начинается. Метка времени присвоена.
12:00:05

12:00:07

Следующий запрос просит записи позже 12:00:05. Запись с меткой 12:00:00 никогда не будет прочитана.

Защититься можно двумя способами:

METHOD 01 / OVERLAP

Чтение с нахлёстом

Отступать от сохранённой отметки на несколько минут и отбрасывать уже обработанное по идентификатору и версии.

METHOD 02 / CURSOR

Курсор источника

Использовать курсор, который выдаёт сам источник, — стабильную позицию или номер изменения с документированной семантикой, позволяющей продолжать чтение без пропусков.

Курсор не должен просто отражать время запроса. Его корректность зависит от того, как источник фиксирует и выдаёт изменения, включая транзакции, которые становятся видимыми с задержкой.

Той же природы ошибка постраничного чтения со смещением (offset): если данные меняются между запросами страниц, записи сдвигаются, и часть из них читается дважды или пропускается. Курсорная пагинация по стабильному ключу уменьшает этот риск, но гарантии зависят от выбранного ключа и от того, как источник меняет набор данных во время чтения.

05 / WEBHOOK ENGINEERING

Webhook изнутри: что обязан сделать получатель

Приёмник webhook — публичная точка входа, и надёжность схемы определяется тем, что сделано до ответа и после него. У получателя пять обязанностей.

Ключевой принцип: сначала надёжно сохранить событие, затем подтвердить приём. Бизнес-обработка выполняется отдельно и не удерживает соединение отправителя.

1. Отвечать быстро и честно

Код 2xx (успешные ответы HTTP, диапазон 200–299) обычно означает для отправителя «уведомление принято», а не «бизнес-операция завершена», но точное значение зависит от протокола конкретного провайдера. Приём сводится к трём действиям: проверить подлинность, записать событие в собственное надёжное хранилище, вернуть ответ. Остальное делает отдельный обработчик. В истории с двойной отгрузкой этого не хватало: ответ ждал 14 секунд работы склада, а терпение отправителя закончилось на десятой.

Ответ должен подтверждать надёжный приём, а не ждать завершения всей цепочки бизнес-операций.

2. Проверять подлинность

Адрес приёмника публичен, и отправить на него POST-запрос может кто угодно. Если провайдер поддерживает подпись, отправитель подписывает тело запроса общим секретом по алгоритму HMAC (код аутентификации сообщения на основе хеш-функции и секретного ключа) и кладёт подпись в заголовок.

Подпись проверяют по исходным байтам тела до разбора JSON, потому что повторная сериализация меняет пробелы и порядок полей. Сравнивают её функцией с постоянным временем выполнения, чтобы снизить риск атак по времени.

Если протокол подписывает также метку времени, приёмник должен проверять её допустимое окно; это помогает против повторного воспроизведения перехваченного запроса. Но timestamp не заменяет дедупликацию события. Фильтр по IP-адресам отправителя остаётся дополнительной мерой: списки адресов меняются, и опираться на него одного нельзя.

HMAC / VALIDATION SEQUENCE
SOURCE

Формирует исходное тело запроса.

→
HMAC

Вычисляет подпись с секретным ключом.

→

Пересчитывает и сравнивает подпись.

Проверка выполняется над исходными байтами тела запроса. Разбор и повторная сериализация JSON должны происходить после проверки подписи.

3. Отсекать дубли

У каждого события должен быть уникальный идентификатор в рамках источника. Приёмник записывает его в таблицу с уникальным ключом, и повторная вставка сама сообщает о дубле. Пример для PostgreSQL:

POSTGRESQL / INBOX PATTERN SQL
CREATE TABLE inbox_events (
    source       text        NOT NULL,
    event_id     text        NOT NULL,
    received_at  timestamptz NOT NULL DEFAULT now(),
    payload      jsonb       NOT NULL,
    processed_at timestamptz,
    PRIMARY KEY (source, event_id)
);

-- Приёмник: записать событие и ответить после фиксации транзакции.
INSERT INTO inbox_events (source, event_id, payload)
VALUES ($1, $2, $3)
ON CONFLICT (source, event_id) DO NOTHING;

-- Обработчик: выбрать пачку необработанных событий.
SELECT source, event_id, payload
FROM inbox_events
WHERE processed_at IS NULL
ORDER BY received_at
LIMIT 50
FOR UPDATE SKIP LOCKED;
INBOX TABLE / DEDUPLICATION / BATCH PROCESSING

Если вставка не добавила строку, это дубль: приёмник может ответить успешным кодом, если событие ранее было надёжно сохранено, и не повторять бизнес-эффект. Во втором уведомлении из начала статьи именно это остановило бы вторую отгрузку. Конструкция SKIP LOCKED позволяет нескольким обработчикам выбирать разные строки, не ожидая блокировок уже захваченных записей.

WHY UNIQUE CONSTRAINT MATTERS

Уникальный ключ `(source, event_id)` защищает от повторного сохранения одного события. Это не просто проверка в приложении перед INSERT: ограничение базы данных обеспечивает корректность и при одновременном поступлении двух одинаковых запросов.

Однако выборка — ещё не законченная реализация обработчика. Нужно в транзакции определить, как запись получает статус обработки, как освобождается блокировка после ошибки и как повторно подхватывается событие после падения процесса.

Если бизнес-эффект выполняется в той же базе, его и отметку processed_at можно объединить в одну транзакцию. Если эффект внешний — например, вызов склада или платёжного API, — атомарность между ним и локальной базой не возникает автоматически: внешний вызов тоже должен быть идемпотентным либо защищён отдельным механизмом восстановления.

4. Не рассчитывать на порядок

Событие «заказ создан» и событие «заказ оплачен» могут прийти в обратной последовательности, особенно после повторов. Есть два подхода.

METHOD 01 / VERSIONING

Версионирование

Класть в событие версию сущности и применять его, только если версия выше сохранённой. Версия должна отражать порядок изменений в источнике; время события не всегда годится для этого.

METHOD 02 / THIN EVENT

Тонкое событие

Отправлять только тип и идентификатор, а актуальное состояние получать через API. Такой подход устойчивее к перестановкам, но добавляет запрос и зависит от доступности API в момент обработки.

«Толстое» событие с полным состоянием самодостаточно, но к моменту обработки может устареть. В обоих случаях бизнес-правила должны определять, можно ли применять события независимо и как обрабатывать переходы состояния.

5. Признать, что окно повторов конечно

Отправитель может повторять доставку ограниченное время, и у разных провайдеров оно разное. Если получатель лежал дольше окна, события могут быть потеряны безвозвратно. Узнать об этом можно только сверкой: периодической выгрузкой фактического состояния источника через API и сравнением с собственными данными.

Сверка выявляет расхождения; их автоматическое восстановление требует возможности повторно получить данные, определить корректное состояние и безопасно применить исправление. Webhook без сверки — это система, в которой никто не контролирует полноту обмена.

DELIVERY WINDOW / CRITICAL LIMIT

Повторы не являются бесконечной гарантией. Если простой получателя превышает окно повторной доставки отправителя, механизм webhook больше не обеспечивает восстановление пропущенных событий. Для контроля полноты необходима сверка с источником.

07 / DELIVERY ARCHITECTURE

Очередь сообщений: что берёт на себя брокер и что остаётся получателю

Брокер берёт на себя хранение недоставленного и разделяет отправителя и получателя во времени. Механика такая. Отправитель публикует сообщение, брокер записывает его в соответствии с настройками надёжности — при необходимости с репликацией на несколько узлов — и подтверждает приём. Получатель забирает сообщение, обрабатывает и посылает подтверждение обработки (acknowledgment, ack). Если подтверждения нет в отведённое время или соединение оборвалось, брокер может отдать сообщение снова: тому же получателю или другому. Поведение зависит от конкретного брокера, режима доставки, настроек и момента сбоя.

MESSAGE LIFECYCLE / ПУТЬ СООБЩЕНИЯ
Публикация и доставкаПодтверждениеПовторная доставка

Из этой механики следует семантика доставки. Если подтверждать до обработки, сбой в середине работы может потерять сообщение: это режим «не более одного раза» (at-most-once). Если подтверждать после обработки, сбой между завершением работы и подтверждением приводит к повторной доставке. Это режим «не менее одного раза» (at-least-once), и он часто используется в системах, где потеря недопустима. При этом фактическая сохранность сообщения зависит от надёжности публикации, репликации, подтверждений, настроек хранения и отказов инфраструктуры — одной схемы ack недостаточно.

AT-MOST-ONCE
Не более одного раза

Подтверждение до обработки. Если обработчик падает после ack, сообщение может быть потеряно.

AT-LEAST-ONCE
Не менее одного раза

Подтверждение после обработки. При сбое до ack сообщение может прийти повторно. Нужна идемпотентность.

Режим «ровно один раз» (exactly-once) не является универсальной гарантией для всей бизнес-системы. Отдельные брокеры обеспечивают транзакционность в пределах своих механизмов: например, Kafka позволяет атомарно записывать сообщения в несколько партиций и связывать их с фиксацией позиции потребителя в поддерживаемых сценариях. Но если обработка включает запись в чужую базу, вызов внешнего API, отгрузку товара или отправку письма, брокер не может сам атомарно объединить эти действия со своей транзакцией. На такой границе нужны идемпотентность, inbox/outbox, транзакция принимающей системы или механизм сверки. Поэтому корректнее говорить о конкретной гарантии на конкретной границе, а не обещать exactly-once для интеграции целиком.

BOUNDARY OF GUARANTEE

Exactly-once внутри механизма брокера не означает exactly-once для всей бизнес-операции. Гарантия заканчивается там, где начинается внешняя система, не участвующая в общей транзакции.

Очередь как буфер нагрузки

Что очередь делает с перегрузкой, показывает расчёт. Допустим, система приёма платежей банка в пиковые 10 минут публикует по 400 сообщений в секунду, а антифрод-сервис (проверка операций на мошенничество) обрабатывает 250 в секунду. Очередь растёт на 150 сообщений в секунду: за 600 секунд набегает 150 × 600 = 90 000 сообщений. При размере сообщения около 2 КБ это порядка 180 МБ полезной нагрузки, без учёта служебных данных, индексов, репликации и накладных расходов брокера.

Реальное время зависит от распределения потока, параллелизма, задержек обработчиков и политики очереди.

Для построения отчёта такая задержка может быть нормой. Для проверки платежа, без которой его нельзя провести, шесть минут означают отказ, и здесь нужен синхронный вызов. Очередь не ускоряет медленного получателя, она превращает отказ или перегрузку в задержку. Допустима ли такая задержка, решает процесс, а не инфраструктура. Поэтому главная метрика очереди — не её длина, а возраст самого старого сообщения и динамика отставания.

OPERATIONAL METRIC
Возраст самого старого сообщения

Длина очереди показывает количество накопленных сообщений. Возраст самого старого сообщения показывает, насколько давно система не успевает выполнять работу и как долго ждёт конкретное событие.

Порядок и параллелизм

Порядок и параллелизм конфликтуют. Один потребитель сохраняет последовательность обработки только при соответствующей реализации и отсутствии конкурирующей обработки, но ограничен собственной скоростью. Несколько потребителей ускоряют обработку, но сообщения могут завершаться в разном порядке. Выход состоит в разбиении по ключу: все события одного заказа направляют в одну очередь или партицию и обрабатывают последовательно в рамках этого ключа. Порядок тогда сохраняется в нужной области — внутри заказа, — а между разными заказами он не требуется. Выбор ключа — проектное решение, которое трудно менять после запуска: если взять идентификатор клиента, а потом понадобится порядок по счёту, данные придётся перераспределять или менять схему маршрутизации.

ОДИН ПОТРЕБИТЕЛЬ
Последовательная обработка

Проще сохранять порядок, но общая пропускная способность ограничена скоростью одного обработчика.

НЕСКОЛЬКО ПОТРЕБИТЕЛЕЙ
Параллельная обработка

Выше пропускная способность, но завершение сообщений может происходить не в порядке поступления.

Transactional Outbox: защита от двойной записи

Самая частая ошибка при подключении брокера — двойная запись. Сервис меняет данные в своей базе и публикует событие в брокер, а общей транзакции у этих систем нет. Если база зафиксировала изменение, а публикация не удалась, событие потеряно. Если событие опубликовано первым, а транзакция откатилась, получатели узнают о том, чего не было. Устоявшееся решение называется transactional outbox («исходящий ящик» в той же транзакции, что и данные):

TRANSACTION / BUSINESS DATA + OUTBOX
BEGIN;

UPDATE orders
SET status = 'paid'
WHERE id = 'A-482913';

INSERT INTO outbox (event_id, type, payload)
VALUES (
    gen_random_uuid(),
    'order.paid',
    '{"order_id": "A-482913"}'
);

COMMIT;

Отдельный процесс читает таблицу outbox, публикует события в брокер и отмечает отправленные. Публикация может случиться дважды, если процесс упал между отправкой и отметкой, поэтому потребитель всё равно остаётся идемпотентным. Это зеркало входящей таблицы приёмника: inbox защищает от повторов на входе, outbox защищает от потери события между фиксацией бизнес-изменения и публикацией.

TRANSACTIONAL OUTBOX / ГРАНИЦА АТОМАРНОСТИ
INBOX / входящие повторы OUTBOX / исходящая публикация

«Ядовитые» сообщения и DLQ

Отдельный класс отказов — «ядовитое» сообщение (poison message): данные, которые не удаётся обработать из-за дефекта, например дата в неожиданном формате. Без ограничений брокер отдаёт его снова и снова, и обработчик либо зацикливается, либо блокирует следующие сообщения в той же очереди. Стандартная защита состоит из лимита попыток и переноса исчерпавших его сообщений в отдельную очередь недоставленных (dead-letter queue, DLQ) с оповещением. DLQ не устраняет проблему автоматически. Повторить после исправления кода, поправить данные вручную или отбросить — выбор с деловыми последствиями, ведь отброшенное сообщение может оказаться платёжным поручением. Решение должен принимать человек, отвечающий за процесс, по регламенту, с сохранением аудита.

FAILURE HANDLING / DLQ
Сообщение → Повторные попытки → DLQ → Разбор человеком

DLQ — не автоматическая корзина для удаления ошибок. Для каждого типа сообщения нужен регламент повторной обработки, исправления или отказа с аудитом решения.

Цена всего перечисленного — новый компонент, который нужно эксплуатировать: кластер или управляемый сервис, диски с запасом под пики и срок хранения, обновления, резервное копирование и восстановление, мониторинг, дежурства. Количество узлов и схема отказоустойчивости зависят от брокера, требуемого уровня доступности и модели quorum. Брокер, который в компании никто не умеет диагностировать, становится новой точкой отказа, а не страховкой.

08 / FAILURE MATRIX

Что происходит при сбое: сравнение по сценариям

У каждого способа обмена есть собственная модель отказа. Сравнивать их полезно не по обещаниям «надёжности», а по конкретным ситуациям: кто обнаружит сбой, где останутся данные и каким способом система сможет восстановиться.

ОЧЕРЕДЬ

API

WEBHOOK

09 / EVENT CONTRACT

Конверт сообщения и версии схемы

Независимо от способа передачи сообщению нужен «конверт»: служебные поля, без которых невозможны дедупликация, упорядочивание и эволюция формата.

event_id
Идентификатор события

Ключ дедупликации: позволяет распознать повторную доставку того же события.

entity.version
Версия сущности

Помогает защититься от перестановок и применения устаревшего состояния.

occurred_at
Время события

Время события в источнике, которое отличается от времени получения.

schema_version
Версия формата

Позволяет получателю определить, по какой структуре читать сообщение.

Поле event_id служит ключом дедупликации, entity.version помогает защититься от перестановок и применения устаревшего состояния. Версия должна быть определена источником и отражать порядок изменений сущности. occurred_at — время события в источнике: оно отличается от времени получения, и при повторах или накоплении в очереди разрыв может достигать часов. Время само по себе не всегда надёжно определяет порядок событий. Поле schema_version указывает версию формата. Деньги передаются целым числом в минимальных единицах: 1 249 000 копеек — это 12 490,00 рубля. Дробные числа для денег порождают расхождения в копейках, которые потом ищут неделями.

Совместимость и эволюция формата

Правила совместимости просты. Добавление необязательного поля обычно не ломает получателей, которые игнорируют незнакомые поля (подход «терпимого читателя»), но только если это предусмотрено контрактом. Переименование и удаление поля, смена типа или смысла значения могут ломать интеграцию. В API и webhook изменение разводят по времени версией в адресе, заголовке или схеме события. В очереди, и особенно в журнале, старые сообщения продолжают жить в хранилище весь срок хранения, поэтому потребитель обязан читать все версии, которые ещё не вытеснены. Иначе перемотка истории упрётся в формат полугодовой давности. В крупных ландшафтах схемы сообщений ведут в реестре схем (schema registry), где совместимость новой версии проверяется автоматически.

10 / NETWORK & DATA SECURITY

Закрытый контур, сетевые зоны и персональные данные

Webhook требует входящего соединения к получателю. В сегментированной сети, где внутренняя зона может только устанавливать исходящие соединения, это невозможно без нарушения политики сегментации. Типовое решение состоит в следующем. Приёмник выносят в демилитаризованную зону (DMZ, промежуточный сегмент между внешней и внутренней сетью). Он принимает запрос, проверяет подпись и надёжно сохраняет событие — например, в брокере на границе. Внутренний потребитель сам подключается к брокеру, и входящих правил во внутреннюю зону не появляется. Тот же результат может дать опрос: внутренняя система сама ходит за данными в DMZ.

NETWORK SEGMENTATION / DMZ PATTERN
Путь передачи данных Граница сетевой зоны

Канал защищают шифрованием TLS, а между внутренними компонентами нередко используют взаимную проверку сертификатов (mTLS). Если система подпадает под требования ФСТЭК к защите информации, приёмник и брокер должны учитываться в границах защищаемой системы и её модели угроз; состав применимых мер зависит от категории системы, нормативных требований и архитектуры.

Две ловушки при работе с персональными данными

RISK 01 / DATA RETENTION
Брокер становится хранилищем ПДн

Журнал с длительным сроком хранения держит сообщения и после того, как цель обработки достигнута.

RISK 02 / LOGGING
Персональные данные попадают в логи

Тела webhook-запросов могут сохраняться в журналах прокси и диагностики без правил доступа, маскирования и хранения.

С персональными данными связаны две ловушки. Первая: брокер становится местом их хранения, а журнал с длительным сроком хранения держит сообщения и после того, как цель обработки достигнута. По требованиям 152-ФЗ обработка должна соответствовать целям и установленным основаниям, а хранение — ограничиваться необходимым сроком, если иное не предусмотрено законом. При сборе персональных данных граждан РФ действует требование использовать базы данных, находящиеся на территории России, в предусмотренных законом случаях и с установленными исключениями. Необходимо отдельно проверять применимость требования к конкретной схеме, включая передачу, копирование и трансграничную обработку. Практический вывод: в событие по возможности кладут идентификатор, а не весь набор персональных данных; срок хранения в журнале и DLQ задают осознанно, а расположение брокера проверяют с учётом применимых требований. Вторая ловушка: тела webhook-запросов попадают в журналы обратных прокси и диагностики, где персональные данные лежат без каких-либо правил доступа, маскирования и хранения.

Зависимость от внешних сервисов и инфраструктуры

Что касается зависимости от внешних сервисов, брокеры с открытым кодом могут разворачиваться на собственной инфраструктуре в изолированной сети без обращений наружу, если это обеспечено конфигурацией и эксплуатацией. Управляемые облачные очереди привязывают обмен к конкретной площадке, и при переносе меняется не только адрес: меняются клиентские библиотеки, лимиты, механизмы доступа, стоимость и нюансы семантики доставки. Если источник находится за пределами контура, а канал между сегментами нестабилен, схема с собственным приёмником, очередью на границе и сверкой предсказуемее прямого вызова — при условии, что её действительно можно эксплуатировать и контролировать.

11 / TOTAL COST OF OWNERSHIP

Из чего складывается стоимость и что считать нельзя

Стоимость обмена состоит из трёх слоёв. Первый слой — разработка и сопровождение: клиент API с таймаутами и повторами, приёмник webhook с подписью и входящей таблицей, публикатор и потребитель для брокера. Второй слой — инфраструктура: у API и опроса это нагрузка на источник и, у платных сервисов, тарификация запросов; у webhook это публичная точка входа с сертификатом, защитой и мониторингом; у брокера это кластер или управляемый сервис, диски, резервное копирование конфигурации и восстановление. Третий слой пропускают чаще всего. Это эксплуатация: дежурства, разбор DLQ, сверка, обучение людей, обновление и расследование инцидентов.

Расчёт на салфетке

Допустим, магазин получает 4 000 уведомлений об оплате в сутки, и в схеме «webhook без сверки» теряется 0,3 % из-за простоев приёмника дольше окна повторов и неудачных выкладок. Это 4 000 × 0,003 = 12 заказов в сутки. Каждый приходится находить и вносить вручную, около 10 минут: 12 × 10 = 120 минут, два часа в день. При 22 рабочих днях выходит около 44 часов в месяц.

Альтернатива — брокер, эксплуатация которого занимает половину рабочего времени инженера: 0,5 × 160 часов = 80 часов в месяц, не считая серверов. На таких объёмах брокер может оказаться дороже устранения потерь. Ежесуточная сверка через API, которая позволяет выявлять расхождения и при наличии данных автоматически восстанавливать пропущенные изменения, может быть дешевле их обоих. Картина меняется, когда меняются входные данные: потерянным событием оказывается платёжное поручение, а не уведомление, получателей становится несколько, пики на порядок превышают среднюю нагрузку или требуется гарантированное восстановление после длительного простоя.

Что считать нельзя

Считать нужно осторожно по двум причинам. Сравнивать брокер только с потерями нельзя: он ещё сглаживает пики, раздаёт событие нескольким потребителям и может уменьшить связность, и эти выгоды в расчёт потерь не попадают. Отчёт «потерь нет» без сверки не доказывает отсутствия потерь, он показывает только, что их никто не измеряет. Сверка нужна при любом выборе, поэтому её стоимость и эффект следует учитывать отдельно, а не считать преимуществом исключительно одного транспорта.

COST MODEL / IMPORTANT

Отсутствие зарегистрированных потерь не доказывает, что потерь нет. Без сверки система может просто не знать о пропущенных событиях.

12 / DECISION FRAMEWORK

Пять вопросов, которые определяют выбор

01

Нужен ли результат в том же действии, где пользователь ждёт?

Если да, нужен синхронный API. Асинхронные способы тогда обслуживают остальную часть процесса: уведомления, пересчёты, выгрузки.

02

Что должно произойти, если получатель недоступен, и сколько времени это допустимо?

Если подходит ответ «подождать и спросить снова», хватит API или опроса. Если данные должны дойти и после простоя, нужен webhook с входящей таблицей и сверкой либо очередь. Если простой может превысить окно повторов провайдера, webhook без собственного надёжного хранения и механизма восстановления ненадёжен.

03

Сколько получателей у события и появятся ли новые?

Для одного получателя подходит любой асинхронный способ. Когда один факт нужен нескольким системам, у webhook отправитель может вести независимое состояние доставки для каждого адресата, а журнал или маршрутизация в брокере позволяют организовать публикацию и независимое чтение. Выбор зависит от того, кто управляет подписчиками и насколько важна история.

04

Нужна ли возможность перечитать историю?

Если нужна, это журнал или хранение исходных событий в собственной базе. Классическая очередь после подтверждения истории обычно не хранит.

05

Кто управляет источником?

Внешний сервис отдаёт то, что умеет: API, webhook или оба. Ставить очередь на его стороне нельзя, но поставить её на границе своей сети можно. Для собственного источника доступны все варианты, и выбор определяют предыдущие вопросы.

Дополнительно учитываются объём с пиками, допустимая задержка, требования к порядку и квалификация команды: брокер без людей, умеющих его эксплуатировать, стоит дороже, чем кажется по смете.

Как работает выбор на конкретной ситуации

Как работает выбор на конкретной ситуации, видно в разговоре двух специалистов. Допустим, внешняя лаборатория передаёт результаты анализов в медицинскую информационную систему клиники (МИС), и аналитик предлагает прямой вызов API.

DESIGN REVIEW / LAB → CLINIC MIS

Результат готов, лаборатория шлёт запрос в МИС, МИС отвечает. Проще некуда.

 
ИНЖЕНЕР

МИС по ночам обновляется, пятнадцать минут недоступна. Что лаборатория делает в это время?

Повторяет.

Сколько раз и с какими паузами? И что с порядком: сначала уходит предварительный результат, через час окончательный. Если повторы перепутают очерёдность, в карте останется предварительный.

 
АНАЛИТИК

Тогда добавить версию к каждому результату.

 
ИНЖЕНЕР

И применять результат, только если версия выше сохранённой. Но версия должна отражать порядок изменений у лаборатории, а не просто время отправки. Что произойдёт, если окно повторов закончится раньше, чем МИС восстановится?

 
АНАЛИТИК

Тогда нужна сверка или возможность повторно выгрузить результаты.

Обработка на стороне получателя — идемпотентность, версионирование и контроль переходов состояния — снижает риск повторов и перестановок. Но она не заменяет механизм восстановления потерянных событий. После этого выбор транспорта определяется тем, кто хранит недоставленное, как долго, можно ли повторно получить историю и кто отвечает за сверку.

BLOCK 13 / TESTING & OBSERVABILITY VALIDATION

Испытания перед запуском и метрики эксплуатации

Схема обмена считается готовой не тогда, когда данные дошли в хороший день, а когда проверены плохие. Минимальный набор испытаний:

01
Недоступность получателя

Отключение получателя на время, равное худшему реальному простою, и проверка, что после подъёма не потеряно ни одно событие; дубли должны либо отсутствовать, либо не приводить к повторному бизнес-эффекту.

02
Повторная доставка

Отправка одного и того же события дважды, в том числе параллельно, и проверка, что эффект наступил один раз.

03
Нарушение порядка

Доставка двух событий об одной сущности в обратном порядке и проверка, что итоговое состояние верное.

04
Некорректные данные

Сообщение с заведомо некорректными данными и проверка, что оно уходит в DLQ или журнал ошибок, а поток не блокируется.

05
Отказ инфраструктуры

Отказ брокера или базы в момент публикации и проверка восстановления после повторного запуска.

06
Контроль полноты

Сверка источника и получателя на реальных данных за сутки с нулевым или объяснённым расхождением.

07
Неопределённый результат операции

Проверка, что повтор после таймаута не создаёт вторую операцию, даже если первая фактически завершилась.

В эксплуатации следят за разным в зависимости от способа:

API и опрос

  • Время ответа по перцентилям (95-й и 99-й, а не среднее).
  • Доля ошибок.
  • Число повторов.
  • Остаток лимита запросов.
  • Таймауты.
  • Количество открытых соединений и признаки исчерпания пула.

Webhook

  • Доля запросов, на которые приёмник ответил медленнее порога отправителя.
  • Число конфликтов вставки во входящую таблицу (то есть дублей).
  • Возраст самой старой необработанной записи.
  • Ошибки проверки подписи.
  • Результат сверки и состояние окна повторов у провайдера.

Очередь

  • Возраст самого старого сообщения.
  • Отставание потребителя (lag).
  • Число повторных доставок.
  • Размер DLQ.
  • Свободное место на дисках брокера.
  • Скорость поступления и обработки, а также прогноз времени разгребания backlog.
SIGNAL INTERPRETATION

Рост числа дублей без изменений в нагрузке может указывать на то, что где-то выросла задержка ответа или появились сбои между обработкой и подтверждением.

Рост возраста самого старого сообщения при нормальной длине очереди может указывать на зависший обработчик, проблемную партицию или ядовитое сообщение.

Эти косвенные признаки полезнее порогов на абсолютные значения, но их следует рассматривать вместе с логами, трассировками и состоянием конкретных потребителей.

BLOCK 14 / DECISION BOUNDARIES FINAL MODEL

Когда случай не укладывается в схему

Выбор способа сводится к ответу на вопрос, что должно произойти с данными, если получатель не ответит прямо сейчас.

 
01 / RETRY BY CLIENT

«Ничего, спросим снова»

Ведёт к API или опросу.

 
02 / SENDER RETRY + RECONCILIATION

«Отправитель подождёт и повторит, а потерянное найдём сверкой»

Ведёт к webhook с входящей таблицей, если гарантии провайдера и механизм восстановления подходят процессу.

 
03 / DURABLE STORAGE

«Данные должны пережить простой получателя, сохраняться независимо от него и допускать повторное чтение»

Ведёт к очереди или журналу.

Три признака особого случая

01 / GLOBAL ORDER

Требуется строгий порядок по всем событиям системы целиком, а не по ключу.

02 / UNTRUSTED NETWORK

Обмен идёт через ненадёжный или регулируемый канал между сетями, где ни одна из сторон не управляет всем путём.

03 / LOSS CRITICALITY

Потеря одного сообщения стоит дороже всей инфраструктуры вокруг.

Тогда пропускная способность упирается в последовательную обработку, и вопрос решается в проектировании данных, а не выбором транспорта. В этих случаях идемпотентность, контроль полноты и сверка перестают быть дополнением и становятся основой схемы.

FINAL / ARCHITECTURE PRINCIPLE

В конечном счёте надёжность интеграции определяется не тем, насколько модный транспорт выбран, а тем, что система делает при таймауте, повторе, перестановке, недоступности получателя и потере события.

API, webhook и брокер решают разные задачи. Хорошая архитектура выбирает каждый из них там, где его механика соответствует процессу, а границы гарантий проверены испытаниями.
