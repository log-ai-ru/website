ТРАНСФОРМАЦИЯ_ТРУДА // HUMAN_WORK_STRUCTURE

Когда в компании говорят об автоматизации, вопрос часто формулируют слишком просто:

«Что система теперь будет делать вместо сотрудника?»

Но для бизнеса гораздо важнее другой вопрос:

«Что сотрудник будет делать после того, как система заберёт рутинную часть работы?»

От ответа зависит, даст ли автоматизация реальный эффект.

[ ЛОВУШКА МНИМОЙ ОПТИМИЗАЦИИ ]

Если просто убрать человека из нескольких операций, но оставить ему ответственность за результат, десятки исключений и постоянную проверку системы, нагрузка может не уменьшиться вообще.

А при правильном перераспределении работы сотрудник перестаёт быть оператором механических действий и переключается на высокоуровневые задачи:

принимать решения;
работать с исключениями;
общаться с клиентами;
контролировать качество;
улучшать процесс.
// ПЕРЕПРОЕКТИРОВАНИЕ_ТРУДА //

Поэтому зрелая автоматизация — это не столько замена человека системой, сколько изменение структуры человеческой работы.

 

ФИЛЬТРАЦИЯ_НАГРУЗКИ // ACTION_VS_RESPONSIBILITY

Автоматизировать действие — не значит автоматизировать ответственность

Представим менеджера, который получает заявку клиента.

[ ДО АВТОМАТИЗАЦИИ // 8 ОПЕРАЦИЙ ]
• открывает письмо;
• читает текст;
• переносит данные в CRM;
• проверяет клиента;
• определяет тип заявки;
• создаёт задачу;
• назначает ответственного;
• отправляет подтверждение.
[ АВТОМАТИЗИРОВАННЫЙ ПОТОК ]
Заявка
↓
распознавание
↓
проверка данных
↓
определение типа
↓
создание записи
↓
назначение ответственного
↓
уведомление

После автоматизации сотруднику уже не нужно выполнять все восемь операций. Но это не означает, что его работа исчезает.

Ему могут остаться критически важные функции контроля:

нестандартные обращения;
спорные случаи;
проверка исключений;
принятие решений;
работа с клиентом;
контроль результата.

Именно на этом этапе особенно важно правильно распределить ответственность.

// СИНЕРГИЯ_ИНТЕЛЛЕКТА //

Система выполняет предсказуемое. Человек принимает решение там, где заранее нельзя надёжно определить правильный ответ.

 

АРХИТЕКТУРА_ПРОЦЕССА // EXCEPTION_MANAGEMENT_PIPELINE

Рутинная работа и работа с исключениями — это разные вещи

Одна из самых больших ошибок при автоматизации — считать весь процесс одинаковым.

На практике большинство процессов состоит из нескольких типов операций:

ПРОЦЕСС
│
├── повторяющиеся действия
│ ↓
│ автоматизация
│
├── действия по понятным правилам
│ ↓
│ автоматизация
│
├── нестандартные случаи
│ ↓
│ человек
│
├── решения с высокой ценой ошибки
│ ↓
│ человек + система
│
└── новые / неизвестные ситуации
↓
человек

Например, если система получает заказ с корректными данными, нет смысла заставлять сотрудника вручную подтверждать каждое поле.

Но автоматический сценарий должен остановиться или передать ситуацию человеку, если:

цена отличается от договора;
клиент просит нестандартные условия;
товар отсутствует;
данные противоречат друг другу;
система не уверена в результате.

Это называется управлением исключениями.

// ОБРАБОТКА_ИСКЛЮЧЕНИЙ //

Чем лучше продуман процесс автоматизации, тем важнее предусмотреть не только основной сценарий, но и обработку нестандартных ситуаций.

 

ГРАНИЦЫ_СИСТЕМЫ // AUTOMATION_LIMITS_PIPELINE

Почему нельзя автоматизировать всё

Технически сегодня можно автоматизировать гораздо больше процессов, чем раньше. Но возможность автоматизации не означает её целесообразность.

Есть операции, где человек выполняет работу не потому, что система пока «не умеет», а потому что человеческое решение действительно является частью процесса. Например:

переговоры;
оценка спорной ситуации;
согласование нестандартных условий;
принятие управленческого решения;
работа с конфликтом;
оценка контекста;
ответственность за исключение из правила.

Если процесс требует экспертной оценки, автоматизация не обязательно должна исключать участие человека. Она может подготовить информацию для его решения.

Например:

Вместо проверки двадцати документов сотрудник проверяет два.

// ОПТИМИЗАЦИЯ_КЛЮЧЕВОГО_МЕСТА //

Это уже серьёзный эффект.

 

РАЗГРУЗКА_ВНИМАНИЯ // DECISION_REDUCTION_FLOW

Хорошая автоматизация уменьшает количество решений, которые человеку приходится принимать вручную

Это один из самых полезных критериев.

Представим склад.

[ ДО АВТОМАТИЗАЦИИ // ПОЛНЫЙ РУЧНОЙ ВЫБОР ]
• какой заказ обрабатывать;
• какой товар взять;
• откуда его взять;

• что делать при расхождении.

↓
Товар соответствует данным
или

Система принимает стандартные решения, а человек занимается нестандартными.

// ЭФФЕКТИВНОСТЬ_ОПЕРАТОРА //

Это значительно эффективнее, чем заставлять человека подтверждать каждое действие системы.

 

КВАЛИФИКАЦИЯ // PROFESSIONAL_QUALIFICATION_SHIFT

Что происходит с квалифицированным сотрудником

Для квалифицированных специалистов последствия автоматизации особенно заметны.

Автоматизация может забрать у сотрудника часть механической работы, но одновременно повысить требования к его квалификации.

[ РАНЬШЕ // МЕХАНИЧЕСКИЙ ТРУД ]
• переносил данные;
• составлял отчёты;
• сверял таблицы;
• искал информацию;
• выполнял повторяющиеся операции.
[ СИСТЕМА ДЕЛАЕТ ЭТО САМА ]
[ ТЕПЕРЬ // ИНТЕЛЛЕКТУАЛЬНЫЙ КОНТРОЛЬ ]
• проверять качество результата;
• анализировать отклонения;
• работать с исключениями;
• понимать ограничения системы;
• принимать более сложные решения.

Получается парадокс:

Чем больше рутины забирает система, тем выше может становиться ценность оставшейся человеческой работы.

// ТРАНСФОРМАЦИЯ_ПРОЦЕССА //

Но только если компания действительно перестраивает процесс.

 

АНАЛИЗ_ЭФФЕКТИВНОСТИ // SYSTEM_OVERSEER_TRAP

Самая опасная ситуация — человек становится «надзирателем системы»

Иногда автоматизация выглядит впечатляюще:

«Мы убрали ручную работу».

Но на практике сотрудник просто начинает постоянно контролировать систему. Он смотрит:

всё ли прошло;
правильно ли распозналось;
не возникла ли ошибка;
не пропустила ли система документ;
правильно ли сформировался заказ;
не сломалась ли интеграция.

И получается ложная оптимизация:

[ БЫЛО ]
человек
↓
выполняет операцию
[ СТАЛО ]
система
↓
выполняет операцию
↓
человек постоянно проверяет систему

Экономического эффекта может оказаться гораздо меньше ожидаемого.

Поэтому при проектировании нужно считать не только первоначальное вытеснение рутины («Сколько операций автоматизировали?»), но и время, которое сотрудник продолжает тратить на контроль.

// ИСТИННЫЙ_БАЛАНС_ВРЕМЕНИ //

«Сколько человеческого времени осталось на контроль этих операций?»

 

ФИЛЬТРАЦИЯ_АННУЛИРОВАНИЯ // AUTOMATED_CONTROL_FLOW

Контроль тоже можно автоматизировать

Это следующий уровень зрелости.

Необязательно заставлять сотрудника проверять каждую операцию. Можно построить систему так, чтобы она сама выделяла подозрительные случаи.

[ БАЗОВАЯ СХЕМА ]
10 000 операций
↓
автоматические проверки
↓
9 850 — норма
↓
сотрудник проверяет 150
[ СХЕМА С ПРИОРИТЕТИЗАЦИЕЙ ]
150 отклонений
↓
приоритетизация
↓
30 критичных
↓
сотрудник

Человек больше не контролирует всё подряд.

В этом примере из 10 000 операций 150 требуют дополнительного внимания, а после приоритизации 30 из них признаются критичными. Остальные 120 отклонений также должны иметь определённый маршрут обработки: автоматическое исправление, отдельную очередь или проверку сотрудником. Приоритизация не означает, что некритичные отклонения можно игнорировать.

Это уже не просто автоматизация операций.

// МАСШТАБИРОВАНИЕ_КОНТРОЛЯ //

Это автоматизация контроля.

 

СУВЕРЕНИТЕТ_ЧЕЛОВЕКА // HUMAN_RESERVED_ZONES

Где должен оставаться человек

Универсального правила нет, но есть несколько зон, где человеческое участие особенно важно.

[ ВЫСОКАЯ ЦЕНА ОШИБКИ ]

Если ошибка может привести к финансовым, юридическим или операционным последствиям, решение следует оставить за человеком.

[ НЕСТАНДАРТНЫЕ СИТУАЦИИ ]

Если случай выходит за рамки заданных алгоритмов, система должна уметь изолировать его и передать оператору.

[ ПЕРЕГОВОРЫ И ВЗАИМОДЕЙСТВИЕ ]

Клиенты формулируют проблемы живым языком, контекст и тон которого часто не заложены в стандартный сценарий.

[ УПРАВЛЕНИЕ КОНФЛИКТАМИ ]

Когда сталкиваются интересы разных сторон или департаментов, баланс компромисса нельзя свести к математической формуле.

[ ИЗМЕНЕНИЕ САМОГО ПРОЦЕССА ]

Система способна выполнять действующие правила автоматически. Решение об изменении бизнес-правил должно оставаться за уполномоченным сотрудником.

 

ИСКЛЮЧЕНИЕ_РУТИНЫ // ROUTINE_REMOVAL_CONTOUR

А где человека действительно лучше убрать

Есть и обратная сторона.

Некоторые операции вообще не имеют смысла оставлять сотруднику:

перенос одинаковых данных между системами;
механическое создание записей;
повторная проверка одного и того же поля;
отправка стандартного уведомления;
расчёт по однозначной формуле;
синхронизация справочников;
регулярное формирование типового отчёта.

Если человек каждый день делает одно и то же по понятному алгоритму, это хороший кандидат на автоматизацию.

Причём не только из-за экономии времени.

Ручные операции создают дополнительный риск ошибок:

// ФАКТОР_ЧЕЛОВЕЧЕСКОЙ_ОШИБКИ //

чем больше однотипных действий выполняется вручную, тем выше вероятность накопления ошибок на всём объёме операций.

 

МОДЕЛИРОВАНИЕ // EXCEPTION_OPERATOR_MODEL

Человек может стать оператором исключений

При таком подходе сотрудник работает только с нестандартными случаями, а типовые операции выполняет система.

[ УСТАРЕВШИЙ ПОДХОД ]

«Сотрудник обрабатывает все операции».

[ ЗРЕЛАЯ ОПТИМИЗАЦИЯ ]

«Система обрабатывает стандартные операции, сотрудник обрабатывает отклонения».

Например:

1000 операций
│
├── 930 стандартных
│ ↓
│ система
│
└── 70 исключений
↓
сотрудник

Но здесь важно правильно определить границу:

[ ИЗБЫТОК СИСТЕМЫ ]

Если системе разрешили слишком много, она начнёт принимать неправильные решения.

[ ИЗБЫТОК РУЧНОГО ТРУДА ]

Если человеку оставили слишком много, автоматизация практически не дала результата.

// АРХИТЕКТУРА_ПРОЦЕССА //

Поэтому граница между автоматическим сценарием и человеческим решением — один из ключевых элементов архитектуры процесса.

 

РАЗДЕЛЕНИЕ_КОНТРОЛЯ // OPERATION_VS_ACCOUNTABILITY

Что происходит с ответственностью

Есть принципиальная разница между двумя уровнями:

[ МЕХАНИЧЕСКИЙ СЛОЙ ]

выполнение операции

[ СТРАТЕГИЧЕСКИЙ СЛОЙ ]

ответственность за результат

Система может автоматически выполнять рутинные операции:

создать документ;
провести заказ;
рассчитать сумму;
отправить уведомление;
изменить статус.

Но это не означает, что система становится владельцем процесса.

Человек или подразделение всё равно должны понимать:

по каким правилам работает автоматизация;
какие ограничения у неё есть;
когда нужно вмешаться;
что делать при ошибке;
кто принимает окончательное решение.
// КРИТИЧНОСТЬ_КОНТУРА //

Особенно это важно в финансовых, производственных, кадровых и других критичных процессах.

 

РЕГЛАМЕНТАЦИЯ // RUNTIME_REGULATIONS_MATRIX

После автоматизации сотруднику нужна новая инструкция

Недостаточно просто сказать: «Теперь это делает система».

Нужно определить новый процесс.

[ РАНЬШЕ ]

Сотрудник сам создаёт документ.

[ ПОСЛЕ АВТОМАТИЗАЦИИ ]

Система создаёт документ автоматически.

Но что дальше? Контур регламентов должен закрывать вопросы:

кто проверяет исключения;
кто получает уведомление об ошибке;
сколько времени даётся на реакцию;
кто исправляет исходные данные;
кто может отменить автоматическое действие;
что происходит при недоступности системы;
где фиксируется ручное решение.
// АНАЛИЗ_РИСКОВ_НЕОПРЕДЕЛЕННОСТИ //

Если этих правил нет, автоматизация создаёт неопределённость.

 

ОРГАНИЗАЦИЯ_ТРУДА // RESOURCE_REALLOCATION_MATRIX

Что делать с высвободившимся временем

Это уже вопрос не разработки, а управления.

[ БЫЛО // РУТИНА ]

6 часов в день на рутинные операции.

[ СТАЛО // АВТОМАТИЗАЦИЯ ]

1 час контроля. Освободилось 5 часов.

Это расчётный пример при условии, что указанные трудозатраты измерены за сопоставимый рабочий день. Реальный эффект необходимо оценивать с учётом времени на контроль, обработку исключений и сопровождение автоматизации.

Но это не значит автоматически, что компания получила экономию. Нужно решить, на что будут направлены эти пять часов.

Например, перенаправить интеллектуальный ресурс:

на обслуживание большего количества клиентов;
на продажи;
на контроль качества;
на работу с проблемными случаями;
на анализ данных;
на развитие процессов.

Если ничего не изменить, сотрудник просто найдёт себе другую ручную работу.

// ОРГСТРУКТУРНЫЙ_БАЛАНС //

Поэтому автоматизация должна сопровождаться изменением организации труда, а не только изменением программного обеспечения.

 

МАСШТАБИРОВАНИЕ // STAFF_THROUGHPUT_EFFICIENCY

Иногда после автоматизации сотрудников становится не меньше

И это нормально.

Представим компанию, которая автоматизировала обработку заказов. Вместо сокращения сотрудников компания может увеличить количество обрабатываемых заказов тем же составом команды — если пропускная способность остальных этапов процесса позволяет выдержать такой рост.

Экономический эффект может возникнуть не за счёт сокращения штата, а за счёт:

роста пропускной способности;
увеличение выручки;
снижение количества ошибок;
отсутствие необходимости пропорционально расширять штат.

Поэтому оценивать автоматизацию только вопросом:

«Сколько людей мы сократим?» — неправильно.

Гораздо полезнее спрашивать:

// ЭФФЕКТ_МАСШТАБА //

«Какой объём работы компания сможет выполнять тем же количеством людей?»

 

УПРАВЛЕНИЕ // EXECUTIVE_DATA_DRIVEN_SHIFT

Автоматизация меняет не только сотрудников, но и требования к руководителям

Когда процесс становится цифровым, руководитель получает больше возможностей видеть его фактическое состояние.

Например, система начинает поставлять объективную аналитику:

сколько операций выполнено;
где возникают задержки;
какие сотрудники получают больше исключений;
какие типы ошибок встречаются чаще;
на каком этапе возникает узкое место.

Это позволяет перевести контур на рельсы управления на основе данных (data-driven management).

И здесь автоматизация перестаёт быть просто способом «сэкономить руки».

// ЦИФРОВОЙ_АРБИТРАЖ //

Она становится инструментом управления бизнесом.

 

АНАЛИЗ_ИЗБЫТОЧНОСТИ // AUTOMATION_COMPLEXITY_OVERHEAD

Почему иногда после автоматизации работа становится сложнее

Это тоже необходимо учитывать.

Если автоматизированный процесс плохо спроектирован, сотрудник может получить избыточную нагрузку:

больше интерфейсов;
больше уведомлений;
новые исключения;
необходимость разбираться с ошибками интеграций;
дополнительные проверки;
ответственность за действия системы.

Получается критическая ситуация:

«Раньше я делал это вручную, а теперь должен контролировать пять автоматических систем».

Это не зрелая автоматизация.

// АРХИТЕКТУРНОЕ_ОЗДОРОВЛЕНИЕ //

Если после автоматизации работа становится сложнее, нужно найти причину и проверить, можно ли устранить её изменением архитектуры системы.

 

ФОКУС_МЕТРИК // VALUE_DRIVEN_METRICS

Лучший показатель — не количество автоматизированных операций

Можно автоматизировать 90% действий и почти ничего не выиграть.

А можно автоматизировать 30% операций и получить огромный эффект.

Например, система автоматизировала только несколько наиболее трудоёмких этапов:

100 операций
↓
автоматизировано 30
↓
но именно эти 30 занимали
70% рабочего времени

Это условный пример: соотношение доли автоматизированных операций и высвобождаемого времени зависит от фактической трудоёмкости каждого этапа.

Поэтому правильный вопрос звучит так:

«Какую часть человеческого времени и внимания мы освобождаем?»

А не поверхностное:

// ФОКУС_НА_ЦЕННОСТИ //

«Какой процент операций автоматизирован?»

 

ФОКУС_ЧЕЛОВЕКА // HUMAN_RESIDUAL_FUNCTIONS

Что должно остаться человеку

После хорошей автоматизации сотруднику обычно остаётся работа четырёх типов.

01. РЕШЕНИЯ

Когда требуется экспертная оценка контекста, взвешивание рисков и выбор между альтернативными вариантами.

02. ИСКЛЮЧЕНИЯ

Когда стандартный линейный сценарий не подходит или аномальные данные прерывают автоматический поток.

03. ОТВЕТСТВЕННОСТЬ

Когда юридический, кадровый или финансовый регламент требует, чтобы человек подтвердил легитимность и правильность результата.

04. РАЗВИТИЕ

Когда нужно улучшить существующий процесс, изменить устаревшие бизнес-правила или спроектировать новый способ работы.

Всё остальное необходимо критически оценивать:

// КРИТЕРИЙ_ЦЕЛЕСООБРАЗНОСТИ //

действительно ли человек должен это делать?

 

АРХИТЕКТУРА_КОНТУРА // MATURE_MIND_MACHINE_CONT_LOOP

Зрелая модель выглядит так

Задача автоматизации — не убрать человека из этой схемы.

// ОПТИМАЛЬНЫЙ_ПЕРИМЕТР //

Задача — исключить участие человека в операциях, где оно не требуется.

 

ИТОГ_МЕНЕДЖМЕНТА // VALUE_DRIVEN_HUMAN_LABOR_FINALE

Итог

Хорошая автоматизация не отвечает на вопрос: «Как заменить сотрудника?»

Она отвечает на другой:

«Какие действия должен выполнять человек, а какие надёжнее, быстрее и дешевле передать системе?»

Система должна брать на себя повторяемое, формализуемое и предсказуемое.

Человек должен участвовать там, где необходимы профессиональное суждение, оценка контекста, принятие решений и ответственность за результат:

контекст;
ответственность;
оценка ситуации;
работа с исключениями;
коммуникация;
принятие решений;
развитие процесса.

Именно поэтому автоматизация не обязательно означает сокращение людей. Она означает изменение ценности человеческого труда.

Сотрудник перестаёт быть оператором последовательности механических действий и становится человеком, который работает там, где автоматический сценарий заканчивается.

А зрелость автоматизации определяется не тем, сколько людей удалось убрать из процесса.

// ФИНАЛ_КОНЦЕПЦИИ //

Она определяется тем, насколько правильно компания разделила работу между системой и человеком.
