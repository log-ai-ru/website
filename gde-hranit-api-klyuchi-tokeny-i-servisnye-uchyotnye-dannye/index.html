Условный кейс: как обычно начинается проблема

Компания внедряет обмен между CRM и внешней платформой.

Для запуска нужен API-ключ. Его кладут в конфиг, чтобы «быстрее проверить». Потом конфиг попадает в репозиторий. Репозиторий — в архив для подрядчика. Подрядчик через полгода больше не работает с проектом, но архив остаётся.

Через 11 месяцев ключ всплывает в неожиданном месте.

СОСТОЯНИЕ_СИСТЕМЫ // COMPROMISED_KEY_STATE
Жизненный цикл
ключ всё ещё действует
Уровень доступа
через него можно читать и изменять данные
Прослеживаемость
никто точно не помнит, где ещё он был скопирован
Аудит и логи
в логах нет понятной картины, кто и когда им пользовался

Дальше начинается не «безопасность», а пожар: отзыв ключа, срочный выпуск нового, проверка всех интеграций, разбор, не было ли обращений извне, объяснения бизнесу.

Почти всегда цепочка одна и та же:

секрет положили туда, где удобно → удобное место оказалось неуправляемым → секрет пережил контекст, в котором его создавали.

 

Что является секретом

Секрет — это конфиденциальное значение, владение которым позволяет получить доступ к системе, данным или операциям в пределах предоставленных полномочий.

АРХИТЕКТУРА_БЕЗОПАСНОСТИ // SECURE_STORAGE_MODELS

Где секреты должны храниться

Рабочая модель строится вокруг одного принципа:

Для каждого секрета должна быть определена система управления, в которой контролируются его актуальное значение, права доступа и жизненный цикл. Передача секрета приложению должна быть организована так, чтобы ограничивать круг получателей, срок действия и возможность повторного использования с учётом возможностей конкретной архитектуры.

КРИТЕРИИ_ХРАНЕНИЯ // STORAGE_LAYERS
1. Secret Manager / Vault

Отдельный контур, который:

  • › хранит секреты с применением предусмотренных механизмов шифрования;
  • › предоставляет доступ на основе политик и идентификации получателя;
  • › ведёт аудит обращений и операций управления;
  • › поддерживает ротацию и отзыв секретов в пределах возможностей конкретной интеграции;
  • › интегрируется с CI/CD и средой выполнения приложений.

Это не «удобный сейф». Это система управления секретами.

Само по себе хранение пароля в объекте Kubernetes Secret не гарантирует достаточной защиты. Необходимо отдельно настроить шифрование данных при хранении, ограничить доступ с помощью RBAC и обеспечить безопасную передачу секретов приложениям.

2. Переменные окружения — способ передачи секрета, но не самостоятельное защищённое хранилище.

Переменные окружения могут использоваться для передачи секрета процессу при запуске, если это допускает модель угроз и особенности платформы. При этом необходимо учитывать возможность доступа к окружению процесса, попадания значений в диагностические дампы и утечки через инструменты отладки.

Не следует хранить файл .env с рабочими секретами в репозитории, общедоступных каталогах или домашних папках без надлежащей защиты.

3. Динамические секреты

Для баз данных и части внутренних сервисов лучше не использовать пароли, которые живут месяцами.

Схема:
сервис запрашивает доступ
получает временные учётные данные
работает
по истечении TTL данные автоматически становятся недействительными

При корректной настройке динамических секретов окно их использования после утечки можно ограничить.

После истечения TTL учётные данные должны перестать приниматься соответствующим сервисом. При этом необходимо учитывать уже открытые соединения, выданные токены и возможность повторного использования полномочий через активную сессию.

Рядом с приложением работает вспомогательный компонент — sidecar или агент, — который получает секреты и передаёт их приложению через контролируемый локальный канал либо предоставляет их в виде файлов в соответствии с моделью безопасности.
ВИЗУАЛИЗАЦИЯ // МАРШРУТЫ ПОСТАВКИ СЕКРЕТОВ В RUNTIME
ЗАПРЕТЫ_РАЗМЕЩЕНИЯ // SECURITY_LOGGING_CONSTRAINTS

Секреты нельзя хранить в открытом виде в постоянных файлах конфигурации, репозиториях и неконтролируемых каталогах. Они также не должны попадать в логи приложения, тексты ошибок, трассировки и артефакты CI/CD.

Если приложению необходим секрет в файле, нужно ограничить доступ к нему, защитить хранение и определить срок существования файла. По возможности используют временные файлы в защищённой среде или передачу секрета без записи на постоянный диск.

Ротация

Секрет, который долго не меняют и не пересматривают, может со временем стать источником повышенного риска.

УПРАВЛЕНИЕ_РИСКАМИ // ROTATION_TRIGGERS
[ АНАЛИЗ // ПРИЧИНЫ РОТАЦИИ ]

Причины ротации прозаические:

  • › увольнения
  • › смена подрядчиков
  • › «временный» доступ, который забыли
  • › старые интеграции, которые уже не нужны, но ключ жив
[ РЕГЛАМЕНТ // МИНИМУМ ДИСЦИПЛИНЫ ]
  • › у каждого секрета есть владелец
  • › есть срок жизни или дата пересмотра
  • › процедура смены описана и выполняется
  • › после завершения ротации старый секрет отозван или выведен из обращения на стороне системы, которая его проверяет; прекращение его действия подтверждено проверкой
ВИЗУАЛИЗАЦИЯ // ОКНО ПАРАЛЛЕЛЬНОЙ РАБОТЫ КЛЮЧЕЙ (GRACE PERIOD)

Для критичных интеграций может предусматриваться короткое окно параллельной работы двух ключей: новый ключ уже используется потребителями, а старый временно продолжает приниматься системой. После перехода всех потребителей старый ключ отключают и проверяют, что он больше не принимается.

КРИТЕРИИ_БЕЗОПАСНОСТИ // EXCUSES_VS_REALITY

«Репозиторий приватный»

Приватность не отменяет копирование, историю и расширение списка доступа.

«Команда небольшая, все свои»

Утечки могут происходить и без злого умысла: при отладке, создании архивов, смене подрядчика или использовании забытого токена. Небольшой размер команды не устраняет эти риски.

«Потом сделаем правильно»

Со временем секретов становится больше, они оказываются в разных системах и копиях, а наведение порядка требует значительно больше усилий, чем внедрение управляемого хранения с самого начала.

«Нам пока рано»

Именно на раннем этапе секреты чаще всего кладут в код «временно». Временное становится постоянным.
