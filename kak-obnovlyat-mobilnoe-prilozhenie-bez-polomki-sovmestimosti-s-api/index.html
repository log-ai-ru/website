Как обновлять мобильное приложение без поломки совместимости с API

 

 

 

Почему серверный релиз может сломать старое приложение

В 10:05 во вторник серверная часть приложения получила плановый релиз. Регистратура давно просила отличать приём, который перенёс врач, от приёма, который отменил пациент. В список статусов записи добавили четвёртое значение: «перенесено клиникой». Тесты прошли. Метрики сервера после выкладки выглядели безупречно: ошибок категории 5xx (сбоев на стороне сервера) не было, время ответа не изменилось, запросы на список записей возвращали код 200.

В 10:40 в контакт-центр начали поступать звонки: в приложении пропали записи на приём. К 11:15 обращений набралось около сорока, и все они были от владельцев iPhone. К полудню выяснилось, что дело в версиях. Приложение до 4.2 включительно показывало пустой экран «У вас нет предстоящих приёмов», а 4.3 и новее работали нормально.

В старых сборках статус записи описан перечислением (enum, закрытым списком допустимых значений). Декодер получил четвёртое значение и выбросил исключение. Из-за этого не удалось прочитать весь список, а не только одну запись. Обработчик ошибки превращал любое исключение в пустой массив, и экран честно рисовал пустое состояние.

Откат серверного релиза занял двенадцать минут. Но записи с новым статусом к тому моменту уже были в базе, их оказалось 63, и после отката кода они по-прежнему отдавались старым клиентам. Пришлось отдельным скриптом возвращать им прежний статус и обзванивать пациентов, у которых приём был назначен на завтра.

В этом примере формальная схема API описывала status как строковое поле без закрытого ограничения enum. Поэтому добавление нового строкового значения не нарушало структурную схему. Однако оно нарушало фактическое ожидание старых клиентов, которые считали перечень значений закрытым. Если бы в опубликованной OpenAPI-схеме присутствовал явный enum с тремя допустимыми значениями, такое расширение уже было бы нарушением описанного контракта.

Ключевой принцип

Именно такие негласные допущения определяют цену любого изменения на сервере, пока в обращении есть версии приложения, которые разработчик не контролирует.

Почему код 200 не означает, что всё работает

Поломка совместимости может происходить непосредственно на устройстве. Сервер видит успешный запрос и успешно сформированный ответ. Решение «эти данные непонятны» принимает клиентский код, и сообщить об этом серверу некому, если такая телеметрия не предусмотрена заранее.

HTTP-уровень сообщает об успешной доставке ответа, но не гарантирует, что клиент смог правильно интерпретировать его содержимое.

Из этого следуют три важных вывода.

01 / OBSERVABILITY

Серверные метрики не видят часть клиентских ошибок

Допустим, версии до 4.2 составляют треть активной iOS-аудитории, а iOS даёт половину всех активных устройств. Тогда затронуто около 1/3 × 1/2 ≈ 17% аудитории. При этом сервер может не зарегистрировать ни одной ошибки 5xx и продолжать отдавать корректные с точки зрения HTTP ответы.

02 / ERROR HANDLING

Превращать сбой декодирования в пустое состояние опаснее, чем показывать явную ошибку

Падение приложения попадает в аналитику крашей. Пустой экран может не вызвать ни одного технического события и обнаружиться только через службу поддержки. Причём пользователь описывает проблему словами «записи пропали», а не «декодер не разобрал статус». Пустое состояние на месте ошибки становится самым вежливым способом сообщить пользователю неправду.

03 / API CONTRACT

Формальная схема не описывает все ожидания потребителей

Серверная команда может считать строковое поле расширяемым, а клиент — использовать его как закрытое перечисление. В документации всё выглядит совместимым, но фактическое поведение приложения зависит от незафиксированных предположений.

Поэтому контракт нужно проверять не только по структуре сообщений, но и по поведению реальных клиентов.

Сборка, API и контракт: три версии, которые принимают за одну

Версия сборки (например, 4.2.1 для пользователя и отдельный номер build для магазина) описывает конкретный бинарный файл на устройстве. Версия API — имя набора операций и их семантики, например /v1/ или /v2/. Версия схемы — точная форма сообщений в определённый момент: какие поля присутствуют, какие обязательны, какие типы и значения допустимы.

Одна версия API может соответствовать множеству сборок приложения и десяткам состояний схемы.

В пределах одной версии API схема может меняться десятки раз, а одной версии API могут соответствовать десятки сборок приложения.

Первая типовая ошибка — связывать версию приложения и версию API один к одному: вышло приложение 5.0, значит, нужен /v3/. Тогда каждый релиз клиента порождает новую копию серверной логики, и через год сервер поддерживает десяток почти одинаковых API.

Вторая ошибка обратная: объявить v1 стабильной и менять её без учёта существующих потребителей. Формально версия остаётся одной, фактически существуют десятки состояний контракта. Без сведений о сборке клиента, времени выпуска и используемых возможностях становится трудно установить, какой именно вариант видел конкретный пользователь.

Терминология совместимости в литературе используется не всегда одинаково. Для дальнейшего обсуждения закрепим следующие определения:

BACKWARD COMPATIBILITY

Обратная совместимость сервера

Новый сервер корректно обслуживает запросы старых клиентов и сохраняет ожидаемое ими поведение.

FORWARD COMPATIBILITY

Прямая совместимость клиента

Способность уже выпущенного клиента безопасно работать с расширениями и данными, которые появились на сервере после выпуска клиента.

LOCAL DATA COMPATIBILITY

Совместимость форматов локальных данных между версиями клиента

Способность новой сборки прочитать и корректно обработать данные, которые сохранила старая: локальную базу, кеш, черновики и очередь неотправленных запросов.

Это рабочие определения для статьи, а не утверждение, что во всей инженерной литературе используется исключительно такая классификация.

В вебе страница и сервер часто обновляются почти синхронно: пользователь получает свежий клиент при загрузке. В мобильной системе число активных копий приложения примерно соответствует числу устройств, на которых оно установлено и используется. Каждая копия обновляется по собственному расписанию. Разработчик не может гарантировать ни скорость обновления, ни установку новой версии, ни удаление уже выпущенного бинарного файла.

Это больше похоже на протокол между независимо версионируемыми участниками, чем на пару «приложение и его бэкенд».

Откуда берётся хвост старых версий и сколько он стоит

Хвост старых сборок существует по нескольким независимым причинам:

01
Автообновление выключено или разрешено только по Wi-Fi, а на устройстве не хватает памяти для новой сборки.
02
Новая версия требует более свежей операционной системы, а устройство больше не получает её обновления.
03
Приложение открывают редко: страховое или транспортное приложение могут запускать только в момент события, поэтому фактическая версия определяется датой последнего обновления, а не датой релиза.
04
Корпоративные устройства обновляются через MDM (Mobile Device Management, систему централизованного управления мобильными устройствами) по окнам обслуживания.
05
Приложение распространяется через несколько каналов. В российских реалиях это могут быть RuStore, AppGallery и другие магазины, а на Android — ещё и прямая установка APK. Версии и сроки публикации в каналах различаются.

Поэтапный выпуск растягивает сосуществование сборок ещё сильнее.

Поэтапное распространение на iOS

У Apple механизм называется phased release. Обновление автоматически предлагается случайной выборке пользователей с включёнными автоматическими обновлениями на совместимых устройствах. Расписание составляет 1%, 2%, 5%, 10%, 20%, 50% и 100% по дням с первого по седьмой. Пользователь может установить доступное обновление вручную в любой момент, не дожидаясь своей очереди.

Поэтапное распространение на Android

В Google Play разработчик сам задаёт процент staged rollout. Если обнаружена проблема, раскатку можно остановить. Но пользователи, которые уже получили обновление, останутся на этой версии. Остановка не возвращает им предыдущую сборку. Для исправления потребуется выпустить новую версию приложения.

RELEASE RISK / CLIENT ROLLBACK

Ни один из механизмов не обеспечивает массового отката клиента. Поэтому серверная архитектура должна допускать откат собственной логики без потери уже записанных данных. Именно этому мешают необратимые изменения, как в истории с 63 записями.

При другом горизонте амортизации и другой маржинальности точка сравнения изменится.

INTERPRETATION

Устойчивый вывод здесь не в конкретном проценте, а в рычаге управления. Доля ушедших зависит не только от инженерии, но и от того, были ли предупреждения, насколько заблаговременно они появились и может ли пользователь вообще обновиться на своём устройстве.

Предупреждение в приложении, push и сообщение по другим каналам за месяц могут заметно изменить эту долю. Насколько сильно — нужно проверять по фактическим результатам коммуникации, а не принимать как гарантированный эффект.

Есть и скрытые статьи расходов. Матрица тестирования растёт с каждой поддерживаемой версией. Ошибки в старых ветках исправляют сложнее, потому что первоначальные допущения контракта уже забыты. Старые сборки могут использовать устаревшие настройки TLS, прежние сценарии аутентификации и давно не обновлявшиеся криптографические библиотеки.

Совместимость как часть безопасности

Отдельно стоит оценивать certificate pinning — закрепление открытого ключа или сертификата. Само отсутствие pinning не означает, что приложение небезопасно: стандартная проверка цепочки доверия TLS является нормальной моделью защиты. Но если закрепление используется, старые клиенты могут потерять соединение после смены ключей или сертификатов. Структура запросов и ответов почти не меняется, но старый клиент получает состояние «требуется подтверждение» и не знает, что с ним делать.

Изменение бизнес-процесса требует отдельного решения: старые версии направляют по прежнему пути, пока он допустим с точки зрения безопасности и правил платёжной системы, либо сервер прекращает операцию и возвращает понятную машинно-читаемую ошибку. Простое добавление поля не решает проблему отсутствующего пользовательского сценария.

Клиент, который не падает от чужих данных

Базовый принцип называется tolerant reader — терпимый читатель. Клиент разбирает нужные ему данные, допускает безопасные расширения и не считает неизвестное значение автоматической причиной отказа от всего ответа.

Это не означает, что любое неизвестное значение можно бездумно игнорировать. Правильное поведение зависит от того, влияет ли оно на безопасность, деньги, медицинское состояние или возможность выполнить операцию.

Успешный разбор данных не означает, что значение безопасно интерпретировано или что операция разрешена.

Здесь важно различать три уровня: успешный разбор данных, безопасную интерпретацию полученного значения и допустимость бизнес-операции. Неизвестное значение может быть успешно разобрано и показано пользователю, но этого недостаточно, чтобы разрешить действие. Например, неизвестный статус платежа нельзя автоматически трактовать как успешный или неуспешный. Решение о проведении операции в любом случае принимает сервер на основании актуальных правил.

Для перечисления на Swift можно использовать явное неизвестное состояние:

SWIFT / DECODABLE ENUM
enum AppointmentStatus: Decodable {
    case scheduled
    case completed
    case cancelled
    case unknown(String)

    init(from decoder: Decoder) throws {
        let raw = try decoder.singleValueContainer().decode(String.self)

        switch raw {
        case "scheduled":
            self = .scheduled
        case "completed":
            self = .completed
        case "cancelled":
            self = .cancelled
        default:
            self = .unknown(raw)
        }
    }
}

Стандартное перечисление без специальной обработки неизвестного строкового значения может завершить декодирование ошибкой. Вариант unknown превращает его в обычное состояние, которое интерфейс обязан уметь показать.

Например, для неизвестного статуса можно показать запись с нейтральной подписью «Статус уточняется» и предложением обновить приложение. Но нельзя автоматически разрешать или запрещать действия только потому, что клиент не распознал значение. Для критичных операций решение принимает сервер, а клиент показывает безопасное состояние.

Для массивов действует второе правило: отказ одного элемента не должен автоматически уничтожать весь список. Если формат и бизнес-логика позволяют, элементы можно разбирать независимо. Но частичный разбор допустим только тогда, когда приложение способно достоверно определить, какие данные получены, какие пропущены и не создаёт ли неполный результат ложного представления о состоянии системы.

Например, в независимом каталоге товаров допустимо показать распознанные позиции и отдельно сообщить, что часть данных не обработана. В медицинском расписании или финансовой истории пропуск записи может исказить представление пользователя о полноте данных. Здесь нужно либо показать явно неполный результат с признаком ошибки, либо считать весь ответ недостоверным и запросить данные повторно.

Для таких сценариев полезно предусматривать метаданные полноты: общее количество элементов, признаки следующей страницы, состояние загрузки и, при необходимости, ошибки отдельных элементов. Нельзя подменять частично обработанный массив полноценным пустым или полным списком. Нечитаемые элементы нельзя молча удалять, если это приводит к потере значимых данных.

DATA INTEGRITY

В медицинском приложении скрытая запись о приёме хуже записи с пометкой «не удалось определить статус». В финансовом приложении аналогичный подход должен учитывать возможность показать сумму и состояние операции без разрешения на повторное выполнение.

Особенности Gson и Kotlin

Бывает и обратная проблема, на Android. Библиотека Gson при десериализации может создавать объект без вызова конструктора и инициализаторов, используя механизм Unsafe или аналогичный способ. Если поле в JSON отсутствует, значения, заданные в конструкторе, могут не примениться: поле останется со стандартным значением JVM, например null или 0.

ANDROID / KOTLIN RISK

Ошибка может проявиться не в момент разбора JSON, а позже, при первом обращении к полю. Причина — отсутствующее поле в ответе — и следствие — сбой на экране оплаты — оказываются в разных частях кода.

Такое поведение не является неизбежным для любой Kotlin-модели: результат зависит от способа создания объекта, конструктора, адаптера и конфигурации библиотеки. В документации Gson отдельно описан сценарий с использованием JDK Unsafe и возможность отключить его через GsonBuilder.disableJdkUnsafe(), чтобы обнаруживать проблемы раньше. Для новых Android-проектов также стоит оценивать библиотеки, которые лучше интегрируются с Kotlin-моделями и позволяют явно задавать правила обработки отсутствующих и неизвестных полей.

Если контракт описан в Protocol Buffers, добавление поля с новым номером обычно безопасно на уровне бинарного формата. Старый клиент не знает этого поля, но proto3 сохраняет неизвестные поля при разборе и повторной бинарной сериализации. Они могут потеряться, если сообщение преобразуют в JSON или создают новое сообщение вручную, копируя только известные поля.

Преобразование в JSON или ручное копирование известных полей может привести к потере неизвестных данных.

Для перечислений необходимо различать открытые и закрытые enum. В proto3 обычные enum имеют открытую семантику: неизвестное числовое значение сохраняется в поле, хотя способ его представления в сгенерированном коде зависит от языка и реализации. Например, в C++ и Go оно может быть представлено непосредственно числом, а в Java для неизвестного значения используется специальное представление UNRECOGNIZED, при этом исходное число можно получить отдельным методом.

В proto2 enum ведут себя как закрытые: неизвестные значения обрабатываются иначе и могут попадать в набор неизвестных полей. В Editions поведение определяется настройкой типа перечисления. Для Editions 2023, 2024 и 2026 по умолчанию используется открытая семантика, но её можно изменить. Кроме того, существуют особенности и отклонения реализаций отдельных языков, поэтому совместимость необходимо проверять на конкретном стеке, а не только по названию синтаксиса.

  string starts_at = 3;

Серверные адаптеры и стабильные категории

Часть работы можно переложить на сервер. Вместо одного расширяемого значения можно отдавать грубую стабильную категорию и дополнительные детали:

JSON / APPOINTMENT RESPONSE
{
  "id": "a-77120",
  "status": "rescheduled_by_clinic",
  "statusGroup": "scheduled",
  "statusLabel": "Перенесено клиникой, подтвердите новое время",
  "startsAt": "2027-02-03T10:30:00+03:00",
  "actions": ["confirm", "cancel"]
}

Новые клиенты знают status и используют его для подробной логики. Старые могут читать statusGroup только в том случае, если это поле уже присутствовало в контракте выпущенных сборок. Если его там не было, серверный адаптер должен продолжать отдавать старым клиентам прежнее значение status, которое они умеют обрабатывать, например scheduled. Нельзя рассчитывать, что добавление нового поля научит уже выпущенное приложение его использовать.

statusLabel можно выводить как готовую строку без собственной интерпретации, если такой способ отображения предусмотрен старой сборкой. Список actions сообщает, какие операции разрешены. Клиент отображает только те действия, которые умеет безопасно выполнять, а сервер всё равно повторно проверяет допустимость операции при её выполнении. Передача списка действий не заменяет авторизацию и серверные проверки.

ADAPTER PRINCIPLE

Сервер может адаптировать представление данных для старой сборки, но не может добавить ей отсутствующую функциональность.

У этого подхода есть предел: он защищает отображение данных, но не реализует новые сценарии. Если для нового статуса требуется отдельный экран подтверждения, которого в старой сборке нет, старую ветку сценария придётся сохранить, пока это допустимо, либо прекратить соответствующую операцию для старого клиента.

GraphQL не отменяет проблему совместимости

GraphQL частично смещает проблему: клиент сам перечисляет нужные ему поля, поэтому добавление необязательного поля на сервере обычно не мешает существующим запросам. Но удаление поля, изменение его семантики и расширение enum остаются источниками несовместимости. Сгенерированные клиентские модели также могут представлять enum как закрытый тип. Поэтому нужно проверять не только схему GraphQL, но и поведение конкретного генератора и клиентской библиотеки при неизвестных значениях.

Схемы версионирования: путь, заголовок, дата, возможности

Версионирование нужно, чтобы неизбежные несовместимые изменения происходили под контролем. Основных подходов четыре.

API versioning / Four approaches
01. Версия в пути PATH VERSIONING
/v2/orders

Версия указана в адресе ресурса. Видна в логах, балансировщике и мониторинге; проста в отладке.

Цена: версионируется набор адресов, возникает риск дублирования логики.
02. Версия в заголовке HEADER VERSIONING
Accept: application/vnd.api.v2+json

Адреса ресурсов остаются стабильными, версия может различаться по ресурсам.

Цена: сложнее кеширование, диагностика и настройка прокси.
03. Версия по дате DATE VERSIONING
2026-11-27

Версия закрепляется за клиентом. Сервер может преобразовывать сообщения к соответствующему контракту.

Цена: нужна инфраструктура адаптеров и политика жизненного цикла версий.
04. Согласование возможностей CAPABILITY NEGOTIATION
payment-sheet-v2, order-actions

Изменения вводятся постепенно, без обязательного создания новых мажорных версий API.

Цена: нужны дисциплина именования и управление устареванием возможностей.

Версионирование по дате публично применялось в некоторых платёжных API. Для мобильного приложения закрепление можно делать за сборкой: при первом обращении клиент объявляет версию контракта, которую ожидает. Сервер сохраняет её в контексте клиента или использует при каждом запросе.

Независимо от выбранной схемы, запросы должны передавать сведения о клиенте: платформу, версию приложения и номер сборки. Например:

HTTP / CLIENT IDENTIFICATION
App-Platform: ios
App-Version: 4.3.1
App-Build: 4312

Это пользовательские заголовки приложения, а не стандартизованные HTTP-поля. При их проектировании стоит учитывать RFC 6648, который не рекомендует использовать префикс X- для новых нестандартных параметров. Уже существующие заголовки с таким префиксом не требуется автоматически переименовывать.

Эти сведения нужны для аналитики, диагностики, сегментации трафика и точечных ограничений. Сравнивать версии как обычные строки нельзя: строковое сравнение может поставить 4.10.0 раньше 4.9.0. Для технических решений лучше использовать монотонный номер сборки либо корректный разбор компонентов версии. Номер сборки должен быть однозначно сопоставим с платформой и каналом распространения: одинаковые номера на iOS и Android не обязательно обозначают один и тот же контракт.

Эти заголовки не являются доказательством подлинности клиента. Их можно подделать. Они подходят для наблюдаемости и выбора совместимого представления, но не для авторизации, проверки прав или обхода серверной защиты.

Версия приложения служит косвенным признаком возможностей, и этот признак неточен. Функцию могли перенести в исправление старой ветки, выпустить на iOS и Android в разных версиях или включить в бинарный файл, но выключить серверным флагом.

Поэтому надёжнее, когда клиент сообщает набор возможностей, например:

HTTP / CAPABILITY NEGOTIATION
App-Capabilities: payment-sheet-v2,order-actions

Сервер может адаптировать ответ под заявленный набор. При этом идентификаторы возможностей должны иметь стабильную семантику, а их удаление и переименование — управляемый жизненный цикл. Сервер не должен доверять таким заголовкам при принятии решений о безопасности: заявленная возможность означает только то, что клиент обещает её поддерживать.

Но это справедливо только при ограниченном количестве вариантов семантики. Если поколения клиентов требуют разных бизнес-процессов, сочетаний условий и специальных правил обработки, сложность может расти значительно быстрее. В таком случае проблема уже не в количестве преобразований данных, а в поддержке нескольких вариантов поведения системы.

Особенно важно не смешивать преобразование контракта с поддержкой разных состояний бизнес-процесса. Адаптер может переименовать поле или преобразовать значение, но не способен выполнить за старый клиент отсутствующий шаг подтверждения, восстановить утраченное состояние или безопасно разрешить конфликт операций.

Есть и границы возможностей адаптеров: преобразование данных не заменяет отсутствующий экран, подтверждение или защищённый сценарий. В таких случаях нужен отдельный шлюз совместимости: старая ветка процесса, если она допустима, либо отказ с понятным сообщением.

Как переименовать поле, которое читают десятки тысяч устройств

Безопасный порядок необратимого изменения называется expand and contract, или parallel change: сначала добавляют новое рядом со старым, потом переводят потребителей, и только после этого убирают прежнее.

Разберём задачу с деньгами. Нужно перейти от дробного числа в рублях (price: 1490.00) к целому числу копеек (priceMinor: 149000).

Expand & contract / Migration sequence
PHASE 01 / EXPAND
Добавить новое поле
Старое и новое представления существуют параллельно.
↓
PHASE 02 / MIGRATE
Перевести клиентов
Новые сборки используют новый формат, старые продолжают работать.
↓
PHASE 03 / OBSERVE
Проверить фактическое использование
Измерить чтение и запись старого поля.
↓
PHASE 04 / CONTRACT
Удалить старое поле
После выполнения критериев миграции и утверждения срока отключения.

Расширение

Сервер начинает отдавать priceMinor рядом с прежним price. В запросах он временно принимает оба поля. В контракте заранее фиксируют валюту, минимальную расчётную единицу, допустимый диапазон и правила округления. Источником истины на сервере назначается одна каноническая денежная величина, например целое количество минимальных единиц валюты. Старое поле становится представлением этой величины, а не независимым хранилищем.

Если пришли оба поля и значения расходятся после нормализации в одну денежную величину, сервер не должен молча выбирать произвольное значение: запрос фиксируется как конфликт, а поведение определяется заранее установленным правилом. Для денежных операций безопаснее отклонить неоднозначный ввод, чем исполнить его по неверной сумме.

Выпуск клиентов

Новые сборки читают и отправляют priceMinor. Старые продолжают работать с price. Если возможно, новые клиенты некоторое время умеют читать оба формата, чтобы пережить переходные состояния. Клиенту не следует независимо изменять оба представления: он отправляет каноническое поле либо одно согласованное значение, а сервер выполняет преобразование.

Согласование записи

Если старые и новые клиенты могут изменять одну сущность параллельно, сервер определяет порядок применения изменений. Для этого используют транзакции, проверку версии записи или optimistic locking. При необходимости добавляют идемпотентность операций, чтобы повторная отправка запроса не приводила к повторному изменению суммы. Двойная запись в два независимых поля не должна становиться источником истины: оба представления формируются из одной канонической величины в рамках согласованной транзакции.

Наблюдение

По метрикам версий и фактическому использованию полей видно, сколько запросов и устройств ещё используют старый формат. Одной статистики установленных сборок недостаточно: клиент может быть установлен, но неактивен, а запросы могут поступать из отложенных очередей. Нужно отдельно учитывать чтение, запись и фактическое использование старого поля.

Сужение

Когда использование старого поля упало ниже заранее установленного порога, предупреждения отправлены, а альтернативные сценарии проверены, сервер перестаёт отдавать price. Шаг выполняют по утверждённому плану с датой, ответственным и возможностью остановить процесс до необратимого удаления.

При этом priceMinor не означает, что число всегда нужно интерпретировать как копейки. Единица зависит от валюты. Например, у валют с нулём или тремя дробными разрядами правила будут другими. Контракт должен однозначно определять, как число соотносится с валютой, и не полагаться на предположение, что все суммы имеют два знака после запятой.

Сужение необратимо для клиентов, которые остались на старой схеме. Поэтому перед ним нужны тесты на реальных старых сборках, проверка журналов использования, тестовая среда и заранее подготовленное сообщение для пользователей.

Тот же порядок применим к базе данных: добавить колонку, начать согласованную двойную запись, заполнить исторические данные, переключить чтение, прекратить запись в старое поле и только затем удалить его. При этом двойная запись должна выполняться в одной транзакции или через механизм, обеспечивающий надёжную доставку изменений, например transactional outbox. Иначе сбой между двумя операциями может оставить поля в разных состояниях.

Database migration / Safe sequence
01 / EXPAND
Добавить новую колонку
02 / WRITE
Начать согласованную двойную запись
03 / BACKFILL
Заполнить исторические данные
04 / SWITCH
Переключить чтение на новую колонку
05 / CONTRACT
Прекратить запись в старое поле и удалить его
Переход между этапами выполняется после проверки согласованности данных. Удаление старой структуры — последний, а не первый шаг миграции.

Перед удалением проверяют резервное копирование и восстановление, но одной резервной копии недостаточно. После появления новых записей восстановление старой схемы может потребовать обратной миграции данных или движения вперёд исправленным кодом.

Для локальной базы мобильного приложения действует тот же принцип, но с дополнительным ограничением: сервер не управляет моментом обновления устройства и не может гарантировать, что пользователь последовательно установит все промежуточные сборки.

Если пользователь обновился с версии 4.0 сразу до 4.9, приложение должно либо выполнить всю цепочку миграций от старой схемы к новой, либо иметь проверенный механизм прямого перехода. Нельзя рассчитывать, что миграция с 4.8 на 4.9 автоматически исправит состояние базы, которая осталась на схеме 4.0.

Обратная миграция также не гарантирована. Новая версия могла добавить поля, изменить типы или сохранить данные, которые старая схема не способна представить. Если требуется возможность отката бинарной версии, это нужно проектировать отдельно: например, временно сохранять старые поля, использовать совместимые форматы и не удалять данные, необходимые предыдущей сборке.

На практике безопаснее часто оказывается не полноценный downgrade, а выпуск исправленной новой версии приложения, которая умеет работать с уже обновлённой локальной схемой.

ROLLBACK ≠ DATA ROLLBACK

Именно поэтому откат приложения не всегда означает откат системы. Код можно вернуть за минуты, а данные, уже записанные в новом формате, могут потребовать отдельной процедуры.

Принудительное обновление: контур, который закладывают в первую версию

Механизм минимально поддерживаемой версии состоит из трёх частей: серверной конфигурации, клиентской проверки и заранее определённого поведения для старых сборок.

Клиент при запуске запрашивает небольшой конфигурационный ответ:

VERSION POLICY / JSON
{
  "minSupportedBuild": 4100,
  "recommendedBuild": 4300,
  "message": "Эта версия приложения больше не поддерживается. Обновите приложение."
}

Клиент сравнивает номер своей сборки с порогами. Ниже минимума показывает блокирующий экран, ниже рекомендуемой — мягкое предложение с ограничением частоты показа. Для актуальной сборки приложение работает как обычно.

Следуют несколько важных ограничений.

01 / LEGACY CLIENTS
Механизм нельзя добавить задним числом

В сборках, где нет запроса конфигурации и кода проверки, нет и возможности показать блокирующий экран. Для них остаётся серверный отказ на устаревших операциях и общий текст ошибки. Поэтому механизм желательно заложить в первую версию приложения.

02 / CONFIGURATION SERVICE
Конфигурация живёт отдельно от основного API

Ей нужны собственный адрес, минимум зависимостей и возможность кеширования на CDN. Если конфигурационный сервис недоступен, приложение не должно автоматически блокировать всех пользователей. Для проверки обновления обычно выбирают поведение fail-open: использовать последнюю корректную кешированную конфигурацию или временно продолжить работу. Срок действия кеша и последствия отсутствия конфигурации нужно определить заранее.

03 / SECURITY BOUNDARY
Fail-open не отменяет серверную защиту

Это решение относится только к проверке версии. Оно не означает, что сервер должен разрешать небезопасные операции. Критичные ограничения безопасности продолжают действовать независимо от доступности конфигурационного сервиса.

Ошибка в одном числе блокирует всех. Допустим, при подготовке релиза в minSupportedBuild вместо 4300 записали 43000. Все устройства оказываются ниже порога, а блокирующий экран ведёт в магазин, где обновления нет. Нужна серверная валидация: минимальная сборка не может превышать реально опубликованную сборку, доступную для соответствующей платформы и канала. Дополнительно нужны подтверждение изменения порога, аудит и возможность быстрого возврата прежнего значения.

CRITICAL CONFIGURATION RISK

Неверное значение минимальной сборки может одновременно заблокировать все устройства. Поэтому изменение порога должно проходить валидацию, подтверждение и аудит, а прежнее значение должно быть доступно для быстрого восстановления.

Порог поднимают после достаточной доступности обновления. При поэтапном выпуске, когда новая сборка доступна только части пользователей, повышение минимума до неё может оставить остальных перед блокировкой, из которой нет выхода. Нужно дождаться завершения раскатки в каждом канале или отдельно убедиться, что все пользователи, на которых распространяется новое ограничение, действительно могут получить обновление.

Здесь важно учитывать не только номер сборки. Доступность зависит от платформы, канала распространения, страны, версии операционной системы, модели устройства и настроек публикации. Одна и та же сборка может быть доступна пользователям одного канала и недоступна другим. Поэтому конфигурация минимальной версии должна поддерживать отдельные пороги для соответствующих групп, а повышение порога — проходить проверку фактической доступности обновления.

Устройство может не получить обновления никогда. Если новая сборка требует более свежей операционной системы, а устройство на ней не работает, кнопка «Обновить» ведёт в магазин, где для этого устройства обновления нет. Это не означает, что компания обязана поддерживать все старые устройства бессрочно. Но прекращение обслуживания должно быть осознанным решением: нужен запасной путь, например веб-версия, альтернативный канал обслуживания или обращение в поддержку. Если такой путь невозможен, пользователь должен заранее узнать о прекращении поддержки и его последствиях.

Клиенту нельзя доверять. Заголовок версии подделывается. Блокирующий экран служит механизмом пользовательского опыта, а не границей безопасности. Если старая версия содержит уязвимость, сервер отключает соответствующую операцию независимо от того, показал ли клиент предупреждение.

Какой HTTP-статус использовать

Для отказа в обслуживании по версии иногда предлагают использовать HTTP 426 Upgrade Required. Но по RFC 9110 этот статус относится к переходу на другой сетевой протокол: сервер должен указать допустимый протокол в заголовке Upgrade. Это не универсальный код «обновите мобильное приложение».

HTTP 410 Gone означает, что целевой ресурс больше недоступен и это состояние, вероятно, постоянно. Его можно использовать, если действительно удалён конкретный ресурс или endpoint, но не следует назначать его универсальным статусом для устаревшей сборки.

Для мобильного API практичнее определить собственный машинно-читаемый код ошибки в теле ответа, например APP_VERSION_UNSUPPORTED, и документировать его поведение. HTTP-статус выбирают по семантике конкретного отказа. Клиент должен отличать эту ошибку от временных сбоев и не повторять запрос бесконечно. В ответе полезно передавать минимальную поддерживаемую сборку, ссылку на обновление для соответствующего канала и понятное сообщение.

Контракты, которых нет в описании API

Список того, что клиент и сервер разделяют, шире списка эндпоинтов. Часть этих элементов живёт дольше, чем отдельные версии API.

Hidden contracts / Mobile ecosystem
Push-уведомления

Содержимое сообщения может получить любая установленная версия. Для уведомлений, которые должна показывать сама операционная система, нужно передавать стандартные поля заголовка и текста в формате, поддерживаемом соответствующей платформой. Но это не распространяется на все push-сообщения: data-only уведомления требуют обработки приложением, а фоновые ограничения iOS и Android влияют на то, когда такая обработка вообще возможна. Маршрут внутри приложения из служебных данных старый клиент может не понять. В таком случае он должен безопасно открыть главный экран или нейтральную страницу, а не завершиться с ошибкой. Полезно версионировать payload и сохранять совместимый fallback-маршрут.

Ссылки

Ссылки из писем и SMS, разосланных полгода назад, всё ещё открывают приложение. Старые маршруты должны разрешаться, а неизвестные направлять на безопасную страницу, например на веб-версию. Ссылку нужно считать долговременным публичным контрактом.

Локальная база и кеш

Пользователи пропускают версии: с 4.0 сразу переходят на 4.9. Миграции проверяют не только переход с предыдущей версии, но и путь от самой старой поддерживаемой схемы к текущей. Если миграции последовательные, необходимо проверять всю цепочку и корректно обрабатывать прерывание миграции на середине. Нужно также определить поведение при нехватке места, повреждении базы и повторном запуске после прерванной миграции. Новая схема не должна приводить к потере данных, которые ещё нужны старому коду, если откат бинарной версии входит в поддерживаемый сценарий.

Очередь неотправленных запросов и черновики

Запрос мог быть сформирован по старому контракту, а отправлен новой сборкой после обновления приложения. Идемпотентные ключи помогают серверу распознавать повторы, но не делают старый формат совместимым с новым. Для очереди нужны версия формата операции, миграция локально сохранённых данных, преобразование старых запросов перед отправкой и политика обработки операций, которые больше нельзя выполнить. Для финансовых операций особенно важно не повторять действие только потому, что клиент не получил ответ. Нужно учитывать неопределённый результат: сервер мог выполнить операцию, но ответ потерялся. Перед повтором клиент должен проверить её состояние по идентификатору операции или использовать предусмотренный сервером механизм идемпотентности.

Адрес сервера, домен и сертификат

Допустим, серверную часть переносят на другую инфраструктуру, в том числе в рамках выполнения требований о локализации персональных данных. Новый адрес не доходит до старых сборок. Старый домен может потребоваться сохранять до завершения поддержки клиентов, которые его используют. Перенаправление помогает не всегда: HTTP-клиент может изменить метод или не передать заголовок авторизации при переходе на другой хост, а клиенты с закреплённым ключом или сертификатом могут отказаться от соединения с новой инфраструктурой. Условия перенаправления, доверия к сертификатам и pinning нужно проверять по фактической конфигурации каждой поддерживаемой версии.

Сессия и токены

Формат токена и сценарий продления сессии тоже являются контрактом. Допустим, новая версия API требует повторного входа: активные сессии на старых клиентах превращаются в экран авторизации. Если вход выполняется по SMS, каждый такой переход стоит денег. При 20 000 повторных входов и условной стоимости 3 ₽ за сообщение это 60 тыс. ₽ разовых расходов, не считая потерянных сессий и обращений в поддержку.

Локализация данных и инфраструктурный контракт

В контексте 152-ФЗ важно различать домен API, местоположение серверов и фактическое использование баз данных. По состоянию на 25 ноября 2026 года часть 5 статьи 18 закона устанавливает, что при сборе персональных данных граждан РФ, в том числе через интернет, перечисленные операции — запись, систематизация, накопление, хранение, уточнение и извлечение — с использованием баз данных за пределами территории России не допускаются, кроме предусмотренных законом исключений.

Эта редакция введена Федеральным законом № 23-ФЗ от 28 февраля 2025 года и действует с 1 июля 2025 года. В тексте части 5 статьи 18 прямо указаны исключения, связанные с пунктами 2, 3, 4 и 8 части 1 статьи 6. Поэтому норму нельзя трактовать как безусловный запрет любых операций с иностранными базами во всех ситуациях.

При этом нужно отдельно анализировать последующую трансграничную передачу персональных данных: она регулируется статьёй 12 закона и не тождественна локализации баз данных при сборе. Требования зависят от конкретного процесса обработки, оснований, ролей участников и применимых исключений. Само размещение API на российском домене не доказывает соблюдение требований локализации. Необходимо проверять, где фактически выполняются операции с данными, в каких базах они хранятся и какие внешние сервисы получают доступ к персональной информации. Оценка соответствия конкретной архитектуры требует анализа всей цепочки обработки, а не только расположения основной базы данных.

ARCHITECTURE CHECKPOINT

Домен, сервер и база данных — разные элементы инфраструктуры. Проверка локализации требует проследить фактический маршрут персональных данных и операции над ними, включая внешние сервисы и последующую передачу.

Проверка до выпуска и наблюдение после

До выпуска сервера работают несколько уровней проверки, и ни один не заменяет остальные.

Сравнение схем в CI

Инструменты сравнения OpenAPI ловят удаление полей, изменение типов и другие структурные нарушения описанного контракта. Они не видят смену смысла, новые шаги процесса и все допущения клиента о значениях перечислений. Сравнивать нужно не только актуальную схему с предыдущей, но и совместимость с наборами схем поддерживаемых клиентов. При этом проверка должна учитывать не только структурную совместимость, но и направление изменения: безопасное для нового клиента изменение не обязательно безопасно для старого.

Контрактные тесты потребителя

Consumer-driven contracts, один из распространённых инструментов — Pact. Клиент публикует, какие взаимодействия ему нужны, а сервер проверяет, что изменения не нарушают эти ожидания. Такие тесты полезны, когда покрывают реальные сценарии и версии потребителей, но не заменяют тестирование пользовательского поведения и бизнес-процессов. Важно сохранять контракты для реально поддерживаемых сборок, а не только для текущей разработки.

Воспроизведение трафика

Из продуктивного трафика выбирают запросы по версиям клиентов, удаляют или маскируют персональные данные и воспроизводят их на кандидате в релиз. Сравнивают не только структуру ответов, но и значимые значения, коды ошибок, порядок элементов и поведение при граничных данных. Персональные данные нельзя переносить в тестовый контур без предусмотренных правовых и технических оснований. Простого удаления имён недостаточно: нужно учитывать возможность повторной идентификации по совокупности полей.

Матрица реальных сборок

Автоматические сценарии для самой старой поддерживаемой сборки, нескольких промежуточных и текущей версии на каждой платформе работают против тестового контура до релиза. Выбор сборок основывается на реальной доле пользователей и рисках, а не только на календаре выпусков. Отдельно проверяют сборки с известными особенностями декодеров, сетевого стека и локальных миграций.

Снятие версии с поддержки — не событие, а процесс с последовательностью действий, сроками и ответственными.

Политика до выхода первой версии

Фиксируется правило: например, поддерживаются сборки не старше определённого срока или несколько последних поколений. Политика известна разработке, поддержке и партнёрам. В ней отдельно учитываются устройства, которые больше не могут получить обновление.

Доля активных устройств и запросов по каждой версии известна в любой день. Учитываются не только установки, но и реальная активность, используемые операции и каналы распространения. Для удаления отдельного поля дополнительно измеряется фактическое использование именно этого поля.

03

Уведомление в приложении, push и сообщения по доступным каналам отправляют за один-три месяца до отключения. Текст объясняет, что именно перестанет работать, когда и что нужно сделать.

05
Блокирующий экран

Его показывают тем, кому действительно есть куда обновиться. Для устройств без доступной новой версии заранее определяют альтернативный путь обслуживания или порядок прекращения поддержки.

06
Отключение

Устаревшие операции перестают обслуживаться по заранее объявленному плану. Сервер возвращает документированную машинно-читаемую ошибку и подходящий HTTP-статус. Код 410 применяют к действительно удалённому ресурсу, а не автоматически ко всем старым сборкам. Клиент должен уметь показать понятное сообщение, если его версия поддерживает такую обработку.

07
Удаление кода

Адаптеры, эталонные примеры и тесты для снятой версии убирают после проверки, что запросов по ней больше нет или их остаточное количество соответствует утверждённому плану. Удаление сопровождают мониторингом, чтобы обнаружить неожиданных потребителей.

Заголовки Deprecation и Sunset

Заголовок Deprecation стандартизован RFC 9745, опубликованным в марте 2025 года. Он сообщает дату, с которой ресурс объявлен устаревшим. Значение передаётся как Structured Field Date, например:

HTTP RESPONSE HEADERS
Deprecation: @1798761600
Sunset: Wed, 01 Sep 2027 00:00:00 GMT
Link: <https://api.example.com/docs/migration-v2>; rel="deprecation"; type="text/html"

Значение @1798761600 соответствует 1 января 2027 года, 00:00 UTC. Sunset указывает ожидаемую дату, после которой ресурс перестанет отвечать. Она не должна быть раньше даты Deprecation. Сам заголовок не меняет поведение ресурса и не отключает его: это уведомление потребителя о жизненном цикле API.

Для мобильных приложений такие заголовки полезны прежде всего как дополнительный сигнал для диагностики и интеграций. Старые клиенты могут их не читать, поэтому предупреждение пользователя должно работать через собственный механизм конфигурации и интерфейс.

Для массового мобильного приложения этот приём почти не годится: он непосредственно бьёт по пользователям. Здесь его обычно заменяют предупреждением внутри приложения и постепенным прекращением поддержки.

Где общие правила меняются

В приложении под управлением MDM версии на устройствах контролирует администратор. Хвост можно сократить централизованной политикой, но скорость и возможность установки зависят от платформы, режима управления, прав администратора и настроек устройства. На корпоративных Android-устройствах, например, автоматические обновления зависят от условий эксплуатации, а администратор может управлять политиками распространения приложений. Это не универсальная гарантия мгновенной установки на любое устройство.

В приложениях, рассчитанных на длительную автономную работу — выездные бригады, склады без связи, удалённые объекты, — эффективный хвост определяется не только релизами, но и интервалом синхронизации. Сервер должен принять данные, созданные по контракту, который действовал в начале автономного периода, и корректно обработать их после обновления приложения или изменения бизнес-правил.

Для таких систем важны версия формата локальной операции, время её создания, идентификатор идемпотентности и правила разрешения конфликтов. Если операция больше не может быть выполнена автоматически, пользователь должен получить понятный статус, а не потерять её при синхронизации.

При этом прекращение поддержки приложения и отключение конкретной уязвимой операции — не обязательно одно и то же. Иногда безопаснее временно отключить один сценарий на сервере, сохранив остальную функциональность для старого клиента. В других случаях продолжение работы старой сборки создаёт неприемлемый риск, и требуется полное ограничение доступа.

SUPPORT POLICY / TWO LEVELS
Ограничение отдельной операции

Отключается конкретный сценарий, создающий риск. Остальная функциональность старого клиента может продолжать работать.

Полное ограничение доступа

Применяется, когда продолжение работы старой сборки создаёт неприемлемый риск.

Срок жизни поля в API определяет не команда разработки, а самый медленный из потребителей, который это поле ещё использует. Поэтому решение удалить элемент контракта относится не только к коду, но и к конкретным людям, устройствам и интеграциям.

Перед удалением нужно уметь назвать три факта: сколько активных потребителей ещё используют этот элемент, какие операции от него зависят и когда их владельцев предупредили. Если этих сведений нет, удаление превращается в эксперимент на пользователях.
