Как организовать поиск по большому каталогу товаров

 

 

 

 

LOG-AI / SEARCH ENGINEERING TECHNICAL ARCHITECTURE

Как организовать поиск по большому каталогу товаров: архитектура, релевантность, фильтрация и индексация

 

Поиск в интернет-магазине — это не просто поле, в которое покупатель вводит название товара. Это механизм, который должен преобразовать неточный пользовательский запрос в конкретный результат среди тысяч или миллионов товарных позиций.

На небольшом сайте с несколькими сотнями товаров проблемы поиска могут оставаться незаметными. Покупатель вводит название модели, получает несколько результатов и быстро находит нужную позицию.

Совершенно другая ситуация возникает в каталоге с 300 000 товаров, несколькими поставщиками, разными производителями, десятками характеристик и постоянно меняющимися остатками.

01 / SEARCH FAILURE SCENARIO
USER QUERY
«ноутбук леново 16 гб 1 тб»
Требуется конкретная конфигурация товара.
SEARCH OUTPUT
Нерелевантные позиции
8 ГБ памяти, другие производители и аксессуары.
RESULT
Нужный товар существует, но оказывается на четвёртой странице.

Покупатель вводит «ноутбук леново 16 гб 1 тб», а система показывает модели с 8 ГБ памяти, устройства другого производителя и аксессуары. В каталоге есть нужный товар, но он оказывается на четвёртой странице. Другой пользователь пишет «беспроводные наушники самсунг», а поиск возвращает пустой результат, потому что в карточках производитель записан как Samsung, а механизм сопоставления не учитывает варианты написания.

С точки зрения базы данных товары существуют. С точки зрения покупателя — их нет.

Именно здесь обнаруживается разница между обычным поиском по тексту и полноценной поисковой системой.

Главная задача поиска — не найти совпадающие слова, а правильно определить, какие товары соответствуют запросу, какие из них доступны для покупки и в каком порядке их следует показать.

Для этого недостаточно одного полнотекстового индекса. Необходимо согласовать обработку запросов, структуру каталога, словари, фильтры, алгоритмы ранжирования, обновление данных и бизнес-правила выдачи.

Разберём, как проектировать такую систему, чтобы она сохраняла точность при росте ассортимента, не ломалась при изменении характеристик и действительно помогала покупателю находить нужные товары.

01 / SEARCH FUNDAMENTALS SQL LIMITATIONS

1. Почему поиск по большому каталогу перестаёт работать как обычный SQL-запрос

На начальном этапе многие интернет-магазины используют стандартный поиск по базе данных.

Например:

SQL / BASIC SEARCH QUERY 001
SELECT *
FROM products
WHERE name LIKE '%ноутбук%'
ORDER BY name
LIMIT 20;

Для небольшого каталога подобный подход может быть вполне приемлемым. Но по мере роста количества товаров, характеристик и вариантов пользовательских запросов ограничения становятся очевидными.

01 / PERFORMANCE
Производительность
Поиск вынужден просматривать большое количество записей.
02 / RELEVANCE
Качество результатов
Буквальное совпадение не означает соответствие намерению покупателя.
03 / FILTERING
Комбинированный поиск
Сложно правильно сочетать характеристики и диапазоны значений.
04 / RANKING
Ранжирование
Найденные товары ещё необходимо правильно расположить в выдаче.

Первая проблема — производительность.

Поиск с шаблоном, начинающимся с %, часто не позволяет эффективно использовать обычный B-tree индекс. СУБД приходится просматривать большое количество записей, прежде чем найти совпадения.

Вторая проблема — качество результатов.

SQL-запрос ищет буквальные совпадения, но практически не понимает смысл пользовательского ввода.

Для него следующие запросы могут быть совершенно разными:

смартфон Samsung самсунг смартфон Samsung Galaxy телефон самсунг галакси с25

Хотя покупатель может подразумевать одну и ту же категорию или конкретную модель.

Третья проблема — сложность комбинированного поиска.

Покупатель может одновременно указать производителя, диагональ, объём памяти, цвет и ценовой диапазон. Эти условия должны применяться к нужным полям, а не просто искаться по всему тексту карточки.

Четвёртая проблема — ранжирование.

Даже если система нашла 500 подходящих товаров, она ещё должна определить, какие из них показать первыми.

И здесь простая сортировка по названию или дате добавления не решает задачу.

Когда обычного поиска уже недостаточно

Переход к специализированному поисковому движку обычно оправдан, когда появляются следующие признаки:

01 Поиск начинает заметно замедляться при увеличении каталога.
02 Покупатели часто получают пустую выдачу, хотя подходящие товары существуют.
03 Нельзя корректно искать по нескольким характеристикам одновременно.
04 Появляются требования к синонимам и исправлению опечаток.
05 Необходимо ранжировать результаты по релевантности.
06 Фильтры должны работать по сотням тысяч позиций.
07 Каталог обновляется из нескольких внешних источников.
08 Необходимо быстро учитывать изменения цен и остатков.
ENGINEERING NOTE / SCALABILITY

Важно не воспринимать количество товаров как единственный критерий перехода на отдельный движок. Иногда даже каталог из 30 000 позиций требует специализированного поиска из-за сложной структуры и большого количества характеристик. А простой каталог на 200 000 записей может вполне эффективно обслуживаться более лёгкой архитектурой.

Решение определяется не только объёмом данных, но и требованиями к поисковому сценарию, нагрузке и допустимой задержке.

02 / SEARCH ARCHITECTURE INDEX DESIGN

2. Архитектура поисковой системы: почему индекс должен быть отдельным представлением каталога

Одна из распространённых ошибок — пытаться использовать структуру основной базы данных одновременно для хранения товаров, управления каталогом и выполнения поисковых запросов.

Эти задачи имеют разные требования.

Основная база данных должна обеспечивать корректность бизнес-данных: цены, остатки, характеристики, связи с категориями, поставщиками и заказами.

Поисковый движок должен быстро находить подходящие документы, выполнять текстовый поиск, рассчитывать релевантность и строить фасетную выдачу.

ARCHITECTURAL PRINCIPLE
Поэтому в большинстве крупных проектов разумно использовать отдельный поисковый индекс.
SYSTEM ARCHITECTURE / DATA FLOW FIG 01
Поток подготовки данных и обработки поискового запроса показан как единая логическая последовательность.

Упрощённая архитектура выглядит следующим образом:

Основная система хранит товары и их актуальные бизнес-данные.
Механизм синхронизации получает изменения каталога.
Слой подготовки данных нормализует характеристики и формирует поисковые документы.
Поисковый движок индексирует подготовленные документы.
Пользовательский запрос преобразуется в поисковую структуру.
Движок выполняет поиск, фильтрацию и ранжирование.
Сайт получает результаты и отображает их покупателю.

Здесь важно разделить два понятия: товар в основной базе и поисковый документ.

Один товар может иметь десятки характеристик, связи с несколькими справочниками, историю изменения цены и остатки по разным складам.

Но поисковому движку не обязательно знать всю эту структуру.

Ему нужно получить подготовленное представление, содержащее поля, необходимые для поиска и фильтрации.

Как должна выглядеть поисковая запись товара

Например, для ноутбука можно сформировать документ:

JSON / PRODUCT DOCUMENT PRODUCT ID: 58142
{
  "product_id": 58142,
  "name": "Lenovo ThinkPad E16 Gen 2",
  "brand": "Lenovo",
  "category": "Ноутбуки",
  "model": "ThinkPad E16 Gen 2",
  "description": "Ноутбук для работы и бизнеса",
  "attributes": {
    "ram_gb": 16,
    "storage_gb": 1024,
    "screen_inches": 16,
    "processor": "Intel Core Ultra 5"
  },
  "price": 89990,
  "available": true,
  "popularity": 84,
  "updated_at": "2026-11-14T10:30:00"
}

Это условная структура. В реальной системе поля проектируются с учётом товарных категорий и используемого движка.

Принципиально важно, чтобы поисковый документ содержал нормализованные значения.

Например, объём оперативной памяти должен храниться как числовое значение, а не как произвольная строка «16 GB DDR5».

Тогда фильтр сможет корректно обработать условие:

NUMERIC FILTER / RAM
ram_gb >= 16

Аналогично цена должна быть числовым полем, производитель — отдельным идентифицируемым значением, а наличие — отдельным признаком.

CORE ARCHITECTURE RULE

Поисковый индекс не должен превращаться в копию всей базы данных. Он должен содержать именно ту структуру, которая необходима для эффективного поиска.

03 / FULL-TEXT SEARCH TEXT PROCESSING

3. Полнотекстовый поиск: как система находит товары по словам, а не по точному совпадению

Полнотекстовый поиск позволяет находить документы по словам, содержащимся в нескольких текстовых полях.

Но его качество зависит от предварительной обработки текста.

Рассмотрим запрос:

USER QUERY
«купить беспроводные наушники самсунг с шумоподавлением»

В карточке товара название может выглядеть так:

«Samsung Galaxy Buds3 Pro Graphite».

Описание может содержать:

«Полностью беспроводная гарнитура с активным шумоподавлением».

Буквального совпадения со всем запросом нет. Однако товар очевидно соответствует намерению покупателя.

Чтобы получить такой результат, поисковая система должна правильно обработать текст.

Токенизация

На первом этапе текст разделяется на отдельные элементы — токены.

Например:

SOURCE STRING
Lenovo ThinkPad E16 Gen 2

Преобразуется в:

TOKEN STREAM / OUTPUT
lenovo thinkpad e16 gen 2

При этом необходимо учитывать специальные символы, дефисы, артикулы и буквенно-цифровые обозначения.

Это особенно важно для электроники, автозапчастей, оборудования и профессиональных инструментов.

Если поисковая система неправильно обрабатывает обозначения вроде RTX-5070, i7-14700H или USB-C, покупатель может не найти точную модель даже при наличии товара в индексе.

ENGINEERING WARNING

Буквенно-цифровые обозначения нельзя обрабатывать как обычные слова без учёта их структуры. Один символ в названии модели может определять принципиально другую товарную позицию.

Нормализация

Далее выполняется приведение текста к сопоставимому виду:

01
Удаление лишних пробелов.
02
Унификация регистра.
03
Обработка специальных символов.
04
Приведение вариантов написания к согласованной форме.
05
Обработка обозначений моделей.
06
Нормализация единиц измерения там, где это необходимо.

При этом нельзя бездумно удалять все знаки препинания.

В товарных артикулах дефисы, точки и другие символы могут иметь значение.

Например, обозначения двух моделей могут различаться всего одним символом. Если нормализация уничтожит это различие, поиск начнёт возвращать неправильные товары.

Морфология

Для русского языка важна обработка словоформ.

Покупатель может ввести:

кресло
кресла
креслом
креслами

С точки зрения языка это разные формы одного слова.

Морфологический анализ позволяет сопоставлять такие запросы без необходимости хранить все варианты написания в карточке товара.

Но здесь есть ограничение.

Не каждое слово нужно автоматически приводить к общей основе. Для товарных моделей и технических обозначений агрессивная обработка способна ухудшить точность.

Поэтому морфологию следует применять прежде всего к обычной лексике, а артикулы, бренды и названия моделей обрабатывать отдельными правилами.

Разные поля — разный вес

Одна из важных особенностей качественного поиска — не все совпадения одинаково значимы.

Если покупатель вводит точную модель, совпадение в поле model должно иметь больший вес, чем случайное упоминание модели в описании другого товара.

Например:

SEARCH FIELD WEIGHT
Точный артикул Очень высокая
Название модели Очень высокая
Бренд Высокая
Название товара Высокая
Категория Средняя
Характеристики Средняя
Описание Ниже

Это не универсальная шкала весов, а пример приоритетов.

Конкретные коэффициенты необходимо определять экспериментально на реальных запросах.

Именно такой подход позволяет избежать ситуации, когда товар с длинным SEO-описанием оказывается выше точной модели только потому, что в его тексте встретилось больше слов из запроса.

SEARCH ENGINEERING / KEY PRINCIPLE

Полнотекстовый поиск должен учитывать не только совпадение слов, но и происхождение совпадения: точный артикул, название модели и описание не могут иметь одинаковую значимость.

04 / SYNONYM ENGINEERING DOMAIN VOCABULARY

4. Синонимы: как научить поиск понимать разные названия одного товара

Синонимы — один из самых полезных механизмов для больших каталогов.

Покупатель не обязан знать, как именно производитель или продавец назвал товар.

Он может использовать разговорное название, сокращение, профессиональный термин или распространённое обозначение.

Например:

QUERY → POSSIBLE MATCH
флешка → USB-накопитель
ноутбук → лэптоп
беспроводная мышь → мышь без провода
смартфон → мобильный телефон
шуруповёрт → аккумуляторная дрель-шуруповёрт

Но здесь часто допускается серьёзная ошибка: синонимы объединяют слишком широко.

Например, «монитор» и «телевизор» могут иметь похожие характеристики, но это не взаимозаменяемые понятия.

Аналогично «память» может означать оперативную память, встроенное хранилище или карту памяти.

Если объединить такие слова без учёта категории, поиск начнёт выдавать нерелевантные товары.

SYNONYM COLLISION / RISK
монитор ≠ телевизор

Похожие характеристики не делают товарные понятия взаимозаменяемыми.

Почему словарь синонимов должен быть предметным

Хорошая система синонимов строится не просто вокруг слов, а вокруг товарных сущностей.

Для категории «компьютерная техника» можно использовать:

CATEGORY / COMPUTER HARDWARE
ноутбук лэптоп портативный компьютер

Для категории «накопители»:

CATEGORY / STORAGE DEVICES
флешка USB-накопитель USB-флеш-накопитель

Для автотоваров словари будут совершенно другими.

Например, один и тот же термин в разных товарных категориях может обозначать разные изделия.

Поэтому словари должны учитывать категорию, а в некоторых случаях — конкретный бренд или модельный ряд.

CONTEXT-AWARE SYNONYMS / LOGIC
Один поисковый механизм может использовать разные словари в зависимости от товарной категории и контекста.

Как управлять синонимами

Не стоит позволять разработчикам бесконтрольно добавлять новые соответствия непосредственно в код.

Лучше создать управляемый словарь с возможностью:

SYNONYM DICTIONARY / MANAGEMENT
01 Добавления новых терминов.
02 Указания категории.
03 Задания направленных и взаимных соответствий.
04 Отключения ошибочных синонимов.
05 Проверки влияния изменений на выдачу.
06 Ведения истории изменений.

Особенно полезно анализировать реальные запросы покупателей.

Если пользователи регулярно вводят «зарядка type c», а в каталоге используется термин «сетевой адаптер USB Type-C», это основание для добавления соответствующего правила.

Но добавлять синоним следует только после проверки, что он не ухудшит результаты в соседних категориях.

DOMAIN DICTIONARY / KEY PRINCIPLE

Словарь синонимов — это управляемая часть поисковой архитектуры, а не случайный набор замен слов. Его качество напрямую зависит от структуры каталога и понимания предметной области.

05 / TYPO TOLERANCE FUZZY SEARCH

5. Поиск с опечатками: как находить товар, даже если покупатель ошибся

Опечатки неизбежны.

Покупатели торопятся, используют мобильные клавиатуры, допускают ошибки в названиях производителей и не всегда помнят точное написание модели.

Например:

Самсунг Самснг Самсун Самсунгг

Обычный полнотекстовый поиск может не найти совпадение.

Для решения этой задачи применяются алгоритмы нечёткого сопоставления.

Расстояние Левенштейна

Один из распространённых подходов — оценка количества операций, необходимых для преобразования одной строки в другую.

К таким операциям относятся:

01 Вставка символа
02 Удаление символа
03 Замена символа

Например, для слов «самсунг» и «самснг» достаточно одной операции вставки.

Чем меньше расстояние, тем выше вероятность, что слова являются вариантами одного написания.

ОГРАНИЧЕНИЕ

Однако использовать такой механизм без ограничений опасно.

Если применять нечёткий поиск ко всему каталогу, система может начать возвращать множество случайных совпадений.

Особенно это заметно на коротких запросах и артикулах.

Почему короткие запросы требуют отдельной логики

Запрос «LG» состоит всего из двух символов.

Любое нечёткое расширение может привести к большому количеству нерелевантных совпадений.

Поэтому для коротких запросов необходимо ограничивать допустимое расстояние ошибок или полностью отключать fuzzy-поиск.

Для длинных названий можно использовать более гибкие правила.

Например:

01 Для артикула — преимущественно точное совпадение.
02 Для короткого бренда — точное совпадение и словарь вариантов.
03 Для длинного названия — допустимое небольшое количество опечаток.
04 Для обычных слов — нечёткое сопоставление с ограничением по категории.

Опечатки в разных раскладках клавиатуры

Отдельная проблема — покупатель вводит русское название латинскими символами или наоборот.

Например:

ВВЕДЕНО
nfrtn

Вместо:

ОЖИДАЕМОЕ НАПИСАНИЕ
кресло

Можно реализовать преобразование между раскладками клавиатуры.

Но его необходимо использовать как дополнительный вариант запроса, а не безусловно заменять первоначальный текст.

Как должна работать корректировка

Хороший поиск не должен незаметно подменять пользовательский запрос.

Если покупатель ввёл название с опечаткой, можно:

  • Показать найденные результаты.
  • Предложить исправленный вариант.
  • Отобразить сообщение «Возможно, вы имели в виду…».
  • Сохранить возможность выполнить поиск по первоначальному написанию.

Так покупатель понимает, почему получил конкретную выдачу, и может самостоятельно выбрать подходящий вариант.

6. Фасетная навигация: как фильтровать сотни тысяч товаров без противоречий

Фасетная навигация — это механизм, позволяющий уточнять поисковую выдачу по характеристикам товаров.

После каждого выбора система должна пересчитать результаты и показать актуальное количество товаров для остальных значений фильтров.

КЛЮЧЕВОЙ ПРИНЦИП

Здесь возникает важная техническая задача: фасеты должны быть согласованы с текущим набором условий.

Предположим, в каталоге есть 12 000 ноутбуков.

Покупатель выбрал бренд Lenovo. После применения фильтра осталось 1 800 товаров.

Теперь система должна пересчитать доступные значения диагонали, памяти, процессора и других характеристик именно для этих 1 800 позиций.

Если показывать количество товаров по всему каталогу, фасеты будут вводить пользователя в заблуждение.

Почему нельзя просто фильтровать всё как текст

Характеристики необходимо хранить в типизированном виде.

Цена Число

Бренд Идентификатор или нормализованное значение
Цвет Справочное значение
Категория Иерархический идентификатор
Наличие Булево или числовое значение

Например, следующие записи:

16 ГБ 16GB 16 gb 16 гигабайт

Должны быть приведены к единому числовому значению.

Иначе фильтр по объёму памяти будет зависеть от формата записи поставщика.

AND и OR: ошибка, которая незаметно меняет смысл фильтрации

Внутри одной группы значений обычно используется логика OR.

ВНУТРИ ОДНОЙ ГРУППЫ
Бренд = Lenovo ИЛИ ASUS
OR

Между разными группами фильтров применяется AND:

МЕЖДУ ГРУППАМИ
(Бренд = Lenovo ИЛИ ASUS)
И Диагональ = 16
И RAM >= 16
И Цена <= 100000

Это принципиально важно.

Если система ошибочно применит AND между выбранными брендами, покупатель не получит ни одного результата, поскольку один товар не может одновременно иметь двух производителей.

Диапазоны и многозначные характеристики

Некоторые характеристики требуют дополнительной логики.

Например, товар может поддерживать несколько стандартов подключения, иметь несколько вариантов цвета или поставляться в комплектации с разными аксессуарами.

В таких случаях необходимо определить, как фильтр должен работать с многозначными полями.

Для числовых диапазонов следует заранее установить правила включения границ.

Например, фильтр цены от 50 000 до 100 000 рублей обычно должен включать товары с обеими граничными ценами.

ВАЖНО ДЛЯ ВАРИАНТОВ ТОВАРА

Особенно внимательно необходимо работать с вложенными структурами и вариантами товара: фильтры не должны случайно объединять характеристики разных вариантов одной модели.

Один использует официальное название категории, другой — собственную классификацию.

8. Ранжирование: почему правильные товары должны находиться в начале выдачи

Найти подходящие товары — только половина задачи.

Если система возвращает 2 000 результатов, покупателю всё равно необходимо быстро увидеть наиболее подходящие варианты.

За это отвечает ранжирование.

Простейший вариант — сортировка по дате добавления или популярности.

Но оба подхода могут ухудшить качество поиска.

Например, новый товар с точным совпадением названия окажется ниже старой модели, которая просто чаще просматривалась.

Или популярный товар другого производителя окажется выше точной модели, которую искал покупатель.

Релевантность должна учитывать несколько факторов

Для построения рейтинга можно использовать комбинацию следующих признаков:

Точность совпадения артикула Совпадение модели Совпадение бренда Соответствие категории Совпадение характеристик Наличие на складе Популярность товара Коммерческие показатели Актуальность предложения

Но эти факторы не должны иметь одинаковый вес.

Для запроса с точным артикулом главным критерием должно быть совпадение артикула.

Для общего запроса «офисное кресло» важнее категория, характеристики, наличие и релевантность названия.

Пример ранжирования

Покупатель вводит:

«Lenovo ThinkPad E16 16GB»

Система находит три позиции:

RESULT / 01 Полное совпадение
Lenovo ThinkPad E16, 16 ГБ
Наличие: Есть
RESULT / 02 Частичное совпадение
Lenovo ThinkPad E16, 8 ГБ
Наличие: Есть
RESULT / 03 Частичное совпадение
Lenovo ThinkPad E14, 16 ГБ
Наличие: Есть

Если ранжирование учитывает только популярность, третья позиция может оказаться выше первой.

Правильная модель должна сначала учитывать точность соответствия запросу, а уже затем дополнительные факторы.

  • Допустимый диапазон цены
  • Совместимость
  • Конкретный артикул, если покупатель ищет точную позицию

Мягкие факторы

Влияют на порядок отображения товаров.

  • Популярность

Нельзя позволять коммерческим факторам полностью перекрывать соответствие пользовательскому запросу.

Если покупатель ищет конкретную модель, товар с более высокой маржой не должен вытеснять точное совпадение.

Персонализация без потери релевантности

В некоторых проектах полезно учитывать историю просмотров и покупок.

Но персонализация должна быть дополнительным фактором, а не заменой поискового соответствия.

Если пользователь часто покупает комплектующие для компьютеров, это может помочь при общих запросах.

Однако при вводе конкретного артикула система должна прежде всего показать именно этот товар.

9. Какой поисковый движок выбрать: Elasticsearch, OpenSearch, Meilisearch или PostgreSQL

Выбор движка необходимо делать исходя из сложности каталога, нагрузки и требований к поисковому качеству.

Неправильно выбирать технологию исключительно по популярности или максимальному количеству поддерживаемых функций.

Elasticsearch

Подходит для сложных поисковых сценариев и крупных каталогов.

Elasticsearch предоставляет развитые механизмы полнотекстового поиска, анализа текста, фильтрации, агрегаций и настройки релевантности.

Его преимущества:

  • Гибкое управление анализаторами.
  • Поддержка сложных запросов.
  • Развитые механизмы фасетов и агрегаций.
  • Настройка весов полей.
  • Возможность распределённого хранения индексов.
  • Поддержка сложных поисковых сценариев.

Однако возможности движка требуют грамотной настройки.

Неправильно построенный mapping, чрезмерное количество полей и неоптимальные запросы могут привести к росту потребления памяти и ухудшению производительности.

OpenSearch

Альтернатива для распределённого поиска с развитой функциональностью.

OpenSearch предоставляет инструменты полнотекстового поиска, фильтрации, агрегаций и управления индексами.

Он подходит для проектов, которым необходима развитая поисковая инфраструктура и возможность самостоятельно управлять её конфигурацией.

При выборе следует учитывать экосистему, используемые плагины, совместимость клиентов и требования к эксплуатации.

Meilisearch

Подходит для быстрого запуска удобного товарного поиска.

Meilisearch ориентирован на удобную реализацию поиска с исправлением опечаток, настройкой ранжирования и фильтрацией.

Его преимущества:

  • Относительно простая интеграция.
  • Быстрое получение результатов.
  • Удобная настройка поискового поведения.
  • Поддержка фильтрации.
  • Механизмы обработки опечаток.
  • Более низкий порог входа по сравнению со сложными распределёнными системами.

Однако при сложных схемах каталога, специфическом ранжировании и высоких требованиях к распределённой инфраструктуре необходимо внимательно оценить ограничения конкретной версии и конфигурации.

PostgreSQL

Рациональный вариант, если отдельный движок пока не нужен.

PostgreSQL предоставляет полнотекстовый поиск, индексы GIN и расширение pg_trgm для работы с похожими строками.

Для небольших и средних каталогов его возможностей может быть достаточно.

Преимущества:

  • Нет необходимости поддерживать отдельную поисковую инфраструктуру.
  • Данные и поиск находятся в одной системе.
  • Удобная работа с реляционными связями.
  • Поддержка полнотекстового поиска.
  • Возможность использовать триграммное сопоставление.

Но по мере усложнения каталога и роста поисковой нагрузки отдельный движок может оказаться более подходящим решением.

10 / INDEX SYNCHRONIZATION INCREMENTAL UPDATES

10. Обновление поискового индекса: как не показывать покупателю устаревшие данные

Отдельный поисковый индекс создаёт важную проблему: данные в основной базе и поисковой системе могут временно различаться.

Например, покупатель оформил заказ на последний экземпляр товара.

Основная система уменьшила остаток до нуля, но обновление индекса задержалось.

Следующий посетитель видит товар как доступный и пытается его купить.

Или другой сценарий: товар получил новую цену, а поисковый индекс продолжает показывать старую.

DATA CONSISTENCY RISK

Такие ситуации особенно опасны, поскольку покупатель видит информацию, которая уже не соответствует состоянию магазина.

Почему нельзя обновлять индекс только по расписанию

Один из простых подходов — периодически выгружать весь каталог и полностью перестраивать индекс.

Для небольших проектов это может работать.

Но в большом каталоге полная переиндексация:

Создаёт дополнительную нагрузку.
Увеличивает время обновления.
Требует больше ресурсов.
Может приводить к длительным периодам рассогласования.
Усложняет эксплуатацию при частых изменениях ассортимента.

Поэтому обычно применяют инкрементальное обновление.

Инкрементальная индексация

Система получает информацию только об изменившихся товарах.

Например:

01 Изменился остаток товара.
02 Событие попало в очередь обновления.
03 Обработчик получил идентификатор товара.
04 Подготовил актуальный поисковый документ.
05 Обновил соответствующую запись в индексе.

Так можно обновлять не весь каталог, а только необходимые документы.

Почему очередь обновления должна быть надёжной

Предположим, товар изменился в основной базе, но приложение завершилось аварийно до отправки события в поисковую систему.

Если механизм синхронизации не предусматривает восстановление, индекс может навсегда остаться устаревшим.

Для устранения этой проблемы применяют Transactional Outbox.

01 / TRANSACTION
Изменение товара
Основная база данных
→
02 / OUTBOX
Запись события
В той же транзакции
→
03 / WORKER
Передача события
Обработчик обновления
→
04 / SEARCH INDEX
Обновление документа
Поисковый индекс

Изменение товара и запись события об обновлении индекса фиксируются в одной транзакции.

Отдельный обработчик передаёт событие поисковому сервису.

Если передача временно невозможна, событие остаётся доступным для повторной обработки.

При этом необходимо учитывать повторные события и изменение одного товара несколько раз подряд.

Версии документов и защита от устаревших обновлений

Есть ещё одна тонкая проблема.

Предположим, товар был изменён дважды.

Первое обновление создало задачу на индексацию версии 12.

Второе обновление создало задачу на индексацию версии 13.

UPDATE / 01
v12
Первая версия
UPDATE / 02
v13
Более актуальная версия

Но из-за задержек задача версии 13 выполнилась первой, а затем пришла старая задача версии 12.

Если просто перезаписать документ, индекс вернётся к устаревшим данным.

Для предотвращения этого необходимо использовать версионирование документов или проверку актуальности данных перед записью.

VERSION CONTROL

Обновление должно применяться только в том случае, если оно не старее уже сохранённой версии.

Полная переиндексация без остановки поиска

Рано или поздно потребуется изменить структуру индекса.

Например, добавить новые поля, изменить анализатор, исправить нормализацию характеристик или полностью перестроить словари.

В такой ситуации безопаснее не удалять действующий индекс сразу.

Можно использовать следующую схему:

01 Создать новый индекс с новой схемой.
02 Построить его на актуальных данных.
03 Параллельно передавать в него текущие изменения.
04 Проверить количество документов и качество выдачи.
05 Сравнить результаты на контрольных запросах.
06 Переключить приложение на новый индекс через alias.
07 Сохранить старый индекс на период возможного отката.

Такой подход позволяет менять поисковую архитектуру без длительной остановки пользовательского поиска.

11 / CATALOG SCHEMA EVOLUTION DYNAMIC FIELDS & VERSION CONTROL

Как избежать проблем при изменении структуры каталога

В большом интернет-магазине структура ассортимента редко остаётся неизменной.

Появляются новые категории, характеристики, производители, варианты товаров и способы представления данных.

Если поисковый индекс проектировался только под первоначальную структуру, каждое расширение каталога может превращаться в отдельную техническую проблему.

Динамические характеристики

Допустим, магазин продаёт электронику, мебель и строительные материалы.

У этих категорий совершенно разные наборы атрибутов.

Если каждую новую характеристику создавать как отдельное поле индекса, со временем схема может стать чрезмерно сложной.

Для таких случаев применяют комбинированную модель:

01 / CORE
Общие поля: название, бренд, категория, цена, наличие.
02 / FILTERS
Типизированные поля для наиболее важных фильтров.
03 / ATTRIBUTES
Структурированные атрибуты для категорий.
04 / IDENTIFIERS
Отдельные поля для поиска по артикулам и моделям.
MAPPING CONTROL / WARNING

В Elasticsearch и OpenSearch необходимо особенно внимательно контролировать количество динамически создаваемых полей. Бесконтрольное расширение mapping может привести к достижению лимитов и проблемам при индексации.

Версионирование схемы

Изменение структуры поискового документа должно быть управляемым.

Например:

V1 catalog_index_v1
 
V2 catalog_index_v2
 
V3 catalog_index_v3

Это позволяет независимо тестировать новую модель данных и выполнять переключение после проверки.

Не стоит изменять структуру поискового индекса без понимания того, как изменение повлияет на существующие запросы, фильтры и сортировки.

Удаление товаров

Отдельно необходимо обрабатывать удаление товара.

Если позиция удалена из основной базы, она не должна бесконечно оставаться в поисковом индексе.

Для этого необходимо предусмотреть события удаления, проверку существования товара и периодическую сверку состава индекса с основным каталогом.

Также важно различать удаление товара и временную недоступность.

REMOVED
Товар удалён из основной базы и не должен оставаться в поисковом индексе.
TEMPORARILY UNAVAILABLE
Товар временно отсутствует на складе, но может оставаться в поиске.

Товар, которого сейчас нет на складе, не обязательно должен исчезать из поиска. В некоторых магазинах его целесообразно показывать с отметкой «Нет в наличии» или предлагать аналогичные позиции.

Решение зависит от бизнес-модели и пользовательского сценария.

12 / IDENTIFIER SEARCH SKU, MODEL & EXACT MATCHING

Как искать по артикулам, моделям и техническим обозначениям

Для некоторых категорий поиск по названию вторичен.

Покупатель может знать точный артикул запчасти, код оборудования или номер модели.

В таких сценариях обычный полнотекстовый поиск способен допускать ошибки, которые практически незаметны при поиске по общим словам.

Например, следующие обозначения могут относиться к разным товарам:

AB-1250
AB-1250A
AB-1250B

Если анализатор удаляет дефисы или слишком агрессивно нормализует строку, результаты могут смешаться.

Поэтому для технических идентификаторов желательно предусмотреть отдельный механизм поиска.

Разделение поисковых сценариев

Можно использовать несколько типов сопоставления:

01
Точный поиск по артикулу.
Приоритетное совпадение полного идентификатора.
02
Нормализованный поиск.
Допускается сопоставление вариантов записи, если они действительно эквивалентны.
03
Полнотекстовый поиск по названию.
Используется для обычных пользовательских запросов.
04
Нечёткий поиск.
Применяется для исправления опечаток в текстовых названиях.
MATCH PRIORITY

При этом точный артикул должен иметь существенно больший вес, чем случайное совпадение его части в описании.

Почему поиск по подстроке может быть опасен

Если покупатель вводит AB-1250, система не должна автоматически считать одинаково подходящими товары AB-1250A и AB-1250B.

Для некоторых категорий такое поведение допустимо, но для автозапчастей и технического оборудования оно может привести к покупке несовместимой позиции.

IDENTIFIER COLLISION / RISK

Поэтому поиск по частичному артикулу должен учитывать категорию и правила идентификации конкретного типа товара.

13 / PRODUCT VARIANT MODELING PARENT & CHILD DOCUMENTS

Поиск по вариантам товаров: как не смешивать разные характеристики

В интернет-магазинах часто существует одна базовая модель с несколькими вариантами.

Например, футболка представлена в размерах S, M, L и XL, а также в нескольких цветах.

Или ноутбук продаётся с разными конфигурациями оперативной памяти и накопителя.

Здесь необходимо заранее определить, что именно индексируется: родительский товар или каждый продаваемый вариант.

Индексация родительского товара

01

В поиске отображается одна карточка модели.

Покупатель открывает её и выбирает доступную конфигурацию.

Такой подход удобен, если варианты отличаются незначительно и не требуют отдельной поисковой выдачи.

Индексация каждого варианта

02

Каждая конфигурация имеет отдельный поисковый документ.

Это оправдано, когда варианты существенно различаются по цене, характеристикам или доступности.

Но здесь возникает риск дублирования.

Покупатель вводит название модели и получает 15 почти одинаковых результатов, отличающихся только цветом или объёмом памяти.

Комбинированная модель

Для многих магазинов наиболее удобен следующий подход:

01 Родительская карточка используется для отображения товара.
02 Варианты сохраняются как отдельные структурированные сущности.
03 Поиск учитывает характеристики вариантов.
04 Фильтрация проверяет наличие хотя бы одного подходящего варианта.
05 При открытии карточки выбирается доступная конфигурация, соответствующая запросу.

Особенно важно, чтобы фильтры не объединяли характеристики разных вариантов.

Например, у одной модели может быть версия с 8 ГБ оперативной памяти и SSD 1 ТБ, а другая — с 16 ГБ и SSD 512 ГБ.

VARIANT DATA / TWO CONFIGURATIONS
VARIANT A
8 ГБ RAM
SSD 1 ТБ
VARIANT B
16 ГБ RAM
SSD 512 ГБ
Запрос: 16 ГБ RAM + SSD 1 ТБ. Ни одна из двух конфигураций ему не соответствует.

Если система агрегирует характеристики на уровне родительского товара, она может ошибочно показать модель как соответствующую запросу «16 ГБ и 1 ТБ», хотя такой конфигурации вообще не существует.

VARIANT FILTERING / CRITICAL ERROR

Это одна из самых неприятных ошибок товарного поиска: формально все характеристики присутствуют, но ни один реальный вариант не удовлетворяет условиям покупателя.

14 / ZERO-RESULT ANALYSIS QUERY DIAGNOSTICS & RECOVERY

Нулевая выдача: как понять, почему покупатель ничего не нашёл

Нулевая выдача — это не просто отсутствие результатов.

Для интернет-магазина это потерянный поисковый сценарий, который иногда можно было бы завершить продажей.

Причины могут быть совершенно разными:

Ошибка в написании.
Неучтённый синоним.
Неправильно настроенная морфология.
Неверная категория.
Слишком строгие фильтры.
Устаревший индекс.
Удалённый товар.
Некорректный артикул.
Ошибка нормализации характеристик.

Если просто показать сообщение «Ничего не найдено», магазин теряет возможность помочь покупателю.

Как должна реагировать система

Предположим, пользователь ищет:

USER QUERY
«беспроводные наушники самснг».

Результатов нет.

Система может обнаружить вероятную опечатку и предложить:

SUGGESTED CORRECTION
«Возможно, вы имели в виду беспроводные наушники Samsung».

Другой случай: покупатель выбрал слишком узкий набор характеристик.

FILTER CONSTRAINTS
  • Цена до 20 000 рублей.
  • Производитель определённой марки.
  • Память от 1 ТБ.
  • Диагональ 17 дюймов.

Если подходящих товаров нет, можно показать, какие фильтры ограничили выбор сильнее всего.

FILTER INTEGRITY / WARNING

Но нельзя незаметно отменять пользовательские условия и выдавать товары, которые им не соответствуют.

Анализ запросов без результатов

Все запросы с нулевой выдачей полезно сохранять в аналитике.

Для каждого такого случая желательно фиксировать:

Исходный запрос.
Нормализованный запрос.
Выбранные фильтры.
Категорию.
Количество результатов.
Предложенные исправления.
Последующее поведение пользователя.

Это позволяет отличить реальную проблему поиска от отсутствия товара в ассортименте.

Например, если покупатели постоянно ищут «адаптер USB C HDMI», а товары существуют под названием «переходник Type-C на HDMI», проблема заключается в словаре и обработке запроса.

Если же пользователи регулярно ищут конкретную модель, которой нет в каталоге, это уже информация для управления ассортиментом.

BUSINESS ANALYTICS

Поисковая аналитика должна помогать не только разработчикам, но и коммерческому подразделению.

15 / SEARCH PERFORMANCE QUERY COST & OPTIMIZATION

Производительность: что происходит, когда поиск начинает тормозить

Даже правильно настроенная поисковая система может терять производительность при росте нагрузки.

Причём проблема не всегда заключается в количестве товаров.

На скорость влияют:

Количество документов.
Размер поисковых документов.
Количество индексируемых полей.
Сложность анализаторов.
Число одновременно выполняемых фильтров.
Количество фасетных агрегаций.
Глубина пагинации.
Частота обновления индекса.
Количество одновременных запросов.

Глубокая пагинация

Обычная схема from/size удобна для небольших глубин.

Но при запросе, например, 20 000-й позиции поисковому движку приходится учитывать большое количество предшествующих результатов.

Для глубокого просмотра больших выдач в Elasticsearch и OpenSearch обычно применяют search_after с устойчивой сортировкой, а для согласованного просмотра изменяющегося набора данных — PIT (Point in Time), если это поддерживается используемой версией.

DEEP PAGINATION / METHODS
from / size
Обычная пагинация для небольших глубин.
search_after
Переход к следующим результатам с устойчивой сортировкой.
PIT
Согласованный просмотр изменяющегося набора данных.

Это особенно важно для каталогов, где сортировка должна оставаться предсказуемой при одновременном изменении товаров.

Слишком тяжёлые фасеты

Если на каждом запросе пересчитывать десятки сложных агрегаций по большому количеству полей, нагрузка может существенно вырасти.

Поэтому необходимо анализировать, какие фасеты действительно используются и какие из них требуют точных значений.

Не все характеристики нужно выводить одновременно.

В некоторых категориях имеет смысл показывать основные фильтры сразу, а дополнительные загружать по запросу.

Размер поискового документа

Не стоит без необходимости помещать в индекс длинные описания, большие HTML-фрагменты, изображения в виде данных и все технические поля основной базы.

Поисковый документ должен оставаться компактным.

Большие текстовые поля следует индексировать только тогда, когда они действительно участвуют в поиске.

Кэширование

Для популярных поисковых сценариев можно использовать кэширование результатов.

Но необходимо учитывать, что выдача зависит не только от текста запроса, но и от:

Фильтров Сортировки Региональных условий Доступности Цены Пользовательских параметров

Поэтому ключ кэша должен учитывать все параметры, влияющие на результат.

CACHE INVALIDATION / WARNING

Кроме того, кэширование требует стратегии инвалидации. Иначе покупатель может продолжать видеть товар по старой цене или с уже неактуальным наличием.

16 / SEARCH QUALITY METRICS RELEVANCE EVALUATION

Как измерять качество поиска, а не просто его скорость

У поисковой системы есть две независимые характеристики:

01 / SPEED
Насколько быстро она возвращает результаты.
02 / RELEVANCE
Насколько правильно она их возвращает.

Можно добиться ответа за 30 миллисекунд, но если покупатель получает нерелевантные товары, такая производительность не имеет коммерческой ценности.

Поэтому необходимо оценивать поисковое качество отдельно.

Основные метрики

Zero Results Rate

Доля запросов, по которым не найдено ни одного результата.

Высокое значение может указывать на проблемы со словарями, каталогом или фильтрами.

Search Click-Through Rate

Доля поисковых сессий, в которых пользователь перешёл хотя бы к одному товару из выдачи.

Помогает оценивать привлекательность и релевантность результатов.

Search Conversion Rate

Доля поисковых сессий, завершившихся покупкой.

Показывает коммерческую эффективность поиска, хотя на неё также влияют цена, наличие и качество карточек товаров.

MRR (Mean Reciprocal Rank)

Метрика, которая учитывает позицию первого релевантного результата.

Если нужный товар находится на первой позиции, оценка выше, чем если он расположен на десятой.

NDCG (Normalized Discounted Cumulative Gain)

Позволяет оценивать качество ранжирования с учётом нескольких релевантных результатов и их позиций.

Для сложного товарного поиска эта метрика особенно полезна, поскольку правильная выдача не всегда состоит из одного единственного товара.

Контрольная выборка запросов

Для регулярной оценки необходимо сформировать набор типичных запросов:

Точные артикулы.
Названия моделей.
Общие категории.
Запросы с опечатками.
Запросы с синонимами.
Запросы с характеристиками.
Сложные комбинации фильтров.
Запросы с несколькими вариантами написания брендов.

Для каждого запроса определяется ожидаемая релевантность результатов.

После изменения анализатора, словаря или алгоритма ранжирования новая версия проверяется на этой выборке.

REGRESSION CONTROL

Так можно обнаружить регрессию до того, как она повлияет на покупателей.

Например, добавление нового синонима может улучшить поиск в одной категории, но ухудшить выдачу в другой.

Без контрольных запросов такое изменение легко пропустить.

17 / MULTI-WAREHOUSE SEARCH REGIONAL AVAILABILITY & OFFERS

Как организовать поиск при нескольких складах и разных регионах доставки

В крупных магазинах наличие товара часто зависит от региона покупателя.

Один и тот же товар может быть доступен на складе в Москве, отсутствовать в Санкт-Петербурге и иметь ограниченное количество в Екатеринбурге.

Если поисковый индекс содержит только общий признак available, он не сможет правильно учитывать региональные условия.

В таких проектах необходимо разделять глобальные свойства товара и локальные данные предложения.

DATA MODEL / PRODUCT & OFFERS
{
  "product_id": 58142,
  "name": "Lenovo ThinkPad E16",
  "offers": [
    {
      "warehouse_id": 1,
      "region_id": 77,
      "available": true,
      "quantity": 12
    },
    {
      "warehouse_id": 2,
      "region_id": 78,
      "available": false,
      "quantity": 0
    }
  ]
}

Это условный пример структуры.

На практике модель может быть сложнее и учитывать несколько продавцов, сроки поставки, резервы и условия доставки.

CORE PRINCIPLE

Главная задача — не смешивать наличие товара и наличие конкретного предложения.

Если покупатель выбирает регион, поиск должен учитывать именно те предложения, которые доступны в его условиях покупки.

При этом остатки для оформления заказа необходимо перепроверять в основной системе. Поисковый индекс не должен быть окончательным источником истины для резервирования товара.

18 / IMPLEMENTATION ROADMAP PHASED SYSTEM DELIVERY

Практическая схема внедрения поиска в крупный интернет-магазин

Попытка сразу реализовать все возможности обычно приводит к усложнению проекта и затрудняет оценку результата.

Гораздо разумнее внедрять поисковую систему последовательно, сохраняя возможность измерять качество каждого этапа.

01

Аудит каталога

До выбора движка необходимо изучить структуру данных.

Проверяются:

  • Количество товаров и вариантов.
  • Качество названий.
  • Заполнение характеристик.
  • Дубли производителей.
  • Артикулы.
  • Категории.
  • Источники данных.
  • Частота изменений цен и остатков.

На этом этапе часто обнаруживается, что основная проблема находится не в поисковом алгоритме, а в качестве товарной информации.

02

Проектирование поисковой модели

Определяются:

  • Поля поискового документа.
  • Типы данных.
  • Категорийные характеристики.
  • Анализаторы.
  • Синонимы.
  • Правила обработки артикулов.
  • Структура фасетов.
  • Бизнес-факторы ранжирования.

Здесь важно сразу определить, какие поля являются обязательными, а какие могут отсутствовать.

03

Выбор движка и создание индекса

На основании требований выбирается поисковая технология. Создаётся первоначальная схема индекса, загружается тестовый каталог и проверяется производительность.

04

Реализация синхронизации

Настраивается передача изменений из основной базы.

Необходимо проверить не только обычное обновление, но и повторную доставку событий, потерю сообщений, удаление товаров и параллельные изменения.

05

Поисковый API

Создаётся единая точка взаимодействия сайта с поисковой системой.

Она должна принимать запрос, фильтры, сортировку и контекст пользователя, а затем формировать корректный запрос к движку.

Не стоит напрямую связывать пользовательский интерфейс с внутренней структурой Elasticsearch или OpenSearch.

Промежуточный API позволит изменять поисковый движок без полной переработки клиентской части.

06

Настройка релевантности

На контрольной выборке запросов проверяются веса полей, точные совпадения, синонимы, опечатки и коммерческие факторы.

07

Нагрузочное и функциональное тестирование

Проверяются:

  • Время ответа.
  • Одновременные запросы.
  • Фасетные агрегации.
  • Глубокая пагинация.
  • Обновление индекса под нагрузкой.
  • Корректность результатов после изменения товара.
  • Восстановление после сбоев.
08

Постепенное переключение

Для крупных проектов разумно использовать постепенное включение нового поиска.

Часть запросов можно направлять в новую систему, сравнивая результаты с действующим поиском.

После проверки качества и стабильности выполняется переключение основной аудитории.

Такой подход позволяет обнаружить проблемы до полного перехода на новую архитектуру.

19 / ENGINEERING PITFALLS COMMON ARCHITECTURAL FAILURES

Типичные ошибки при разработке поиска, которые дорого обходятся магазину

Некоторые проблемы повторяются в проектах независимо от выбранной технологии.

Использование одного текстового поля для всех характеристик.

Поиск становится неспособным корректно различать числовые параметры, бренды, артикулы и категории.

Бесконтрольное добавление синонимов.

Выдача расширяется, но её точность снижается.

Одинаковая обработка названий и артикулов.

Точные идентификаторы начинают сопоставляться с похожими, но совершенно другими моделями.

Сортировка исключительно по популярности.

Точные совпадения проигрывают товарам, которые чаще покупают.

Отсутствие нормализации характеристик.

Одинаковые значения дробятся на множество вариантов, а фильтры работают непредсказуемо.

Полная переиндексация при каждом изменении товара.

Нагрузка растёт, обновления замедляются, а масштабирование становится дороже.

Отсутствие контроля устаревших событий.

Старые данные могут перезаписывать новые.

Использование индекса как источника истины для остатков.

Покупатель видит товар доступным, хотя в основной системе его уже нет.

Отсутствие поисковой аналитики.

Разработчики не знают, что именно ищут покупатели и на каких запросах система теряет продажи.

Изменение ранжирования без регрессионных проверок.

Улучшение одного поискового сценария незаметно ухудшает другие категории.
