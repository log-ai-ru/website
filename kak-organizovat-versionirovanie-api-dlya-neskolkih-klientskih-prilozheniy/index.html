Как организовать версионирование API для нескольких клиентских приложений

 

 

 

 

 

 

Допустим, у сети клиник три потребителя серверной части: сайт онлайн-записи, мобильное приложение для пациентов и интеграция с внешним агрегатором, через который записываются люди, о клинике ничего не знавшие. Все три работают через один API (application programming interface, программный интерфейс: набор запросов и форматов ответов, по которым одна программа обращается к другой).

Утро условного четверга выглядит так.

INCIDENT LOG / THURSDAY
07:40 — 09:15
 
07:40 / DEPLOY

Выкладывается новая версия сервера. В списке записей на приём поле status перестаёт быть числом (1 — записан, 2 — подтверждён, 3 — отменён) и становится строкой: "booked", "confirmed", "cancelled". Правка воспринималась как наведение порядка: таблица соответствий чисел и смыслов занимала в документации полстраницы.

 
07:44 / FRONTEND

Сайт, обновлённый в той же выкладке, работает.

 
07:52 / IOS CLIENT

Первые обращения в поддержку: у владельцев iOS-приложения версии 3.8 экран «Мои записи» пуст. Приложение разбирает ответ строго, и одна запись с неожиданным типом поля приводит к ошибке разбора всего списка.

 
08:10 / ANDROID CLIENT

Выясняется, что Android-версия экран открывает, но каждая запись показана с серым статусом «неизвестно»: клиент подставляет значение по умолчанию.

 
08:25 / EXTERNAL INTEGRATION

Агрегатор, в поддержку не звонивший, получает строку там, где ждал число. Его код сводит нераспознанное значение к нулю, а ноль в его модели означает «отменено». Слоты освобождаются и тут же занимаются другими пациентами.

 
08:30 / ROLLBACK

Сервер откатывается к прежней версии.

 
09:15 / INCIDENT RESULT

Итог: за 50 минут в агрегаторе отменены 38 записей, 11 слотов уже заняты. Остальные 27 восстанавливаются вручную, 11 пациентов обзванивают и переназначают.

Ошибки одного человека здесь нет. Серверная команда поступила так, как допустимо, когда потребитель один и обновляется вместе с сервером. Приложение 3.8 написано в предположении, что тип поля не изменится. Агрегатор — в предположении, что незнакомое значение безопасно считать нулём. Сломалось допущение, что все стороны меняются одновременно, а не код.

CORE PRINCIPLE

Версионирование API — это правила изменения интерфейса, пока существуют потребители, которых нельзя обновить по команде: что им обещано, как о них узнать, как их предупредить и когда обещание заканчивается. Номер в адресе (/v2/) составляет в этом наименьшую часть.

CLIENT LANDSCAPE

Три потребителя с разной скоростью обновления

Для выбора схемы важно не число клиентов, а две характеристики каждого: как быстро он обновляется и можно ли узнать, на какой версии он работает сейчас. Три типичных потребителя различаются по обеим.

CLIENT UPDATE MODEL / CONCEPTUAL
Схема показывает относительную управляемость обновлений, а не нормативные сроки для всех проектов.

Сайт: управляемый, но не мгновенный

Фронтенд сайта обычно выкладывается вместе с сервером, и кажется, что версия у него одна. Это неверно по двум причинам. Одностраничное приложение (SPA, single-page application: сайт, который загружает код один раз и дальше работает без перезагрузки страницы) остаётся в открытой вкладке со старым кодом, пока пользователь её не обновит. Вкладка, открытая вчера, вечером обращается к серверу нового выпуска. Кроме того, во время поэтапной выкладки несколько минут одновременно работают серверы старого и нового выпусков, и один клиент может попасть на любой из них.

Отставание сайта измеряется часами и днями, но не нулём. Поэтому даже полностью управляемому клиенту нужна совместимость в течение окна выкладки и отката. Особенно важно учитывать кеширование статических ресурсов, service worker и CDN: старый HTML может загрузить уже новый JavaScript или, наоборот, продолжить обращаться к серверу с прежним контрактом. Версии фронтенда и серверной части необходимо связывать через совместимые периоды развёртывания, а не только через номер релиза.

Мобильные приложения: хвост, который не закрывается

Сборка проходит проверку в магазине приложений, затем начинается обновление пользователей. Часть обновляется в первые дни, остальные — за недели и месяцы, некоторые не обновляются вовсе: отключено автообновление, не хватает места, операционная система слишком старая для новой сборки. В итоге одновременно работает несколько версий приложения, и самая старая может быть выпущена больше года назад.

Ошибку в клиентской сборке нельзя гарантированно исправить за час: серверные обходные решения иногда помогают, но доставить новую сборку на все устройства быстро невозможно. Установленные копии нельзя централизованно заменить, поэтому сервер вынужден учитывать поведение старых клиентов, а не рассчитывать на их немедленное обновление.

Отсюда два требования к самому приложению.

Первое: каждый запрос несёт версию сборки и платформу в заголовках, например:

HTTP REQUEST HEADERS
X-App-Version: 3.8.1
X-Platform: ios

Это отдельная сущность от версии API: одну версию API обслуживают много сборок, и именно по сборкам видно, кто остался в хвосте и для какой из них нужна серверная заплатка.

Если политика поддержки зависит от версии сборки, необходимо учитывать ограничение такого механизма: обычный HTTP-заголовок не доказывает подлинность приложения. Для управления доступностью старых сборок его можно использовать как операционный сигнал, но при необходимости защиты от модифицированных клиентов требуется отдельная проверка подлинности приложения, соответствующая модели угроз. Даже аттестация приложения не должна рассматриваться как абсолютная гарантия: она лишь повышает достоверность сведений о клиенте и усложняет подмену.

Второе: механизм принудительного обновления должен быть уже в самой первой сборке. Он состоит из ответа сервера «минимально поддерживаемая версия такая-то» и экрана приложения, который блокирует работу и ведёт в магазин. Научить этому уже установленную сборку нельзя. Без механизма единственный способ отключить старую сборку — сломать её, а сломанное приложение порождает обращения в поддержку и низкие оценки, но не обновление.

OPERATIONAL CONSTRAINT

Порог минимальной поддерживаемой версии должен задаваться управляемой конфигурацией на стороне сервера, а не жёстко зашиваться в приложение. При этом само приложение должно содержать неизменяемую логику обработки ответа о необходимости обновления, иначе изменить политику без выпуска новой сборки не получится. Следует предусмотреть безопасное поведение при недоступности сервиса проверки: например, использовать последнее полученное значение в пределах установленного срока или временно разрешать ограниченную работу. Иначе отказ небольшого служебного endpoint может заблокировать всех пользователей приложения.

Механизм обновления должен учитывать и минимальную поддерживаемую версию операционной системы. Пользователь может хотеть обновиться, но не иметь технической возможности установить новую сборку. Для таких пользователей необходима отдельная политика: ограниченный режим, альтернативный канал обслуживания или заранее объявленное прекращение поддержки с понятным объяснением. Простое повышение минимальной версии приложения не решает проблему, а исключает эту аудиторию.

Принудительное обновление также не гарантирует, что пользователь установит новую сборку. Оно лишь позволяет приложению, в котором уже реализован такой механизм, прекратить работу со старой версией. Поэтому до повышения минимальной версии необходимо проверить доступность обновления для поддерживаемых устройств, подготовить канал помощи и определить, что делать с пользователями, чьи устройства больше не поддерживаются.

Внешние интеграции: чужие сроки и неизвестные адресаты

Изменение API попадает в очередь задач партнёрской команды на общих основаниях и конкурирует с её приоритетами. Часть интеграций написана один раз и годами не трогается: автор мог уйти, а скрипт продолжает забирать данные каждые десять минут. Срок уведомления нередко зафиксирован в договоре или условиях использования API и тогда ограничивает не хуже технических причин.

Практический вывод: без реестра потребителей предупреждать некого. Минимальный реестр сопоставляет идентификатор потребителя с организацией, техническим контактом, используемой версией и временем последнего обращения. Полезно также хранить перечень используемых операций, дату последнего подтверждения контакта и ответственного менеджера. Ключ доступа можно использовать как один из идентификаторов, но не как единственный источник сведений о потребителе.

REGISTRY GAP / RISK

Ключи, выданные «на всех» или без контакта, превращаются в неизвестных потребителей, и ломаются при отключении обычно именно они.

Один ключ не всегда равен одному потребителю: за ним может стоять несколько систем, подразделений или фоновых заданий. Поэтому для критичных интеграций реестр должен учитывать не только ключ, но и владельца, назначение и фактические сценарии использования. Если несколько независимых систем используют один ключ, их необходимо различать отдельными идентификаторами потребителей. Версию контракта в таком случае следует закреплять за идентификатором интеграции, а не за общим ключом. Если сервер не может однозначно определить интеграцию по запросу, необходимо либо разделить ключи, либо явно передавать дополнительный идентификатор. Иначе переключение версии для одного потребителя может одновременно изменить контракт для остальных.

Вебхуки: когда сервер сам стучится к клиенту

Вебхук (webhook) — запрос, который сервер платформы отправляет на адрес клиента, когда происходит событие. Здесь роли меняются: формат сообщения становится контрактом, реализованным на стороне клиента, а момент получения клиент не выбирает. Новое поле или новый тип события приходит без запроса.

У вебхуков нужно различать как минимум три сущности:

01 / SCHEMA
Версия схемы события

Определяет структуру сообщения: поля, типы и правила их интерпретации.

02 / EVENT TYPE
Тип события

Определяет, что произошло: например, appointment.created или appointment.cancelled.

03 / SUBSCRIPTION
Подписка

Определяет, какие события конкретный потребитель хочет получать.

Эти сущности не обязательно должны иметь одну версию. Потребитель может получать несколько типов событий одной версии схемы, а один тип события может существовать в нескольких совместимых редакциях структуры.

Новые типы событий можно включать по подписке, если такая модель предусмотрена платформой. Другой вариант — отправлять все типы событий, требуя от клиента безопасно обрабатывать неизвестные. В обоих случаях поведение должно быть явно определено: нельзя предполагать, что любой обработчик спокойно переживёт неизвестный тип события.

Для вебхуков важны ещё четыре свойства, которые не решаются одной версией схемы:

01
Идентификатор события

Каждая логическая публикация получает устойчивый уникальный идентификатор. Повторная доставка сохраняет его.

02
Идемпотентная обработка

Повтор одного события не должен повторно выполнять бизнес-операцию. Клиент сохраняет обработанные идентификаторы и проверяет их до применения изменений. Проверка и фиксация идентификатора должны быть согласованы с обработкой события: иначе два параллельных повтора могут одновременно пройти проверку и выполнить действие дважды.

03
Подлинность сообщения

Клиент проверяет подпись, например HMAC с секретом, известным обеим сторонам. Нужно также проверять временную метку и защищаться от повторного воспроизведения старого подписанного запроса. Подписывать следует точное тело сообщения, а сравнение подписей выполнять способом, устойчивым к атакам по времени.

04
Повторная доставка

Платформа определяет тайм-ауты, интервалы повторов, максимальный срок доставки и поведение при постоянной ошибке. Клиент должен быстро подтвердить приём, а длительную обработку выполнять асинхронно.

Повторные попытки должны использовать ограниченную экспоненциальную задержку и случайный разброс времени (jitter), чтобы после восстановления сервиса множество клиентов не отправляли запросы одновременно. Для каждого события необходимы понятные правила исчерпания попыток, журнал неудачных доставок и, по возможности, механизм ручного повтора.

При изменении схемы необходимо сохранять идентификатор события и правила повторной доставки, чтобы переход версии не создавал дубликаты или потерю событий. Если событие нельзя обработать из-за временной ошибки, клиент должен иметь возможность безопасно получить его повторно. Если ошибка постоянная, необходим механизм регистрации неудачной доставки и последующего разбора.

CONTRACT / VERSIONING

Что получает номер версии, а что нет

В разговорах о версиях встречаются четыре разных числа, и их постоянно путают.

01 / CONTRACT
Версия контракта

Договорённость о форме запросов и ответов; её использует или выбирает клиент в зависимости от модели API.

02 / CLIENT
Версия клиента

Сборка приложения или выпуск сайта; нужна серверу для диагностики и определения состава потребителей, но сама по себе не должна определять контракт.

03 / SERVER RELEASE
Версия выпуска сервера

Меняется при каждой выкладке и клиенту обычно безразлична.

04 / DATABASE
Версия схемы базы данных

Меняется миграциями и снаружи видна быть не должна.

Типовая ошибка — привязать номер API к номеру выпуска (v2.14.3). Клиент тогда не может понять, какие из выпусков опасны, а сервер вынужден поддерживать столько версий контракта, сколько выложено сборок. Клиенту нужен идентификатор контракта — обычно мажорный номер или дата, — который меняется при несовместимом изменении. Совместимость внутри версии — обязанность сервера, она проверяется тестами, а не нумеруется.

Совместимость бывает двух направлений, но терминологию важно использовать аккуратно.

01 / BACKWARD COMPATIBILITY
Новый сервер обслуживает старых клиентов

Это обычно называют обратной совместимостью: после обновления сервера он продолжает принимать старые запросы и формировать ответы, понятные прежним сборкам.

02 / FORWARD COMPATIBILITY
Старый сервер обслуживает клиентов после отката

Этот сценарий иногда называют прямой совместимостью (forward compatibility), однако термин используется неодинаково. Поэтому в эксплуатационных требованиях лучше описывать конкретное свойство: старый выпуск должен продолжать корректно работать с запросами, состояниями и данными, которые могли появиться во время частичного развёртывания нового выпуска.

Это особенно важно при поэтапной выкладке. Если новый клиент начинает отправлять поле, которое старый сервер не понимает, откат может нарушить работу даже после восстановления прежнего кода. Аналогично, если новая версия сервера записала в базу значение, которое старый код не умеет читать, откат приложения не вернёт систему в прежнее состояние.

DEPLOYMENT / ROLLBACK

Поэтому откат — не просто возврат бинарного файла. Он должен учитывать изменения API, схемы базы данных, форматов сообщений и уже записанных данных. Для этого и применяют последовательность expand/contract: сначала вводят совместимые расширения, затем переводят потребителей и только после завершения перехода удаляют старые элементы.

BREAKING CHANGES / COMPATIBILITY

Что ломает клиента: от очевидного к незаметному

Ломающее изменение (breaking change) — такое, после которого корректно реализованный клиент без правки своего кода начинает работать неправильно. Коварство определения в слове «корректно»: реальный контракт шире написанного в документации.

Удобно проверять изменения отдельно для запросов и ответов. В запросах добавление нового необязательного поля обычно безопасно для нового сервера при условии, что он корректно обрабатывает его отсутствие. Но это не гарантировано: строгий валидатор может отвергнуть запрос с дополнительным свойством, если его отправит уже обновлённый клиент на старый сервер.

В ответах добавление поля может сломать клиента, если тот отвергает неизвестные свойства. Удаление поля также может быть ломающим, если клиент его использует. Поэтому ни расширение, ни сужение структуры само по себе не гарантирует совместимость. Важны направление обмена, правила разбора и фактические ожидания потребителей.

Две строки о перечислениях объясняют, зачем в контракте прямо записывают, какие из них открыты. Клиент, прочитавший такую запись, обязан показать незнакомое значение нейтрально («неизвестно»), не скрывая запись и не подставляя ноль. Для закрытого перечисления сервер, наоборот, гарантирует, что набор значений не расширится в пределах версии контракта.

Клиентская сторона этого правила называется принципом устойчивого читателя (tolerant reader): игнорировать лишние поля, не падать на незнакомых значениях, брать из ответа только нужное. Но устойчивость не означает безусловно игнорировать любые изменения. Неизвестное поле можно пропустить, если оно действительно необязательное. Неизвестное значение статуса можно отобразить как «неизвестно», но нельзя автоматически трактовать как «отменено».

API EVOLUTION / EXPAND-CONTRACT

Сначала эволюция, потом новая версия

Большинство изменений обходится без нового мажорного номера, если выполнять их как параллельное изменение (parallel change), оно же схема expand/contract («расширить, затем сжать»). Шагов три: добавить новое рядом со старым, перевести потребителей, убрать старое, когда оно больше никому не нужно.

Но у схемы есть предварительное условие: добавление нового элемента должно быть совместимо с уже работающими клиентами. Если старые клиенты отвергают неизвестные поля, простое добавление второго поля тоже может оказаться ломающим изменением. В таком случае сначала необходимо обновить клиентов, согласовать режим разбора или предоставить отдельное представление ответа.

Статус записи на приём, сделанный по этой схеме, выглядит так. На стадии расширения ответ несёт оба поля, и их значения всегда согласованы:

RESPONSE / EXPAND STAGE
{
  "id": "a-91837",
  "status": 2,
  "state": "confirmed"
}

Поле status помечается в спецификации устаревшим, state объявляется открытым перечислением. Для состояний, которые старое поле выразить не может (скажем, новое «перенос запрошен»), проекция фиксируется заранее: допустим, старый клиент увидит status: 2, потому что запись для него всё ещё действует. Это продуктовое решение, а не техническое, и принимать его нужно до выкладки.

При этом проекция должна быть согласована не только с отображением, но и с доступными операциями. Если старый клиент видит запись как подтверждённую и на основании этого может отменить её, сервер обязан определить, что именно означает такая отмена для нового состояния. Нельзя допускать, чтобы формально допустимый старый статус открывал операцию с другой бизнес-семантикой. Если безопасной проекции нет, соответствующую операцию следует запретить для старого контракта или потребовать обновления клиента.

Важно, чтобы оба поля вычислялись из одного внутреннего состояния, а не обновлялись независимо. Иначе рано или поздно сервер вернёт противоречивую пару, например status: 3 и state: "confirmed". Соответствие значений должно быть определено явно, покрыто тестами и сохраняться на всём протяжении перехода.

Следующая стадия, переход, содержит неудобство, которое редко замечают заранее: сервер в обычном обмене не видит, какие поля клиент читает. Он знает, кто вызвал операцию, но не знает, использует ли клиент status. Поэтому поле убирают не по наблюдению за полем, а по составу клиентов: известно, что сборки до 4.0 читают status, а сборки 4.0 и новее используют state, и убрать поле можно, когда последняя сборка, зависящая от status, выйдет из срока поддержки.

Номер сборки сам по себе не доказывает, что клиент больше не использует поле. Это должно следовать из проверенной реализации и политики поддержки. Если есть сомнения, для критичных потребителей необходимо получить подтверждение владельца или проверить использование через специально реализованную телеметрию.

Наблюдение на уровне поля возможно, если его специально реализовать: например, через отдельные GraphQL-поля, инструментирование сериализатора или контрактные тесты, фиксирующие конкретные ожидания потребителя. Но обычный HTTP-запрос не сообщает серверу, какие поля клиент использовал после получения ответа. Даже запись факта отправки поля не доказывает, что клиент от него зависит.

Стадия сжатия — удаление status — наступает после объявленного срока, проверки миграции потребителей и подтверждения, что оставшиеся клиенты больше не зависят от старого поля. Для критичных интеграций одного отсутствия запросов в течение короткого окна недостаточно: необходимы подтверждение владельца или наблюдение, покрывающее реальный цикл работы.

Тот же вопрос через /v2/ решается иначе. Сервер выпускает v2 со строковым статусом, v1 продолжает отдавать число, и именно разделение представлений не позволяет новому формату случайно попасть к старому клиенту. Но v2 — целый интерфейс: все операции, даже не менявшиеся, должны быть доступны под новым номером, клиент вынужден переносить весь код ради одного поля, а команда несёт две версии ради одного изменения.

Новая версия оправдана, когда изменение нельзя выразить добавлением: у записи стало несколько услуг вместо одной (изменилась кратность связи), поменялась модель авторизации, операция получила другую семантику, сменилась модель постраничной выдачи. Такие изменения накапливаются и выходят пакетом, а не по одному.

При этом переход на v2 не означает, что вся реализация должна быть скопирована. Различаться могут внешние контракты, а бизнес-логика и внутренние модели оставаться общими.

Путь удобен для API, которым пользуются несколько собственных клиентов и внешние потребители с понятным графиком миграции. Для публичного API с десятками интеграторов подходит версия, закреплённая за конкретным потребителем или интеграцией: интегратор сам решает, когда перейти, и не получает новый контракт после очередной выкладки сервера. Такая модель используется, например, в API с датированными версиями.

Заголовок оправдан, когда клиенту нужно выбирать представление ресурса независимо от адреса. Если версия выбирается через Accept, необходимо учитывать согласование представления и кеширование: ответ должен корректно различаться по заголовку, а промежуточные кеши — учитывать соответствующий Vary: Accept. Для собственного заголовка версии действует тот же принцип: кеш не должен отдавать одному клиенту ответ, сформированный для другой версии. В таком случае в Vary указывают и этот заголовок. При этом одного Vary недостаточно, если CDN или другой промежуточный кеш настроен игнорировать его: ключ кеширования должен действительно учитывать выбранную версию. Если кеширование не требуется, его можно отключить соответствующими директивами, но проблему смешения представлений всё равно нужно учитывать на уровне шлюзов и прокси.

Выбор параметра запроса обычно менее удобен: он смешивает версию контракта с параметрами конкретной операции и может усложнять кеширование и построение ссылок. Но в некоторых ограниченных интеграциях он остаётся приемлемым вариантом.

Для версии, закреплённой за потребителем, важно не путать версию контракта с версией самого ключа доступа. Ключ идентифицирует потребителя и его права, а версия определяет контракт, который он получает. Их жизненные циклы независимы. Не следует считать, что один ключ обязательно соответствует одной системе: если ключ используется несколькими интеграциями, версию лучше закреплять за отдельной записью потребителя или интеграции.

DEFAULT VERSION / POLICY
Что делать, если клиент не передал версию?

Здесь нет универсального правила, что сервер обязан выбрать самую старую или самую новую версию. Политика зависит от модели API.

01
Для публичного API, в котором версия обязательна, отсутствие заголовка или сегмента пути лучше завершать понятной ошибкой, а не выбирать контракт молча.
02
Если предусмотрена версия по умолчанию, она должна быть явно задокументирована и стабильна. Её нельзя незаметно менять при выпуске новой версии сервера.
03
Если версия закреплена за идентификатором потребителя, сервер может использовать эту настройку, но должен предоставлять владельцу способ проверить и изменить её.
04
Для внутренних API допустима фиксированная версия по умолчанию, если все потребители управляются одной командой и изменение политики проходит через контролируемый процесс.

Неявное переключение на самую старую версию не является универсальной защитой. Оно маскирует ошибки конфигурации и может заставить нового клиента работать с устаревшей моделью. Предсказуемость важнее удобства случайного запроса без версии.

И ещё одно правило: версия относится к контракту API целиком, если команда специально не выбрала модель независимого версионирования ресурсов. Раздельные версии ресурсов (/appointments/v2 рядом с /patients/v1) порождают таблицу допустимых сочетаний. Она не всегда невозможна, но требует отдельной политики совместимости и тестирования комбинаций. Для большинства API с общими бизнес-сценариями единая версия контракта проще и надёжнее.

В GraphQL (язык запросов, где клиент сам перечисляет нужные поля) обычно используют эволюцию единой схемы: поля добавляют, устаревшие помечают директивой @deprecated, а их использование отслеживают на уровне конкретных полей. Но сама директива не прекращает поддержку и не гарантирует обнаружение всех потребителей. Для безопасного удаления нужны телеметрия, понятный срок миграции и проверка фактического использования. При этом телеметрия должна учитывать идентичность потребителя: статистика по полю без понимания того, какая интеграция его запрашивает, недостаточна для принятия решения об отключении.

В gRPC с Protocol Buffers (бинарным форматом с нумерованными полями) номер поля, однажды выданный клиентам, не переиспользуют. Удалённые номера и имена резервируют, чтобы будущие изменения не привели к повторному использованию старого идентификатора. Резервирование имён особенно важно для JSON- и TextFormat-представлений, в которых имя поля участвует в сериализации. Совместимость типов, значений перечислений и семантики всё равно необходимо контролировать отдельно.

MULTI-VERSION ARCHITECTURE

Несколько версий без нескольких программ

Схем поддержки нескольких версий три.

01 / SEPARATE DEPLOYMENTS
Отдельное развёртывание для каждой версии

Изоляция полная, но каждое исправление, включая закрытие уязвимости, приходится переносить в каждую копию. Копии расходятся, а общая база данных заставляет их все быть совместимыми с одной схемой. Это годится на короткий срок, когда старая версия доживает последние недели, либо когда версии действительно должны быть изолированы по требованиям безопасности или эксплуатации.

02 / VERSIONED DTO
Единый код со слоем представления для каждой версии

Бизнес-логика одна, у каждой версии своя модель ответа (DTO, data transfer object: объект, описывающий форму данных на границе системы) и маппинг в неё. Дублируется только форма. Схема работает, пока версии различаются форматами, а не логикой. Если различается бизнес-поведение, его придётся выделять в отдельные политики или ветви, иначе слой представления начнёт незаметно принимать решения, не относящиеся к сериализации.

03 / TRANSFORMATION CHAIN
Цепочка преобразований

Ядро знает только последнюю версию. На входе запрос старой версии поднимается к последней шаг за шагом (v1 в v2, v2 в v3), на выходе ответ опускается обратно. Каждое звено знает разницу только между соседними версиями, поэтому новая версия добавляет одно звено и не умножает число сочетаний.

Допустим, в v3 у записи список услуг, а в v2 — ровно одна услуга. Для примера зафиксируем контракт: v2 требует поле service, а в v3 поле services должно содержать ровно один элемент, если ответ необходимо представить в v2. Пустой список и несколько услуг в v2 выразить нельзя, поэтому преобразователь должен завершиться явной ошибкой, а не терять данные.

PYTHON / RESPONSE TRANSFORM V3 → V2
from typing import Any


class UnsupportedVersionError(Exception):
    """Запрошенная версия контракта не поддерживается."""


class UnrepresentableResponseError(Exception):
    """Состояние нельзя без потери смысла представить в старом контракте."""


class ContractValidationError(Exception):
    """Внутреннее представление не соответствует ожидаемой схеме."""


def validate_v3_response(body: dict[str, Any]) -> None:
    if not isinstance(body, dict):
        raise ContractValidationError("Ответ v3 должен быть объектом")

    if not isinstance(body.get("id"), str):
        raise ContractValidationError("В ответе v3 отсутствует строковый id")

    services = body.get("services")
    if not isinstance(services, list):
        raise ContractValidationError("Поле services должно быть массивом")

    for service in services:
        if not isinstance(service, dict):
            raise ContractValidationError(
                "Каждый элемент services должен быть объектом"
            )


def validate_v2_response(body: dict[str, Any]) -> None:
    if not isinstance(body, dict):
        raise ContractValidationError("Ответ v2 должен быть объектом")

    if not isinstance(body.get("id"), str):
        raise ContractValidationError("В ответе v2 отсутствует строковый id")

    if not isinstance(body.get("service"), dict):
        raise ContractValidationError(
            "Поле service должно быть объектом"
        )


def v3_to_v2_response(body: dict[str, Any]) -> dict[str, Any]:
    validate_v3_response(body)

    services = body["services"]

    if len(services) != 1:
        raise UnrepresentableResponseError(
            "Контракт v2 поддерживает ровно одну услугу"
        )

    result = {
        "id": body["id"],
        "service": services[0],
    }

    validate_v2_response(result)
    return result

Это иллюстрация механизма, а не готовый слой API: в рабочей реализации необходимы полные схемы валидации запросов и ответов на границах, обработка ошибок преобразования и отдельные правила для операций чтения и записи. В частности, преобразователь не должен молча отбрасывать неизвестные поля, подставлять значения по умолчанию вместо обязательных данных или возвращать null, если целевой контракт этого не допускает.

Ошибки преобразования также должны иметь определённое отображение на HTTP-ответы. Неподдерживаемая версия контракта, некорректный запрос и невозможность представить состояние в старом формате — разные ситуации, для которых следует определить отдельные машиночитаемые коды ошибок.

Особенно важно учитывать операции записи. Если бизнес-действие уже выполнено, но сервер не смог преобразовать результат в формат старого клиента, нельзя представлять ситуацию как обычный отказ операции: клиент может повторить запрос и создать дубликат записи или повторно провести платёж. Сервер должен обеспечить возможность безопасно определить результат первоначального выполнения, например через сохранённый результат идемпотентной операции или отдельный механизм получения состояния по идентификатору операции. Повтор запроса с тем же ключом идемпотентности не должен запускать бизнес-действие заново.

Нельзя автоматически превращать ограничение совместимости в 500 Internal Server Error, если причина не в неисправности сервера. Выбранный HTTP-код должен соответствовать семантике конкретной операции и быть задокументирован. Невозможность представить результат чтения и отказ в выполнении неподдерживаемой команды могут требовать разных ответов.

Важное различие: ограничения чтения и записи не совпадают. Сервер иногда может представить новое состояние старому клиенту в упрощённом виде, но не может безопасно принять от него команду, потому что старый контракт не выражает нужные параметры. Поэтому преобразования запросов и ответов проектируют отдельно, а совместимость чтения не считают доказательством совместимости записи.

TRANSFORMATION CHAIN / FAILURE POINTS
01
Потеря данных при понижении

Клиент v2 видит только одну услугу визита. Если в v3 услуг несколько, нельзя просто вернуть первую: клиент может затем отменить «свою» услугу, а сервер должен решить, что отменяется — вся запись или одна из нескольких услуг. Преобразование формата ответа этого не определяет. Нужны бизнес-правило и решение продукта. Если представить состояние без потери смысла невозможно, сервер должен явно сообщить, что операция недоступна в старой версии, а не выдать неполные данные за полные.

 
02
Изменение логики, а не формата

Если в v3 запись подтверждается только после предоплаты, клиент v2, не знающий этого шага, пройти его не может. Остаются варианты: серверное поведение по умолчанию для старых клиентов, если оно безопасно; явная ошибка с требованием обновиться; либо отказ поддерживать операцию в старой версии. Нельзя обходить новое обязательное бизнес-правило только ради совместимости. Например, если предоплата стала требованием финансовой или регуляторной модели, старый клиент не должен получать возможность подтвердить запись в обход неё.

 
03
База данных

Версия API не равна версии схемы базы: миграции должны быть совместимы со всеми поддерживаемыми версиями одновременно, то есть тоже идти по схеме «расширить, затем сжать». Удаление столбца, который читает звено для v1, остаётся ломающим релизом, только происходит внутри системы.

Цепочка преобразований не всегда дешевле отдельных DTO. При большом числе версий каждое звено становится самостоятельным кодом, который нужно тестировать, документировать и поддерживать. Если версии существенно различаются, несколько явных адаптеров от внешних контрактов к общей внутренней модели могут быть понятнее цепочки последовательных преобразований. Выбор зависит от числа версий и характера различий, а не от стремления любой ценой сделать архитектуру универсальной.

Проверяют цепочку на двух уровнях: каждое звено отдельно и сквозной прогон записанных образцов для каждой поддерживаемой версии. Для операций записи дополнительно проверяют, что преобразования не меняют бизнес-смысл и не создают повторных побочных эффектов. Полезно также проверять преобразования на границах представимости: пустые коллекции, максимальное число элементов, неизвестные значения перечислений, null и состояния, которые нельзя выразить в старом контракте.

QUALITY GATES / CI & OBSERVABILITY

Как узнать о поломке до выкладки, а не из поддержки

Работают четыре слоя, и каждый ловит то, что пропускает предыдущий.

01 / SPEC DIFF
Сравнение спецификаций

OpenAPI — машиночитаемое описание HTTP-интерфейса: адреса, методы, схемы запросов и ответов. Утилиты сравнивают две редакции и классифицируют изменения на ломающие и потенциально безопасные; запуск в CI (continuous integration: автоматическая сборка и проверка при каждом изменении кода) может блокировать слияние.

Ограничения: смысловые изменения и недокументированное поведение не видны, а расхождение спецификации с кодом обесценивает проверку. Поэтому ответы сервера в тестах сверяют со спецификацией либо спецификацию генерируют из кода. При этом автоматическая классификация не заменяет инженерную проверку: добавление поля может быть безопасным для одного клиента и ломающим для другого. Важно также проверять не только наличие поля, но и его обязательность, допустимость null, ограничения значений и изменения кодов ошибок.

02 / CONSUMER CONTRACTS
Контрактные тесты, управляемые потребителем

Consumer-driven contract tests: каждый потребитель описывает конкретные сценарии взаимодействия — какие запросы отправляет и какие части ответа ожидает получить. На их основе формируется контракт, который сервер проверяет при каждой сборке.

Важно не переоценивать такой тест. Например, Pact формирует контракт из конкретных взаимодействий, описанных в тестах потребителя. Он проверяет именно эти сценарии, а не автоматически обнаруживает все поля, которые приложение использует во всех возможных состояниях. Если тест проверяет только ответ со статусом confirmed, он не доказывает, что клиент правильно обработает cancelled или новое значение перечисления.

Для собственных мобильных и веб-клиентов подход реалистичен, для внешних партнёров обычно нет, и там остаётся наблюдение за трафиком, тестовые среды и согласованные наборы примеров. Контрактные тесты также не доказывают корректность бизнес-смысла: они подтверждают соответствие зафиксированным ожиданиям. Поэтому сценарии должны покрывать не только типичные ответы, но и значимые границы, ошибки и неизвестные значения.

03 / TRAFFIC REPLAY
Воспроизведение записанных запросов

Набор типичных запросов каждой поддерживаемой версии проигрывается на кандидате в выпуск, ответы сравниваются с эталоном с поправкой на допустимые отличия: новые поля, идентификаторы, время.

Записи боевого трафика содержат персональные данные, и до попадания в тестовую среду, защищённую обычно слабее боевой, их необходимо обезличить. Но обезличивание — не единственная мера. Необходимо удалять токены авторизации, секреты, платёжные данные и другие чувствительные сведения, а сами тесты запускать в изолированной среде.

Особенно опасно воспроизводить запросы записи: создание записи, отмена приёма или проведение платежа не должны повторно выполнять реальные побочные эффекты. Для этого используют тестовые данные, подмену внешних систем, контролируемые обработчики и отдельные сценарии проверки идемпотентности. Простое повторное выполнение боевого запроса на рабочей системе недопустимо. Даже обезличенный запрос может содержать действующие идентификаторы объектов, токены, ключи идемпотентности или параметры, запускающие реальные действия. Поэтому воспроизведение следует выполнять в изолированной тестовой среде с тестовыми данными и подменёнными внешними системами. Перед использованием записи необходимо удалить или заменить не только персональные данные, но и все действующие секреты и идентификаторы, способные повлиять на реальные объекты. Само по себе обезличивание не делает запрос безопасным для повторного выполнения.

04 / LEGACY CLIENTS IN CI
Старые клиенты в CI

Самая строгая проверка — прогнать код разбора ответов самых старых поддерживаемых сборок, используя настоящие модели данных, а не тестовые заглушки. Строгий разбор версии 3.8 из начала статьи такая проверка поймала бы до выкладки.

Полезно проверять не только самую старую сборку, но и характерные промежуточные версии: иногда проблема появляется после перехода на определённую библиотеку или изменения модели данных. При этом не обязательно запускать каждую когда-либо выпущенную сборку — достаточно обоснованного набора поддерживаемых и наиболее распространённых вариантов. В набор следует включать версии, отличающиеся поведением сериализатора, схемами моделей и правилами обработки перечислений.

После выкладки график выпусков сервера сопоставляют с долей аварийных завершений и ошибок разбора по сборкам клиента. В примере от первой жалобы до отката прошло около сорока минут (с 07:52 до 08:30), и почти всё это время сигнал существовал только в поддержке, а не на графике.

Для этого в наблюдаемость включают как минимум:

01
Версия API и сборка клиента
02
Платформа и версия операционной системы
03
Идентификатор операции
04
Код и класс ошибки
05
Идентификатор потребителя или ключа доступа
06
Доля успешных запросов и бизнес-ошибок

Персональные данные и содержимое запросов не должны попадать в обычные метрики и логи без обоснованной необходимости. Для диагностики достаточно идентификаторов и агрегированных показателей, а доступ к чувствительным данным должен контролироваться отдельно. Идентификаторы потребителей также не следует без необходимости раскрывать в общедоступных метриках.

OBSERVABILITY / BUSINESS OUTCOME
HTTP 200 ещё не означает, что всё прошло правильно

Особенно важно различать техническую успешность и бизнес-результат. HTTP 200 не гарантирует, что запись создана в правильном статусе, а HTTP 4xx не всегда означает неисправность клиента. Для критичных операций наблюдают не только ответы API, но и фактические изменения бизнес-состояния.

API RETIREMENT / DEPRECATION

Как выводить версию из эксплуатации

Версия проходит стадии: действующая, устаревшая (работает, но объявлена к отключению), отключаемая на время (brownout), отключённая и, наконец, удалённая из кода. У каждой стадии свой сигнал потребителю и своё условие перехода.

01
Действующая
Версия доступна и поддерживается без объявленной даты отключения.
02
Устаревшая
Продолжает работать, но потребителям объявлены сроки и порядок миграции.
03
Brownout
Доступность старой версии временно ограничивается по объявленному расписанию.
04
Отключённая
Запросы к старой версии больше не обслуживаются.
05
Удалённая
Старые обработчики и преобразования удалены из кода после завершения периода восстановления.
01 / DEPRECATION NOTICE
Объявление об устаревании

В ответах устаревающей версии можно передавать заголовок Deprecation, стандартизированный в RFC 9745 и опубликованный в марте 2025 года. Он сообщает, что ресурс будет объявлен устаревшим в указанную дату или уже был объявлен устаревшим в прошлом. Эта дата не обязана совпадать с датой отправки письма потребителю: уведомление можно направить заранее, а сам ресурс объявить устаревшим в установленный день.

Для указания планируемого момента прекращения работы ресурса используется Sunset, определённый RFC 8594.

Заголовки решают разные задачи:

Deprecation

Сообщает, что ресурс объявлен устаревшим или будет объявлен устаревшим с указанной даты. Это не означает, что он уже перестал работать.

Sunset

Сообщает ожидаемую дату, после которой ресурс, вероятно, станет недоступен. Это объявление о намерении, а не безусловная гарантия конкретного HTTP-ответа.

Link; rel="deprecation"

Указывает на документацию об устаревании и порядке миграции.

Link; rel="sunset"

Может указывать на политику вывода ресурса из эксплуатации.

Пример ответа:

HTTP / DEPRECATION HEADERS
HTTP/1.1 200 OK
Deprecation: @1795651200
Sunset: Wed, 30 Jun 2027 00:00:00 GMT
Link: <https://api.example.ru/docs/migrate-v1-to-v2>; rel="deprecation"
Link: <https://api.example.ru/docs/api-retirement-policy>; rel="sunset"

Значение Deprecation иллюстрирует формат Structured Fields: дата передаётся как Unix-время в секундах с префиксом @. В примере это 26 ноября 2026 года, то есть дата объявления ресурса устаревшим. Значение Sunset использует другой формат — HTTP-date. Дата прекращения работы не должна предшествовать дате устаревания.

Эти заголовки стандартизированы, но не являются механизмом принудительного обновления. Клиент может их не читать, а промежуточные системы — не передавать. Кроме того, Deprecation относится к ресурсу, указанному в ответе. Sunset также действует в отношении ресурса, вернувшего заголовок, если сервер явно не документирует более широкую область действия. Если объявляется устаревание целой версии API, необходимо определить и документировать, какие операции входят в эту политику, а не предполагать, что один заголовок автоматически распространяется на все адреса.

02 / CONSUMER NOTIFICATION
Уведомление потребителей

Основной канал — письма техническим контактам из реестра с просьбой подтвердить получение, а для мобильных приложений — экран о необходимости обновиться. Старые сборки заголовков могут вообще не читать. Партнёрам необходимо сообщать дату отключения, новую версию, перечень несовместимых изменений, инструкцию миграции, тестовый контур и контакт для технических вопросов.

03 / MIGRATION WINDOW
Период миграции

Старая версия продолжает работать, пока потребители переходят на новую. Команда отслеживает не только число запросов, но и конкретных владельцев, операции и бизнес-нагрузку. Для важных интеграций миграция завершается после подтверждения владельца и проверки результатов, а не только после исчезновения ошибок.

04 / BROWNOUT
Временное ограничение доступности

Brownout — это плановое кратковременное ограничение доступности старой версии в рабочее время по заранее объявленному расписанию с нарастанием: 15 минут, час, сутки. Приём выявляет потребителей, игнорирующих уведомления, пока цена обнаружения мала: ошибка длится минуты, а не обнаруживается в день финального отключения.

Brownout — эксплуатационная практика, а не обязательная или стандартизированная стадия жизненного цикла API. Его применяют только там, где временная недоступность допустима и предусмотрена эксплуатационными соглашениями. Перед проведением необходимо проверить, как клиенты повторяют запросы, есть ли у операций идемпотентность, не приведёт ли повторная отправка к дублированию записей или платежей и кто будет реагировать на инцидент.

Для операций записи одной проверки наличия заголовка Idempotency-Key недостаточно. Сервер должен связывать ключ с конкретным потребителем и операцией, сохранять результат первого выполнения и при повторе возвращать этот результат, не выполняя бизнес-действие заново. Повторное использование того же ключа с другим содержимым запроса должно отклоняться. Срок хранения ключей должен покрывать допустимое окно повторов, а сохранение ключа и результата операции должно быть организовано так, чтобы сбой между выполнением действия и записью результата не приводил к повторному выполнению.

Это особенно важно при сетевом тайм-ауте: клиент может не получить ответ, хотя сервер уже создал запись или провёл платёж. Повтор без идемпотентности способен выполнить операцию второй раз. Поэтому клиент должен передавать тот же ключ при повторе одной логической операции, а сервер — уметь распознать её результат. Если операция не поддерживает безопасные повторы, brownout для неё следует проводить только после отдельной оценки риска или не проводить вовсе.

Повторные запросы должны ограничиваться по частоте и количеству попыток, использовать экспоненциальную задержку со случайным разбросом времени. Для временных отказов сервер может возвращать Retry-After, указывая, когда клиенту следует повторить запрос. Клиент должен учитывать этот заголовок, но не выходить за собственные ограничения по времени и количеству повторов. Иначе после завершения brownout множество клиентов могут одновременно повторить накопившиеся запросы и перегрузить восстановившийся сервис. Для операций записи повтор допустим только при наличии механизма идемпотентности или другого способа гарантировать отсутствие повторного бизнес-действия.

BROWNOUT / CLINIC EXAMPLE

Для клиники окно выбирают вне утренних пиков. Операции записи и отмены приёма требуют особой осторожности: кратковременное отключение может запустить повторные запросы и создать дубли.

Brownout для массового мобильного хвоста обычно не подходит, там работает принудительное обновление, если новая сборка доступна пользователю.

RETIREMENT / METRICS & DECISION

По каким данным решать, что версию пора выключать

Первая ошибка — смотреть на долю запросов.

Интеграция, опрашивающая сервер каждые 10 секунд, делает:

86400 / 10 = 8640
запросов в сутки

Пользователь приложения делает, допустим, 20 запросов в сутки, и:

8640 / 20 = 432

Один скрипт создаёт столько же трафика, сколько 432 человека. Два процента запросов в старой версии могут означать один скрипт, а могут тысячи людей. Поэтому считают различимых потребителей: организации, интеграции, ключи доступа, сборки клиентов и активные установки на них за скользящее окно в 30 дней.

Однако и эта метрика требует аккуратной интерпретации. Один ключ может обслуживать несколько интеграций, одна сборка — миллионы пользователей, а один пользователь может использовать несколько устройств. Поэтому показатели нельзя складывать как равнозначные единицы. Их рассматривают раздельно: количество организаций, интеграций, ключей, активных установок, пользователей и бизнес-операций.

Кроме числа потребителей, учитывают ещё несколько вещей.

Какие операции старой версии вызываются

Часто это две из сорока, и операции можно выключать по одной раньше версии целиком, если контракт и архитектура позволяют независимое отключение.

Бизнес-вес

Сколько записей, платежей и заказов проходит через старую версию. Число обращений этого не показывает.

Длина окна наблюдения

Оно должно покрывать самый длинный цикл потребителей: выгрузка для бухгалтерии раз в квартал, годовая отчётность, сезонный партнёр. Версия «молчит» не обязательно потому, что она больше никому не нужна. Для интеграций с отчётным циклом окно составляет не меньше квартала, а там, где есть годовые процессы, — год либо прямое подтверждение владельца.

Форма кривой миграции

Если число потребителей на старой версии перестало убывать, остался твёрдый остаток, и с ним работают поимённо, а не рассылкой.

Мобильный хвост

Сколько активных пользователей физически не может обновиться. Перед повышением минимальной версии подсчитывают тех, кто сидит на версиях ОС, где новая сборка не устанавливается. Принудительное обновление эти люди не пройдут.

Риски для критичных операций

Даже один оставшийся потребитель может быть основанием продлить поддержку, если через него проходят жизненно важные или юридически значимые операции.

Возможность восстановления

До отключения проверяют, что есть способ вернуть доступность, восстановить данные и связаться с ответственными лицами.

Отсутствие трафика само по себе не доказывает, что потребитель больше не существует. Он может запускать задание раз в квартал или год, временно приостановить работу либо обращаться к API только при наступлении определённого события. Для критичных интеграций решение об отключении принимают по совокупности телеметрии, длительности наблюдения и подтверждения владельца.

CASE STUDY / V1 RETIREMENT
Условная хронология отключения v1 при 14 ключах доступа
МЕСЯЦ 0
Выходит v2, v1 объявляется устаревшей, в её ответах появляется Deprecation и публикуется дата планируемого отключения через Sunset. Всем 14 владельцам уходит уведомление.
МЕСЯЦ 1
Девять владельцев подтверждают план миграции, трое молчат, у двух контакты недействительны (сотрудники ушли): 9 + 3 + 2 = 14.
МЕСЯЦ 3
Первый brownout на 15 минут. В течение дня звонят все трое молчавших, причём за одним из ключей оказывается ночной скрипт отдела, о котором никто не помнил. Контакты ушедших находятся через менеджеров по договорам.
МЕСЯЦ 4
На v2 перешли 12 ключей из 14. Один партнёр просит отсрочку из-за заморозки релизов в конце года, второй обещает перейти до конца месяца.
МЕСЯЦ 6
Второй из оставшихся перешёл. Для 13 ключей v1 закрывается на шлюзе, для партнёра с отсрочкой остаётся индивидуальная дата: 13 + 1 = 14.
МЕСЯЦ 7
Индивидуальная дата истекает, все запросы к v1 получают 410 Gone.
МЕСЯЦ 9
Тихий период позади, код звеньев преобразований удаляется.

В этой хронологии важно не только то, что все 14 ключей учтены. Перед отключением необходимо проверить, что за каждым ключом не скрывается неизвестный потребитель, не осталось фоновых заданий с редким циклом запуска и нет операций, которые выполняются реже выбранного окна наблюдения.

RETIREMENT / COST ANALYSIS

Сколько стоит держать старую версию и сколько стоит её выключить

Прямые расходы на старую версию складываются из звеньев преобразований, тестов, документации, мониторинга и обращений в поддержку. Два скрытых расхода заметнее прямых. Исправление ошибки или уязвимости приходится проверять во всех поддерживаемых версиях, причём некоторые исправления сами оказываются ломающими. А устаревший контракт ограничивает модель данных: кратность «одна услуга на запись» мешает ввести несколько услуг, пока жив клиент, который иного не понимает.

Расчёт на салфетке, все числа условные. Допустим, старая версия забирает 2 инженеро-дня в месяц на разбор регрессий и сопровождение тестов, а ещё на учёт при каждой новой функции уходит по полдня: при шести функциях за квартал:

6 × 0,5 = 3
дня в квартал

То есть 1 день в месяц.

Итого:

2 + 1 = 3
инженеро-дня в месяц

При условной полной стоимости 15 000 ₽ за инженеро-день:

3 × 15 000 = 45 000
рублей в месяц
 
45 000 × 12 = 540 000
рублей в год

Теперь хвост мобильного приложения. Допустим, 600 000 активных пользователей в месяц, из них 2,2 % сидят на сборках, привязанных к v1:

600 000 × 0,022 = 13 200
человек

При средней выручке на пользователя (ARPU, average revenue per user) 90 ₽ в месяц хвост приносит:

13 200 × 90 = 1 188 000
рублей выручки в месяц

Предположим, что принудительное обновление безвозвратно теряет 15 % хвоста:

13 200 × 0,15 = 1 980
человек
 
1 980 × 90 = 178 200
рублей выручки в месяц

Это примерно в четыре раза больше, чем стоит поддержка:

178 200 / 45 000 ≈ 3,96
DECISION

Выключать версию ради одной только экономии на сопровождении пока бессмысленно.

Условная точка равенства при этих допущениях:

45 000 / (0,15 × 90) ≈ 3 333
пользователя

Хвост должен сократиться примерно вчетверо — с 13 200 до 3 333 человек, — чтобы предполагаемая потеря месячной выручки сравнялась с расходами на поддержку.

Но здесь есть важное методологическое ограничение: выручка не равна прибыли. Для реального решения следует использовать маржинальный доход на пользователя, а не только ARPU. Кроме того, 15 % — условная вероятность потери, которую нужно оценивать по данным предыдущих принудительных обновлений или контролируемых экспериментов. Часть пользователей может обновиться позже, обратиться в поддержку или вернуться после решения проблемы.

Более корректная модель сравнивает ожидаемую потерю маржинального дохода с полной стоимостью поддержки старого контракта и с ценой изменений, которые он блокирует. Последняя часто оказывается важнее прямых расходов на тесты и сопровождение.

В расчёте также не учитываются затраты на разработку и выпуск новой сборки, поддержку пользователей старых операционных систем, возможное увеличение нагрузки на поддержку и стоимость альтернативного обслуживания. В реальном проекте эти составляющие могут существенно изменить результат.

Один партнёрский ключ с большим оборотом перевесит весь мобильный хвост, поэтому считают по потребителям, а не по средним. Отдельное замечание о способе поддержки: при цепочке преобразований стоимость растёт примерно линейно с числом версий, если каждое новое звено добавляет одну пару преобразований. При отдельных развёртываниях каждое исправление приходится проверять и переносить между копиями, а расходы растут вместе с числом независимых реализаций.

API VERSIONING / WHEN NOT TO VERSION

Случай, когда версионирование избыточно

Если у API единственный потребитель и он собирается и выкладывается вместе с сервером (внутренний сервис, фронтенд в одном репозитории с бэкендом, одна выкладка), отдельные номера версий контракта могут быть не нужны. Достаточно совместимости в окне выкладки и правильного порядка обновления компонентов.

Но даже в таком случае остаются требования к миграциям базы данных, откату и совместимости между одновременно работающими экземплярами. Если развёртывание выполняется поэтапно, старый и новый код некоторое время могут обращаться к одной базе. Поэтому отсутствие публичного версионирования не означает отсутствия требований к совместимости.

Появление второго потребителя, который обновляется отдельно, — момент, когда нужны формализованные правила изменения контракта. Общий признак такого момента: любое изменение ответа перестаёт быть вопросом одной команды.

READINESS CHECK

Готовность к правилам проверяется одним вопросом:

Можно ли по любой операции API за несколько минут сказать, кто её вызывает, на какой версии, какие операции использует и с кем связаться?

Если нет, порядок работ обратный привычному: сначала учёт потребителей (версия сборки в заголовках, идентификатор потребителя, контакт владельца, перечень используемых операций), затем правила изменения контракта и только потом номера версий.
